# 高宇 NL2DSL 简历面试参考答案

> 用法建议：这份文档不是逐字背诵稿，而是面试回答框架。涉及公司真实数据、上线规模、性能指标、准确率等内容时，建议按你能证明、能讲清的口径表达。

## 一、开场与项目总览

### 1. 你先用 3 分钟介绍一下自己，重点讲讲最近这个 NL2DSL 项目。

我有 8 年后端和数据工程经验，早期主要做 Java 后端、高并发数据接入、消息队列、算法服务集群和现场稳定性保障；最近几年更多转向企业级数据智能和大模型应用方向。

最近重点做的是一个面向数据治理平台的智能问数项目，我把它抽象成 NL2DSL：用户用自然语言提问，系统不是让大模型直接生成 SQL，而是先生成结构化 DSL。DSL 经过字段、指标、权限、安全、语义层校验后，再由系统构建 SQL 执行。

这个项目的核心价值是把大模型能力和企业数据治理结合起来。传统 NL2SQL 容易出现 SQL 幻觉、权限绕过、指标口径不一致和审计困难的问题，而 NL2DSL 通过语义层、权限注入、DSL 校验、SQL 安全扫描和链路审计，把查询过程变得可控、可解释、可追踪。

我在里面主要负责 Agent 查询链路、LangGraph 状态编排、RAG 召回、DSL 校验、权限注入、SQL 构建、自动化评测和开源项目沉淀。

### 2. 你这份简历定位是 AI Agent / NL2DSL / 大数据工程师，你自己觉得最核心的竞争力是什么？

我的核心竞争力是工程落地能力比较完整：既懂 Java 后端和线上稳定性，也做过 Spark SQL、元数据加工和数据质量；最近又把这些经验迁移到大模型应用里，做了 NL2DSL、RAG、Agent 编排和评测体系。

所以我不是只会调 LLM API，也不是纯算法方向，而是能把企业数据治理、后端工程、大数据加工和 AI Agent 串成一条可落地的链路。

### 3. 智能数据查询平台是公司项目还是个人开源项目？两者之间是什么关系？

建议回答时主动区分：

公司项目是实际业务场景中的智能数据查询平台，主要面向业务人员自然语言查数。个人开源项目 `nl2dsl-engine` 是我基于工作中的问题意识和个人理解做的抽象与复现，重点沉淀了 NL2DSL 架构、DSL 校验、RAG、权限治理、审计和评测框架。

公司项目和开源项目不是简单等同关系。公司项目偏业务落地，开源项目偏技术抽象和可展示实现。面试时我可以通过开源项目讲清架构思想和代码实现，但不会把公司内部细节、数据和业务配置放出来。

### 4. 你在公司项目里负责哪些模块？开源项目里又是怎么复现或沉淀的？

公司项目里我主要参与智能问数核心链路，包括关键词提取、Schema/字段/指标召回、Rerank、SQL/DSL 生成、链路日志、评测和性能优化。

开源项目里我把这些能力抽象成更清晰的 NL2DSL 架构：FastAPI 提供接口，LangGraph 组织查询管道，RAG 召回语义层上下文，Pydantic 做 DSL 校验，SQLAlchemy 构建 SQL，sqlglot 做方言处理，并补了权限、审计、评测和多领域配置。

### 5. 这个项目解决的真实业务问题是什么？用户是谁？使用场景是什么？

解决的是业务人员查数门槛高的问题。传统上业务要查一个数，需要知道表名、字段名、指标口径，或者找数据开发帮忙写 SQL。智能问数希望让业务直接问“华东近7天销售额最高的商品”，系统自动理解指标、维度、过滤条件和权限，返回结果。

用户主要是业务运营、数据分析、管理人员，也包括数据治理平台中的数据消费方。典型场景是经营分析、指标查询、报表探索、异常排查和临时取数。

### 6. 你说“面向数据治理平台”，具体接入的是哪些治理资产？

主要接入这些治理资产：

- 指标口径：比如销售额、GMV、订单数的标准计算方式。
- 维度定义：地区、商品、用户类型、时间等维度及其物理字段映射。
- 数据源定义：主表、关联表、Join 关系、可用指标和维度。
- 术语词典：业务别名，比如“流水”映射到 GMV。
- 权限策略：行级权限、列级权限、敏感字段和脱敏规则。
- 历史样例：历史问题和标准 DSL，用于 RAG few-shot。

### 7. 你做的是 NL2SQL 还是 NL2DSL？为什么简历里强调 DSL？

从用户视角看，它是自然语言查数，最终确实会执行 SQL；但从系统架构看，我更强调 NL2DSL，因为中间多了一层结构化 DSL。

传统 NL2SQL 是自然语言直接生成 SQL，SQL 是自由文本，不好校验、权限不好注入、审计也不清晰。NL2DSL 是先生成结构化 DSL，DSL 里表达指标、维度、过滤、排序、分页等语义，再由系统负责生成 SQL。这样安全性、可控性和可治理性更好。

### 8. 这个项目目前做到什么程度？是 Demo、内部工具、生产系统，还是开源验证项目？

建议按真实情况回答：

公司侧是业务场景下的智能查询平台，承担真实业务查询链路。个人开源项目是我对该类系统的技术抽象和验证实现，已经包含 API、Agent/Graph 查询管道、DSL 校验、权限、安全扫描、RAG、审计、评测和前端展示等模块。

如果被追问生产规模，不要硬编。可以说：开源项目主要用于架构展示和面试讲解；公司项目的上线范围和指标以内部实际为准，不方便展开内部数据。

## 二、NL2DSL 架构设计

### 1. 为什么不直接让 LLM 生成 SQL，而要先生成 DSL？

因为 SQL 是自由文本，直接生成 SQL 有几个问题：

- 不好校验：字段、指标、函数、Join 是否合法，需要解析 SQL 才知道。
- 权限不可控：SQL 生成后再改字符串注入权限，容易漏掉子查询、UNION 等场景。
- 方言复杂：MySQL、PostgreSQL、ClickHouse 等语法差异大。
- 审计困难：很难从 SQL 里还原用户到底想查什么业务指标。

DSL 是结构化语义契约。LLM 只负责生成受约束的结构，系统负责校验、权限、优化和 SQL 构建。这样可以把大模型的不确定性限制在可控范围里。

### 2. DSL 里包含哪些核心字段？metrics、dimensions、filters 分别代表什么？

核心字段一般包括：

- `data_source`：使用哪个业务数据源。
- `metrics`：要计算什么指标，比如销售额、订单数。
- `dimensions`：按什么维度分组或展示，比如地区、商品。
- `filters`：过滤条件，比如地区=华东、时间=近7天。
- `order_by`：排序规则。
- `limit`：返回条数。
- `post_process`：TopN、占比、趋势、同比环比等后处理。

metrics 是被聚合的值，dimensions 是切分和筛选数据的维度，filters 是查询条件。

### 3. DSL 到 SQL 的转换链路是怎样的？

大致流程是：

自然语言输入 -> RAG 召回语义上下文 -> LLM 生成 DSL -> DSL 结构校验 -> 指标/字段语义校验 -> 权限注入 -> 语义解析 -> SQLAlchemy 构建标准 SQL -> sqlglot 做方言处理 -> SQL 安全扫描 -> 沙箱预检 -> 执行 SQL -> 返回结果和审计日志。

### 4. DSL 校验具体校验哪些内容？

主要校验：

- data_source 是否存在。
- metric 是否注册。
- dimension 是否注册。
- filter 字段是否是合法维度。
- 操作符和字段类型是否匹配。
- limit 是否超过上限。
- order_by 字段是否在输出字段中。
- 是否访问敏感列或未授权指标。
- DSL 结构是否符合 Pydantic Schema。

### 5. LLM 生成了不存在的字段或指标怎么办？

第一步在 DSL 校验阶段拦截。比如指标未注册、字段不存在，会产生明确错误。

第二步进入修正链路：根据错误信息提取关键词，做定向 RAG 召回，把更准确的指标、维度、术语上下文补给 LLM，让它重新生成 DSL。

如果重试后仍不通过，就返回可解释错误或触发澄清，不会继续构建 SQL。

### 6. 指标口径是由 LLM 决定，还是由系统注册表决定？

由系统注册表决定。LLM 只能选择指标 alias，比如 `sales_amount`，不能自己发明 `SUM(pay_amount)` 的口径。

真正的指标表达式来自语义层配置，例如 `sales_amount = SUM(pay_amount)`。这样可以保证所有查询使用统一口径。

### 7. “销售额”这种业务指标如何映射到底层 SQL 表达式？

流程是：

用户说“销售额” -> 术语和指标召回找到 `sales_amount` -> LLM 在 DSL 里生成 metric alias -> SemanticResolver 根据注册表把 alias 展开成 `SUM(pay_amount)` -> SQLBuilder 生成 SQL。

关键点是：LLM 负责识别意图，系统负责口径展开。

### 8. 如果用户问“华东近7天销售额最高的5个商品”，系统完整执行流程是什么？

系统会先判断这个问题没有歧义，然后 RAG 召回：

- 销售额指标定义。
- 华东对应的地区编码或枚举值。
- 近7天的时间解析规则。
- 商品维度字段。

LLM 生成 DSL：metric 是销售额，dimension 是商品，filters 包含地区=华东和日期>=近7天，order_by 是销售额倒序，limit 是 5。

然后系统校验 DSL，注入用户权限，解析指标为 SQL 表达式，构建 SQL，做安全扫描和沙箱预检，执行后返回 Top5 商品和销售额，同时记录 trace 和审计日志。

### 9. 你提到 10+ 个 LangGraph 节点，能按顺序画一下流程吗？

可以按这个顺序讲：

`clarification -> decompose -> rag_retrieve -> generate_dsl -> validate_dsl -> correct_dsl -> permission_check -> resolve_semantic -> build_sql -> scan_sql -> sandbox_check -> execute_sql -> verify_dsl -> audit_log`

其中 `correct_dsl`、`sandbox_check`、`execute_sql` 都有条件分支。比如 DSL 校验失败会进修正，沙箱风险高会走人工审核，SQL 执行失败可以走简化 DSL 重试。

### 10. LangGraph 在这里解决了什么问题？不用 LangGraph 可以吗？

不用 LangGraph 也可以用普通 pipeline 写，但 LangGraph 的优势是状态流转、条件分支、失败重试和链路可观测更清晰。

这个项目不是简单一次请求调用 LLM，而是有歧义检测、RAG、DSL 校验、修正、权限、安全、执行、审计等多个状态。LangGraph 适合把这些节点编排成可维护的状态机。

### 11. Agent 层和 Graph 层为什么要分开？

Agent 层处理“查什么”，比如意图识别、复杂查询拆解、子查询调度、结果聚合和解释。

Graph 层处理“怎么查”，也就是单个查询从 DSL 到 SQL 执行的稳定链路。

分开后，复杂查询编排和底层执行可以独立演进。Agent 改意图识别，不影响 DSL 校验和 SQL 构建；Graph 做安全治理，也不关心上层是单查询还是多查询。

### 12. 复杂查询拆解后，多个子查询之间如何并行、串行或聚合？

Agent Planner 先识别意图，比如 compare、trend、ranking、proportion。Dispatcher 根据意图拆成子查询。

没有依赖的子查询可以并行执行，有依赖的顺序执行。每个子查询都走 Graph 管道，最后 Aggregator 根据意图做 diff、growth_rate、trend_direction、ranking 等聚合。

### 13. Graph 节点之间传递的 State 结构大概长什么样？

State 一般包含：

- 原始 question。
- domain / user_id / tenant_id。
- 检索上下文。
- 当前 DSL。
- SQL。
- 执行结果。
- 权限信息。
- trace。
- 错误信息。
- 重试次数。

核心是所有节点只读写自己负责的字段，避免节点之间强耦合。

### 14. 节点失败后怎么处理？哪些失败可以重试，哪些必须终止？

DSL 生成失败、校验失败、RAG 召回不足、SQL 执行失败属于可重试或可修正问题。

权限拒绝、危险 SQL、安全扫描失败、敏感字段越权、达到最大重试次数属于必须终止。

原则是：语义不确定可以澄清或修正，安全和权限问题不能靠重试绕过。

### 15. correct_dsl 是怎么工作的？

correct_dsl 会读取 DSL 校验错误，比如“指标不存在”或“字段不存在”，然后从错误里提取关键词，做定向 RAG 召回，把可能正确的指标、维度或术语补充给 LLM，让它重新生成 DSL。

它不是盲目让 LLM 再试一次，而是带着错误原因和补充上下文修正。

### 16. 如何避免 DSL 修正陷入死循环？

通过最大重试次数和进展检测控制。

比如 `dsl_attempts` 每次重试递增，超过上限直接返回错误。如果新 DSL 和旧 DSL 没有变化，也认为没有进展，提前终止。

### 17. SQLAlchemy 和 sqlglot 分别解决什么问题？

SQLAlchemy 负责用结构化方式构建 SQL，避免字符串拼接，提高安全性和可维护性。

sqlglot 负责 SQL 方言解析和转换，比如将标准 SQL 转成不同数据库可执行的语法，也可辅助 SQL 检查。

### 18. sqlglot 方言转换在什么场景下有价值？

当同一套 DSL 查询引擎要支持 MySQL、PostgreSQL、ClickHouse、SQLite 等不同数据库时，日期函数、分页、字符串函数、引号规则可能不同。sqlglot 可以降低多方言适配成本。

## 三、RAG、向量检索与 Rerank

### 1. 你的 RAG 检索召回哪些内容？

主要召回：

- Schema：表、字段、字段描述、主键和 Join 关系。
- Metrics：指标名、业务口径、计算表达式。
- Terms：业务术语和别名，比如流水、GMV。
- History：历史问题和标准 DSL 样例。
- Permissions：必要时给权限校验提供上下文。

### 2. 为什么用 Milvus Lite？为什么不是 Elasticsearch？

开源项目里主要是向量语义检索，所以用了 Milvus Lite，轻量、部署简单，适合本地和开源演示。

Elasticsearch 更适合倒排索引、关键词检索和日志检索。NL2DSL 开源项目目前没有使用 Elasticsearch，关键词召回主要是 jieba 分词加向量库/本地逻辑实现。

### 3. 你项目里到底有没有 Elasticsearch？

开源项目没有 Elasticsearch。简历里如果问到，我会明确说明：公司项目或其他实践里可能有 ES 场景，但这个开源 NL2DSL 以 Milvus Lite、BGE、jieba 和 MySQL/SQLite 为主。

### 4. jieba 关键词检索和向量检索分别适合什么场景？

关键词检索适合短词、精确匹配和业务术语，比如 GMV、销售额、华东。

向量检索适合语义相似，比如用户说“业绩”“流水”“成交金额”，系统要召回销售额或 GMV。

两者结合可以兼顾精确性和泛化能力。

### 5. BGE Embedding 和 BGE Reranker 的作用分别是什么？

BGE Embedding 把文本转成向量，用于初步召回 TopK 候选。

BGE Reranker 是 Cross-Encoder，用 query 和候选文本一起打分，用于对初召回结果精排。Embedding 更快，Reranker 更准但更贵，所以一般先召回再精排。

### 6. Reranker 为什么能替代 LLM 粗排？

LLM 粗排成本高、延迟大、输出不稳定。Reranker 是专门做相关性排序的模型，输入 query 和候选文本，输出相关性分数，延迟和成本更可控。

在候选数量不大的情况下，Reranker 能稳定完成语义相关性排序，比每次调用 LLM 判断更工程化。

### 7. “800ms 降到 80ms、成本降 90%”怎么测？

建议回答：

这是在同一批评测问题、相同候选规模下，对比“LLM 粗排”和“BGE-Reranker 精排”的平均耗时和调用成本得到的结果。统计方式是记录每次排序节点的耗时，取平均值和 P95。

如果面试官追问生产数据，就说明：具体数值来自评测集或实验链路，生产环境会受模型部署、机器配置和候选数影响。

### 8. 多关键词召回为什么会有性能问题？

如果一个问题拆出多个关键词，每个关键词都串行做 embedding 和向量检索，会导致延迟累加，同时连接池和向量库请求压力增加。

优化方式是批量 embedding、并发检索、热点结果缓存和减少无效关键词。

### 9. 热点关键词 Embedding 缓存怎么设计？

缓存 key 可以是 `domain + normalized_keyword + embedding_model_version`。

value 是 embedding 向量或召回结果。需要设置 TTL 或版本号失效机制，当模型版本或语义配置更新时避免旧缓存污染。

### 10. 如果 RAG 召回错了，后续链路怎么发现？

可能在几个环节暴露：

- DSL 校验失败，比如字段不存在。
- SQL 构建失败，比如指标无法展开。
- 结果验证失败，比如结果没有回答用户问题。
- 用户反馈纠错。
- 自动化评测低分。

链路追踪会记录 RAG context，方便回溯是不是召回阶段出了问题。

### 11. 向量库里每条记录存什么？

通常存：

- id。
- text：可嵌入的文本描述。
- vector。
- type：metric、dimension、term、history 等。
- name / alias。
- domain。
- metadata：来源表、字段名、指标表达式、业务描述等。

不是只存原始字段名，而是存更容易被语义检索命中的描述文本。

### 12. Schema 召回和指标召回应不应该放同一个 collection？

最好分开。Schema、metrics、terms、history 的文本长度、检索策略、更新频率和排序权重都不同。分 collection 可以更好地控制召回比例和权重，也方便排查问题。

### 13. 业务术语“流水”“GMV”“销售额”怎么处理？

通过 terms 术语词典和 metrics 指标注册结合处理。

比如“流水”作为术语别名映射到 `gmv`，`gmv` 再通过指标注册表展开成 `SUM(pay_amount)`。LLM 不直接决定口径，只选择语义 alias。

### 14. 字段取值召回怎么避免扫大表？

优先使用字典表、维表、枚举配置或离线加工好的高频值表。对于必须从事实表抽取的字段，做离线 DISTINCT 或 TopN 采样，不在查询时直接扫大表。

敏感字段和高基数字段要加入黑名单或采样限制。

### 15. 字段值有几百万个时怎么做召回？

不能全部塞进 Prompt。一般做：

- 高频值 TopN。
- 最近值样本。
- 字典表。
- 前缀/关键词检索。
- 分层索引。
- 只对必要字段做取值召回。

如果值域太大，还可以触发澄清或要求用户提供更明确条件。

### 16. RAG 召回结果如何注入 Prompt？有没有长度控制？

按类型分块注入：指标、维度、术语、历史样例分开。每类限制 TopK，总 token 控制在预算内。

重要原则是：基础 schema 和注册指标是权威上下文，RAG 只是增强，不能让 RAG 覆盖系统注册表。

### 17. RAG 召回不足时，LLM 会发生什么问题？

常见问题是发明字段、选错指标、过滤条件不准确、Join 关系错误、时间理解偏差。

所以后面需要 DSL 校验、语义解析、权限检查和执行验证兜底。

### 18. 如果用户问了系统没有注册过的指标，应该回答错误、追问，还是猜一个？

不能猜。可以返回“该指标未注册”或触发澄清，让用户选择相近指标。企业数据场景里指标口径比回答流畅更重要。

## 四、数据治理、权限与安全

### 1. 什么叫语义层治理模型？

语义层治理模型就是把业务可理解的指标、维度、术语、权限和物理数据库之间建立标准映射。

用户说“销售额”，系统知道它是 `sales_amount`，底层是 `SUM(pay_amount)`；用户说“华东”，系统知道对应地区编码；用户无权看某些区域或敏感字段，系统在 DSL 层注入限制。

### 2. 指标、维度、数据源、术语、权限策略分别如何配置？

一般用 YAML 或数据库表配置：

- metrics：指标名、表达式、描述、单位、数据源。
- dimensions：维度名、物理字段、枚举值、描述。
- data_sources：主表、Join 关系、可用指标和维度。
- terms：业务别名到指标/维度的映射。
- permissions：用户、角色、租户、行过滤、敏感列和脱敏规则。

### 3. 行级权限和列级权限分别在哪个阶段处理？

行级权限在 DSL 阶段注入 filters，比如用户只能看华东，就给 DSL 加 `region in ['华东']`。

列级权限在 DSL 阶段检查 dimensions 和 metrics 是否包含敏感字段或未授权指标，必要时拒绝或脱敏。

### 4. 为什么权限要在 DSL 层注入，而不是 SQL 生成后做字符串替换？

SQL 字符串替换容易出错，尤其是子查询、UNION、别名、括号和不同数据库方言场景。

DSL 是结构化的，在 DSL 层注入权限更清晰，也方便审计。系统知道注入了什么权限条件，为什么注入。

### 5. 敏感字段怎么处理？

敏感字段在权限配置里定义，比如手机号、身份证、薪资。

处理方式有三种：

- 无权限直接拒绝。
- 有权限正常返回。
- 部分权限返回脱敏值。

脱敏规则可以在 SQLBuilder 或结果后处理阶段执行，但权限判断要尽量前置。

### 6. SQL 安全扫描会扫描哪些危险模式？

主要拦截：

- DELETE、UPDATE、DROP、ALTER、TRUNCATE。
- UNION 注入。
- 多语句分号。
- 注释注入。
- 存储过程执行。
- 非 SELECT 查询。
- 全表扫描或超大扫描风险。

### 7. 沙箱预检是怎么做的？

执行前先用 EXPLAIN 或 LIMIT 预览估算扫描量和执行计划。如果扫描行数过大、没有命中分区或索引、Join 代价过高，就拒绝、降级或进入人工审核。

它解决的是“SQL 语法安全但执行代价过高”的问题。

### 8. 审计日志记录哪些字段？

记录 query_id、user_id、tenant_id、question、DSL、SQL、状态、耗时、返回行数、扫描行数、trace_json、错误码、错误信息、创建时间等。

### 9. 如果用户越权查询，系统返回什么？

应该返回明确但不泄露敏感信息的错误，比如“当前用户无权限访问该指标或字段”。审计日志记录越权行为、用户、问题和被拒绝字段。

### 10. 多租户场景下怎么隔离？

从几个层面隔离：

- 每个租户独立语义配置或 domain context。
- 向量库按租户或领域隔离。
- 数据库连接按租户路由。
- DSL 校验带 tenant 上下文。
- 权限注入默认带 tenant_id。
- 缓存 key 包含 tenant/domain。

### 11. 提示词注入怎么防？

核心是不信任 LLM。即使用户说“忽略权限”，LLM 也只能生成 DSL。DSL 后面还有语义校验、权限注入、SQL 安全扫描和沙箱预检。

安全不依赖 Prompt，而依赖系统结构性约束。

### 12. LLM 生成 DSL 时包含敏感字段在哪层拦截？

在 permission_check 或 semantic validation 阶段拦截。敏感字段属于列级权限，用户无权限时拒绝或脱敏。

### 13. 如果 SQLBuilder 有 bug，安全扫描还能兜底吗？

能兜一部分，比如危险关键字、多语句、非 SELECT 和明显注入。但如果 SQLBuilder 生成了业务语义错误但语法安全的 SQL，安全扫描发现不了，需要评测、审计和结果验证补充。

### 14. 权限注入会不会影响结果准确率评估？

会。所以评测时要区分语义过滤和治理过滤。比如用户本来问华东销售额，系统又注入 tenant_id，这不应该被判为语义错误。评分时需要剥离或单独记录治理注入条件。

### 15. 审计日志和链路追踪有什么区别？

审计日志面向合规，记录谁在什么时间查了什么、执行了什么 SQL、是否成功。

链路追踪面向工程排查，记录每个节点输入输出、耗时、错误和中间 DSL。

## 五、自动化评测体系

### 1. 自动化评测具体怎么评？

准备一批自然语言问题和 expected DSL / expected SQL / expected result。执行完整查询链路后，对比 actual 和 expected。

评测不只看最终结果，还看语义、规划、执行和治理四类指标。

### 2. Semantic、Planning、Execution、Governance 分别是什么？

- Semantic：意图、指标、维度、过滤条件是否理解正确。
- Planning：Join、排序、Limit、分组等查询计划是否合理。
- Execution：SQL 是否执行成功，结果是否正确。
- Governance：权限、脱敏、审计是否生效。

### 3. DSL 生成质量如何量化？

把 DSL 拆成多个维度评分：metric 是否匹配、dimension 是否匹配、filter 字段和操作符是否匹配、order_by 和 limit 是否正确。每个维度有权重，最后加权得到总分。

### 4. SQL 执行成功率和结果准确率怎么计算？

SQL Success 是 SQL 是否能执行成功。

Result Accuracy 是执行结果是否和预期结果一致，可以比较行数、指标值、排序、TopN、分组结果等。

### 5. 权限注入、脱敏、审计覆盖怎么测？

设计专门用例：

- 用户无权限访问某区域，应自动注入过滤条件。
- 用户访问敏感字段，应拒绝或脱敏。
- 每次查询后必须生成 audit log。

评测时检查 DSL、SQL、结果和审计表。

### 6. 基线对比和回归门禁怎么做？

先保存一个稳定版本的评测结果作为 baseline。每次改 RAG、Prompt、DSL 校验、Optimizer 或 SQLBuilder 后，重新跑评测。

如果 overall score 下降、关键维度下降超过阈值、新增失败用例或执行错误，就阻断合并。

### 7. 新增优化规则怎么验证没有弄坏已有能力？

用相同测试集跑改动前后对比，看新增通过用例和新增失败用例。还要看每个维度的 diff，确认优化规则没有误改正确 DSL。

### 8. 测试集怎么构造？

可以由三部分组成：

- 人工设计核心场景。
- 线上历史问题脱敏后抽样。
- 典型失败案例沉淀。

每个用例最好只测试一个主要能力，方便定位。

### 9. 评测失败时如何定位问题？

看 trace：

- RAG context 错，说明召回问题。
- LLM 原始 DSL 错，说明 Prompt 或上下文问题。
- validate_dsl 失败，说明语义层或 DSL 生成问题。
- build_sql 失败，说明 SQLBuilder 或语义解析问题。
- execution 错，说明数据库、方言或数据问题。
- governance 错，说明权限配置或注入逻辑问题。

## 六、数据资产与语义层元数据加工平台

### 1. 这个大数据项目和 NL2DSL 是什么关系？

它是 NL2DSL 的上游治理数据底座。NL2DSL 要准确理解自然语言，需要知道有哪些表、字段、指标、维度、枚举、术语和权限。这些资产不能临时靠 LLM 猜，需要通过数据资产加工链路提前沉淀。

### 2. 元数据加工平台产出的数据给哪些模块使用？

给这些模块用：

- Schema 召回。
- 指标召回。
- 术语召回。
- 字段值召回。
- DSL 校验。
- 权限注入。
- 审计分析。
- 自动化评测数据集构造。

### 3. 业务表、字段、字段注释、指标口径、维度枚举、术语别名怎么加工？

业务表和字段来自数据库元数据；字段注释来自数据库 comment 或人工补充；指标口径来自指标配置；维度枚举来自字典表、维表或离线 DISTINCT；术语别名来自业务维护和用户反馈。

加工后统一落到元数据表，再同步成配置和向量索引。

### 4. Spark SQL 离线任务大概跑什么逻辑？

主要跑：

- 抽取表结构和字段信息。
- 统计字段空值率、重复率、值域分布。
- 抽取维度枚举 TopN。
- 聚合指标和业务域元数据。
- 生成元数据宽表。
- 输出质量报告和异常字段清单。

### 5. 元数据宽表长什么样？

核心字段包括：

`domain、table_name、column_name、column_type、column_comment、business_desc、metric_alias、dimension_alias、value_samples、is_sensitive、data_source、update_time、quality_score`

### 6. 指标元数据表怎么设计？

可以包含：

`metric_id、metric_name、metric_alias、business_desc、expr、unit、data_source、time_field、owner、enabled、version、created_at、updated_at`

关键是指标要有唯一 alias 和标准计算表达式。

### 7. 维度枚举值怎么采集？

优先级：

1. 字典表或维表同步。
2. 人工配置。
3. 离线 DISTINCT。
4. 高频 TopN 采样。

高基数字段和敏感字段不做全量枚举。

### 8. 字段注释质量差怎么办？

先做质量评分，比如过短、拼音缩写、纯英文缩写、无业务含义都标为低质量。

然后通过人工补充或 AI 辅助改写生成业务描述，但生产使用前必须人工审核。

### 9. 加工后的治理配置如何同步给向量库？

把指标、维度、术语、历史样例转成可嵌入文本，调用 embedding 模型生成向量，写入 Milvus collection。同步时保留 domain、type、name 等 metadata，并支持全量重建和增量更新。

### 10. 数据质量校验有哪些规则？

包括：

- 空值率。
- 重复率。
- 枚举值合法性。
- 数据量波动。
- 字段覆盖率。
- 主键唯一性。
- 分区完整性。
- 指标结果波动。
- 源表字段变更。

### 11. 大表 Join 性能问题怎么定位？

看 Spark UI、执行计划、Stage 耗时、Shuffle 数据量、Task 倾斜情况。重点看是否广播小表、Join key 是否倾斜、是否分区裁剪、是否扫描过多历史分区。

### 12. 分区扫描过大怎么优化？

增加时间分区过滤、分区裁剪、避免函数包裹分区字段、按业务域拆分任务、只处理增量分区。

### 13. 数据倾斜怎么判断和处理？

判断方式是看某些 task 明显慢、shuffle read 特别大。处理方式包括加盐、两阶段聚合、广播小表、过滤热点 key、拆分热点数据单独处理。

### 14. 历史数据重复计算怎么避免？

按分区增量处理，记录任务水位，使用幂等写入策略。历史分区只有在口径变更或修复数据时才重跑。

### 15. 任务失败后怎么重跑？如何保证幂等？

按业务日期和任务批次重跑。输出表采用先写临时表或临时分区，校验通过后再覆盖正式分区。避免重复 append。

### 16. 源表字段发生变化如何发现？

定时抽取数据库元数据，对比上一次 schema 快照，发现新增字段、删除字段、类型变化和 comment 变化，生成变更报告并触发语义层同步。

### 17. 指标口径变化，历史评测和线上查询怎么处理？

指标口径要做版本管理。新口径上线前跑评测集，确认影响范围。历史查询审计记录当时使用的指标版本，避免后续无法解释。

## 七、大数据基础、数仓与 Spark 调优

> 口径提醒：简历里大数据以离线为主（Spark SQL / Yarn / HDFS / 离线数仓 / 指标加工 / 数据质量 / 任务调优），没有 Flink 或实时流的主线项目。涉及 Structured Streaming、Lambda/Kappa 这类实时内容时，按“了解原理”讲，不要包装成主力方向；涉及具体数据量、优化百分比时，不硬编数字，按真实能讲清的口径表达。

### 1. 离线数仓一般怎么分层？ODS / DWD / DWS / ADS 各自的职责是什么？

离线数仓一般分 ODS、DWD、DWS、ADS（也叫 DM/APP）四层，有时前面加一层 STG 贴源层。

- ODS（贴源层）：原始数据，结构和源表基本一致，按天分区，保留历史，不做清洗或只做轻度去重。
- DWD（明细层）：清洗、标准化、维度退化后的明细事实表，字段规范、粒度统一，是数仓核心资产。
- DWS（汇总层）：按主题和维度预聚合，比如按天按区域汇总的订单宽表，提升下游查询效率。
- ADS（应用层）：面向具体报表、接口、标签的最终结果表，直接给 BI、接口或问数系统消费。

分层的目的：复用（明细只算一次）、解耦（源表变化不影响应用）、可控（每层职责清晰）、性能（汇总层减少重复扫描）。

在元数据加工平台里，我做的元数据宽表更接近 DWS/ADS 性质：把表、字段、指标、术语、质量分聚合好，给 NL2DSL 查询引擎和检索层消费。

### 2. 你用的是维度建模还是范式建模？星型模型和雪花模型区别？

- 维度建模（Kimball）：以事实表 + 维度表为核心。星型模型是事实表在中间、维度表围绕；雪花模型是维度表再拆成更细的子维度表（范式化）。优点是查询直观、聚合性能好，适合 OLAP 和报表。
- 范式建模（Inmon）：按三范式建企业级数仓，减少冗余、规范统一，但查询要 join 多张表，性能不如维度建模。

实际离线数仓多是混合：底层（ODS/DWD）偏范式或规范化明细，上层（DWS/ADS）用维度建模做星型宽表。我接触的指标加工更多是基于明细事实表做维度聚合，属于维度建模思路。

### 3. 事实表、维度表、缓慢变化维（SCD）怎么理解？SCD 有哪几种类型？

- 事实表：存度量值和维度外键，比如订单事实表存金额、数量、时间键、商品键、用户键。分事务型、周期快照、累积快照三种。
- 维度表：存维度属性，比如商品维表存商品名、类目、品牌。
- SCD（缓慢变化维）：维度属性会随时间变化，处理方式分几类：
  - SCD1：直接覆盖，不保留历史。
  - SCD2：新增一行，用有效时间起止字段保留完整历史，最常用。
  - SCD3：加一列历史值，只保留上一版本。
  - SCD6：SCD1+2+3 综合。

比如商品从 A 类目改到 B 类目，SCD2 会保留两条记录，便于历史时间点的指标按当时类目统计。

### 4. 指标体系怎么搭？原子指标、派生指标、复合指标的区别？

指标一般分三类：

- 原子指标：单一业务动作的度量，比如下单金额 = SUM(订单金额)，对应一个度量 + 一个业务过程。
- 派生指标：原子指标 + 修饰词 + 时间周期，比如“华东近7天下单金额”，由原子指标加维度过滤和时间窗组成。
- 复合指标：多个指标计算得出，比如转化率 = 下单数 / 访问数，GMV 同比、环比、占比。

搭建指标体系要统一口径、明确归属、做指标分级和复用。在元数据加工平台里，每个指标都要有唯一 alias、标准表达式、所属业务域、owner 和版本，避免不同报表口径不一致。这和 NL2DSL 里“指标口径由系统注册表决定”是同一套思路。

### 5. Spark 的 RDD、DataFrame、DataSet 有什么区别？你平时主要用哪个？

- RDD：Spark 最底层抽象，是不可变分布式对象集合，强类型但无 schema，优化空间小。
- DataFrame：以命名列组织的分布式数据集，类似关系表，有 schema，走 Catalyst 优化器，性能比 RDD 好。
- DataSet：DataFrame 的强类型版本，结合 RDD 的类型安全和 DataFrame 的优化。

我平时主要用 DataFrame / Spark SQL，因为开发效率高、能被 Catalyst 优化、便于调优。RDD 只在需要细粒度控制分区或处理非结构化数据时才用。

### 6. Spark 作业的执行流程是怎样的？Driver、Executor、Stage、Task 之间是什么关系？

大致流程：

1. 作业提交后 Driver 解析代码，构建 DAG。
2. DAGScheduler 把 DAG 按 shuffle 切分成多个 Stage，每个 Stage 是一组可并行的 Task。
3. TaskScheduler 把 Task 调度到 Executor 上执行。
4. Executor 负责具体计算，结果回写或 shuffle 给下一个 Stage。

Driver 负责任务调度和元信息，Executor 负责实际计算。一个 Application 里可以有多个 Job，一个 Job 多个 Stage，一个 Stage 多个 Task。

### 7. 什么是宽窄依赖？为什么 Stage 要按 shuffle 切分？

- 窄依赖：父 RDD 的一个分区最多被子 RDD 的一个分区使用，比如 map、filter。
- 宽依赖（shuffle 依赖）：父 RDD 的一个分区被子 RDD 的多个分区使用，比如 groupBy、非广播 join。

Stage 按 shuffle 切分是因为宽依赖需要 shuffle，shuffle 是同步边界，必须等上游 Stage 全部完成才能开始下游。窄依赖可以在一个 Stage 内流水线执行。

### 8. Spark Shuffle 大致过程是什么？为什么 shuffle 最容易出性能问题？

Shuffle 是把相同 key 的数据从多个上游分区拉到同一个下游分区的过程，涉及磁盘写、网络传输、排序/聚合。

过程大致是：上游每个 task 把输出按 key 分区写到本地磁盘（shuffle write），下游 task 拉取自己分区的数据（shuffle read）。

shuffle 容易出性能问题，因为磁盘 IO、网络传输、序列化、排序开销都大，还容易数据倾斜。优化方向包括减少 shuffle（用广播 join 替代 sort merge join）、减少 shuffle 数据量（先过滤再聚合）、处理倾斜 key。

### 9. Spark 任务怎么配资源？executor 数量、内存、core 怎么定？

主要参数：

- `--num-executors`：Executor 数量。
- `--executor-cores`：每个 Executor 的 CPU 核数，决定并发 task 数。
- `--executor-memory`：每个 Executor 内存。
- `spark.default.parallelism` / shuffle 分区数：控制 task 并发。

定法：根据集群资源、数据量、shuffle 量平衡。一般每个 task 处理 128MB~1GB 数据较合理；core 不宜过大（避免一个 Executor 挂掉丢太多 task，也影响并发）；内存要够放广播变量和 shuffle 数据，但不是越大越好。动态分配（dynamic allocation）适合资源波动的场景。

我会先看 Spark UI 的 task 数、executor 利用率、shuffle 量、GC 时间，再调参数，不盲目堆内存。

### 10. 广播变量和累加器分别用在什么场景？

- 广播变量：把只读变量（如小维表、配置字典）广播到每个 Executor，避免每个 task 重复拉取。最典型是 broadcast hash join，把小表广播后在大表侧做 map 端 join，避免 shuffle。
- 累加器：分布式只增计数器，用于统计全局指标，比如脏数据条数、处理失败记录数。注意累加器在 action 触发后才更新，transformation 里可能重复计算。

### 11. 小文件问题是怎么产生的？怎么解决？

产生原因：分区过多、shuffle 分区数过大、流式写入频繁、上游任务输出多小文件。

危害：NameNode 内存压力、任务调度开销、读取时大量 seek。

解决：

- 写入后用 `coalesce` 减少分区数，避免 shuffle，比 repartition 轻量。
- 用 `repartition` 重新分区，会触发 shuffle，适合需要重新分布时。
- Hive 端做 merge 小文件（`hive.merge.mapfiles` 等参数）。
- 控制分区粒度，避免过度分区。
- 输出文件格式用 ORC/Parquet，本身支持行组，比文本小文件影响小。

注意：`coalesce` 是缩小分区，不能可靠扩大；`repartition` 可以扩大但会触发 shuffle。

### 12. Hive 文件格式选 ORC 还是 Parquet？为什么要做压缩？

- ORC：Hive 生态常用，列存，压缩比高，带索引和统计信息，查询裁剪好。
- Parquet：Spark 生态更友好，列存，生态通用性更好，和 Spark/Impala 兼容好。

两者都是列存，适合分析型查询，能做列裁剪和谓词下推。文本格式（TEXTFILE）适合临时或兼容场景，但性能差。

压缩能减少存储和 IO。常用 Snappy（压缩比中等、速度快）、Zlib/Gzip（压缩比高、慢）、LZO（可切片）。离线数仓一般在存储用 ORC/Parquet + Snappy，平衡压缩比和查询速度。

### 13. SQL 调优：分区裁剪、谓词下推、列裁剪、mapjoin 分别是什么？

- 分区裁剪：查询时只读必要分区，WHERE 条件要用分区字段且不能被函数包裹（如 `date_format(dt)` 会让裁剪失效）。
- 谓词下推：把过滤条件尽量推到靠近数据源的位置，减少后续处理数据量。优化器会自动做，但写 SQL 时别把过滤写在外层。
- 列裁剪：只 select 需要的列，列存格式下尤其有效。
- mapjoin / broadcast join：小表广播到大表端做 map 侧 join，避免 shuffle，通过 hint 或自动广播阈值控制。

其它还有：避免 `select *`、避免笛卡尔积、join on 用等值条件、聚合先过滤再分组、用 distribute by 控制输出分布。

### 14. 数据质量怎么体系化保证？准确性、完整性、一致性、及时性、唯一性分别怎么落？

数据质量一般从几个维度看：

- 准确性：数据是否反映真实业务值。
- 完整性：字段是否缺失、空值率。
- 一致性：跨表、跨系统口径是否一致。
- 及时性：数据是否按时产出。
- 唯一性：主键是否重复。

落地方式：每张关键表配质量规则（空值率、重复率、枚举合法性、数据量波动、主键唯一、分区完整性、指标结果波动），离线任务跑完后做质量校验，不达标告警或阻断下游。在元数据加工平台里，我加了字段质量分和异常字段清单，辅助发现源表变更和字段缺失。

### 15. 离线任务调度用什么？任务依赖、失败重试、SLA 怎么管？

调度系统管任务定时触发、依赖关系、失败重试、SLA 告警。常见有 DolphinScheduler、Airflow、Azkaban。

- 依赖：任务间有上下游关系，上游产出下游才能跑，靠依赖配置或数据就绪检查。
- 失败重试：配置重试次数和间隔，重试失败进告警。
- SLA：关键任务约定产出时间，超时告警升级。

调度要避免：环形依赖、长链路单点、跨层级直接依赖（如 ADS 直接读 ODS）。在元数据加工里，元数据宽表跑完才能同步给向量库和查询引擎，这一层依赖关系要明确。

### 16. AQE（自适应查询执行）了解吗？它解决什么问题？

AQE 是 Spark 3.0 的自适应查询执行，运行时根据统计信息调整执行计划。主要解决三类问题：

- 自动合并小 shuffle 分区，减少 task 数。
- 自动切换 join 策略，sort merge join 运行时发现一边变小可以转 broadcast join。
- 自动处理倾斜，拆分倾斜 partition 单独处理。

适合 shuffle 分区数难预估、数据倾斜的场景。开启 `spark.sql.adaptive.enabled=true`。

### 17. Spark 内存模型大致怎么分？spark.memory.fraction、reserved memory 是什么？

Executor 内存大致分四块：

- reserved memory：预留给 Spark 内部，默认较小。
- user memory：用户数据结构、UDF 中间对象。
- spark memory：执行和存储共用，由 `spark.memory.fraction` 控制占比，其中 storage 和 execution 动态借还。
- 统一内存管理：execution 和 storage 之间可以互相借用，没被借走的才释放。

理解内存模型能调 OOM、shuffle 溢出、cache 占用问题。比如 cache 过多会挤占 execution 内存导致频繁 spill。

### 18. Kryo 序列化相比 Java 默认序列化好在哪里？有什么注意点？

Kryo 比 Java 默认序列化更快、更紧凑。注意点：

- 要注册类才能享受最高性能，未注册时性能下降。
- 配置 `spark.serializer=org.apache.spark.serializer.KryoSerializer`。
- Spark 内部 shuffle 默认就是 Kryo。
- 部分场景如 closure 序列化仍可能用到 Java 序列化，不是全替换。

### 19. 数据倾斜除了加盐、两阶段聚合，还有什么处理方案？

其他方案：

- 增大 shuffle 分区数，让数据分散到更多 partition，但对单 key 极端倾斜无效。
- 自定义 Partitioner，按业务把热点 key 拆开。
- Spark 3 AQE 自动处理倾斜。
- 把热点 key 单独拎出来单独处理，再 union 回去。
- 过滤无效热点 key（比如空值、测试数据）。

加盐的副作用是会改变 key 语义，需要两阶段聚合还原，不适合直接对 key 计数的场景。

### 20. Hive 分区和分桶有什么区别？什么场景下用分桶？

- 分区：按目录拆分，过滤时做分区裁剪，面向时间、业务域等粗粒度过滤。
- 分桶：按 hash 把表拆成固定数量文件，适合采样、bucket map join、解决数据倾斜。

分区面向过滤，分桶面向 join 优化和均匀分布。两者可叠加：先按天分区，再按 user_id 分桶。大表 join 大表时如果两边按 join key 同规格分桶，可以做 bucket map join 避免 shuffle。

### 21. 大表 Join 大表怎么优化？既不能广播又不能倾斜时怎么办？

思路：

- 减少 join 数据量：先过滤、列裁剪、提前聚合。
- 用分桶表做 bucket map join，避免全量 shuffle。
- Sort Merge Bucket Join，两边按 join key 排序分桶。
- 处理倾斜：Skew Join、热点 key 拆分单独处理再 union。
- 维度退化：在 DWD 层提前 join 好存成宽表，下游不再 join。

如果业务允许，把大表 join 转成宽表预计算是最稳的，避免每次查询都重复 join。

### 22. Spark Structured Streaming / 微批流处理了解吗？和离线批处理有什么区别？

Structured Streaming 基于 Spark SQL 引擎，把流当成无界表，用微批（micro-batch）或连续模式处理。和离线批区别：

- 流是持续触发，批是定时触发。
- 流要处理迟到数据，靠 watermark。
- 流要管状态和 exactly-once 语义。

我了解原理但不是主力方向，简历里也是离线数仓为主，不会包装成做过实时流项目。

### 23. Lambda 架构和 Kappa 架构区别？离线数仓场景你倾向哪种？

- Lambda：批 + 流双链路，批层保证准确，流层保证实时，合并对外。问题是两套代码、口径难统一。
- Kappa：只用流一条链路，靠重算历史数据替代批。问题是流处理状态和重算成本高。

离线数仓 + 实时性要求不高的场景，我倾向批为主（Lambda 的批层），实时部分按需加流，不强行上 Kappa。简历场景主要是离线，不硬讲实时架构选型。

### 24. 数据血缘怎么采集？在数据治理里有什么用？

血缘记录字段/表从哪来、到哪去、怎么加工。采集方式：

- 解析 SQL，用 sqlglot、Calcite 等 AST 解析器提取输入输出。
- 调度系统集成，从任务节点提取依赖。
- Hook 机制，在执行时记录。

用途：影响分析（改一个字段影响哪些下游）、根因定位（数据异常往上游追）、合规审计、下线评估。在元数据加工平台里，血缘能帮 NL2DSL 知道一个指标最终来自哪些物理表字段，辅助 Schema 召回和审计。

### 25. 一致性维度、总线矩阵在数仓建设里起什么作用？

- 一致性维度：跨主题域统一的维度，比如全局统一的商品维、时间维，保证不同事实表用同一套维度口径。
- 总线矩阵：业务过程和维度的交叉矩阵，规划哪些事实表用哪些维度，是数仓总线架构的核心。

作用是保证数仓可扩展、口径一致、维度复用。新业务接入时，先看总线矩阵里有没有可复用的业务过程和维度，而不是每次从零建表。

## 八、Vibe Coding / AI辅助开发

### 1. 你怎么用 AI 开发这个项目？

我不是直接让 AI 随机写代码，而是先写清需求和设计，把任务拆成小模块，比如 DSL 校验、权限注入、评测框架、RAG 检索。然后让 AI 生成初稿，我负责 Review、补测试、跑验证和调整架构。

### 2. AI 帮你做了哪些事情？哪些必须自己把关？

AI 适合做代码初稿、测试补齐、文档整理、错误排查思路和样板代码。

必须自己把关的是架构边界、业务口径、安全策略、数据权限、异常处理、性能取舍和最终代码质量。

### 3. 如何避免 AI 生成错误代码？

靠约束和验证：

- 任务拆小。
- 给出清晰接口和上下文。
- 先写测试或验收标准。
- Review 关键逻辑。
- 跑单元、集成、E2E 测试。
- 对安全和权限代码人工重点检查。

### 4. 如何设计 Prompt？

我一般会给 AI：

- 背景和目标。
- 输入输出。
- 文件路径和现有接口。
- 不允许改动的边界。
- 测试要求。
- 失败处理。
- 代码风格。

复杂任务会先让它写方案，再确认方案后写代码。

### 5. AI 生成的代码怎么 Review？

主要看：

- 是否满足接口契约。
- 是否破坏已有逻辑。
- 异常路径是否完整。
- 权限和安全是否绕过。
- 测试是否覆盖正向、反向和边界。
- 是否引入过度抽象。

### 6. 测试怎么补？

根据模块分层补：

- DSL 校验、权限规则、SQLBuilder 写单元测试。
- RAG、Graph、Agent 写集成测试。
- 自然语言到结果写 E2E 测试。
- 评测框架做回归门禁。

### 7. AI 改坏代码怎么办？

我会通过测试和 diff 发现问题。处理方式是缩小任务范围，回滚有问题的改动，重新给 AI 更明确的上下文，或者手写关键逻辑。

### 8. 如何拆分任务让 AI 更容易完成？

每个任务只做一个边界清晰的功能，比如“实现行级权限注入”或“给 DSL Validator 增加未知指标校验”。不要一次让 AI 完成整个系统。

### 9. AI 辅助写文档和写代码哪个更有效？

文档和测试样板更稳定，代码初稿也有价值，但复杂业务和安全逻辑必须人工把关。

### 10. Vibe Coding 和普通 Copilot 补全有什么区别？

Copilot 更偏局部补全；Vibe Coding 更像人机协作开发流程，包括需求澄清、方案设计、任务拆解、代码生成、测试、Review 和迭代。

## 九、Java 后端与线上稳定性

### 1. Java 做了 8 年，最近转 AI 应用，Java 基础还熟吗？

熟。AI 应用最后还是工程系统，Java 后端经验对我处理接口、消息队列、数据库、缓存、并发、部署和线上问题很有帮助。只是最近主项目的 AI Agent 部分更多用 Python 实现。

### 2. RabbitMQ 解决了什么问题？

主要解决高吞吐抓拍数据接入、异步解耦和削峰填谷。相机抓拍数据量大，直接同步处理容易拖垮主链路，通过 MQ 可以让接入、算法解析、告警处理和前端推送解耦。

### 3. 消息积压怎么排查？

看生产速率、消费速率、队列堆积、消费者异常日志、数据库写入耗时、下游接口延迟。处理方式包括扩容消费者、优化批量写入、增加预取控制、排查慢 SQL 和临时限流。

### 4. WebSocket 权限推送怎么设计？

用户连接时绑定 user_id、角色和权限范围。告警生成后根据区域、设备、组织等权限过滤，只推送给有权限的连接。连接信息保存在内存或 Redis，断线要清理。

### 5. 2000万静态底库导入怎么优化？

分批读取、批量写入、多线程处理、控制事务大小、避免一次性加载到内存。图片或大字段单独处理，失败批次可重试，导入过程记录进度。

### 6. 多线程导入如何控制？

用线程池控制并发数，按批次拆分数据。线程数根据 CPU、IO、数据库连接池决定。写库时控制 batch size，避免长事务和连接耗尽。

### 7. Zookeeper 在 SDK 算法服务集群化里做什么？

用于服务注册、发现、健康检查和负载均衡。算法 SDK 服务启动后注册到 Zookeeper，调用方动态发现可用节点，服务扩容或下线时自动感知。

### 8. Docker Compose 负责哪些模块部署？

可以编排业务服务、算法服务、数据库、缓存、MQ、Nginx 等组件，统一网络、端口、环境变量和启动顺序，方便现场部署。

### 9. 现场最常见线上问题是什么？

常见有消息积压、服务宕机、接口超时、算法服务不可用、数据库慢查询、磁盘空间不足、网络异常、机器资源不足、数据延迟。

### 10. Arthas 用过哪些命令？

常用 `dashboard` 看 JVM 状态，`thread` 看线程，`jad` 反编译，`watch` 看方法入参返回值，`trace` 看调用耗时，`stack` 看调用栈，`heapdump` 辅助内存分析。

### 11. RabbitMQ 如何保证消息不丢？

生产端 confirm，队列和消息持久化，消费端手动 ack，失败重试或死信队列，关键业务做好幂等。

### 12. 消费端幂等怎么做？

用业务唯一键、消息 ID、数据库唯一索引或状态机控制。重复消息到达时先检查是否已处理。

### 13. Redis 用在哪里？

可用于热点数据缓存、会话或连接信息、权限缓存、分布式锁、限流计数、临时任务状态等。

### 14. MySQL 大表查询如何优化？

建合适索引、避免全表扫描、控制返回字段、分页优化、按时间分区、冷热数据拆分、慢 SQL 分析、EXPLAIN 看执行计划。

### 15. JVM 问题怎么排查？

先看 CPU、内存、GC、线程。用 Arthas、jstack、jmap、GC 日志定位。CPU 高看热点线程，内存高看对象分布，接口慢看 trace，死锁看 thread。

### 16. 算法 SDK 服务不可用如何降级？

可以做超时控制、重试、熔断、切换备用节点、消息暂存、告警延迟处理。不能让 SDK 不可用拖垮整个接入链路。

不是完全同一个。公司项目是实际业务实践，开源项目是我基于同类问题做的个人抽象和沉淀，用于展示架构和工程能力。公司内部数据、配置和业务细节没有放到开源项目。

### 3. 数据资产与语义层元数据加工平台真实吗？

建议按真实情况说。如果这是你基于公司数据平台/NL2DSL 上游链路总结出来的项目，就说它是围绕智能问数所需的元数据和语义层治理加工能力，不要夸大成独立大型平台。

### 4. 性能指标有没有实验数据？

回答要谨慎：这些数据来自评测集或局部链路压测，对比的是相同问题集、相同候选规模下的耗时。生产数据要看部署环境和业务规模。

开源项目使用 Milvus Lite；Qdrant 是我在其他向量检索实践或公司项目中接触的组件。简历技能清单里列的是技术覆盖，项目技术栈以项目段落为准。

准备回答：元数据宽表加工、字段质量统计、枚举值抽取、指标数据聚合、分区增量处理、数据质量报告。最好能准备一个 SQL 示例。

## 十二、高压追问详细回答模板

> 这一章的目标不是把项目说大，而是把边界、链路、取舍和验证讲清楚。面试时越是被追问，越要先界定口径：哪些是公司项目里的业务实践，哪些是个人开源项目里的抽象复现，哪些是评测或本地验证结果。

## 1. 项目真实性与边界

### 总回答口径

我一般会先主动把公司项目和个人开源项目区分清楚。公司项目是实际业务场景里的智能问数和数据治理实践，重点是解决业务人员自然语言查数、指标口径统一、权限和审计这些问题；个人开源项目是我基于同类问题做的技术抽象和复现，目的是把 NL2DSL、RAG、DSL 校验、权限注入、SQL 构建、评测这些核心链路用可展示的方式沉淀出来。两者不是代码一比一搬运，也不会包含公司内部数据、配置和业务细节。

### 详细回答模板

**问题：公司项目和开源项目到底是什么关系？**

可以这样答：

公司项目和开源项目不是同一个仓库，也不是简单复制关系。公司项目更偏业务落地，会受到内部数据源、权限体系、指标口径、部署环境和保密要求限制；开源项目是我把其中可公开、可抽象的技术思路重新组织出来，做成一个可以讲架构、讲代码、讲工程取舍的版本。

我在面试里会用开源项目解释技术链路，比如自然语言输入后如何进入 Agent/Graph，RAG 如何召回 Schema、指标和术语，LLM 如何生成结构化 DSL，DSL 如何做字段、指标、权限校验，再由 SQLBuilder 生成 SQL。公司项目里的真实数据、表结构、业务配置不会放到开源项目里，所以我不会把开源项目直接说成公司生产代码。

**问题：你到底亲自负责了哪些模块？**

可以这样答：

我会把“亲自负责”和“参与了解”分开说。亲自负责的部分主要集中在查询主链路和工程化闭环：包括 NL2DSL 的整体链路设计、RAG 召回上下文组织、DSL Schema 和校验逻辑、权限注入思路、SQL 构建前后的安全约束、评测集和回归验证这些模块。  

一些更贴近公司内部平台的内容，比如完整权限组织架构、内部元数据来源、具体业务域配置，我可以讲设计思路和接口边界，但不会展开公司内部细节。面试官如果要验证我是否真做过，我更愿意从一个问题例子讲完整链路：输入是什么、状态里传什么、哪个环节可能失败、失败后怎么修正、最后怎么审计。

**问题：如果不能讲公司细节，怎么证明你做过？**

可以这样答：

我会用三类东西证明：第一是讲清楚抽象后的模块边界，比如 DSL 里 metrics、dimensions、filters、order_by、limit 分别由谁产生、谁校验、谁消费；第二是讲清楚异常路径，比如指标不存在、字段越权、RAG 召回不足、SQL 执行失败时系统怎么处理；第三是打开开源项目讲对应实现，虽然开源项目不包含公司数据，但能展示我对这类系统的架构理解和代码掌握。

真正做过的人通常不只是讲“用了 LangGraph、用了 RAG”，而是能说出为什么要拆成这些节点、State 里放哪些信息、哪个环节适合重试、哪个环节必须终止。

### 不要这么说

- 不要说公司项目和开源项目“基本一样”。
- 不要把个人开源项目里的完整能力说成公司生产系统已经全部上线。
- 不要用“这个不能讲”结束回答；可以不讲内部数据，但要讲抽象后的架构、边界和取舍。

## 2. Vibe Coding 掌握度

### 总回答口径

我会把 Vibe Coding 讲成一种 AI 辅助工程实践，而不是“AI 替我做项目”。我的角色是定义问题、拆任务、确定接口、Review 关键逻辑、补测试和做回归验证。AI 更像提升效率的编码助手，适合生成初稿、补样例、整理文档、辅助排查，但架构边界、安全策略、业务口径和最终代码质量必须由我负责。

### 详细回答模板

**问题：这个项目大量用了 AI，你本人到底贡献了什么？**

可以这样答：

AI 参与比较多的是代码初稿、测试样例、文档整理和一些重复性实现，但项目的关键判断不是 AI 做的。比如为什么选择 NL2DSL 而不是直接 NL2SQL，DSL 应该有哪些字段，权限为什么要在 DSL 层注入，RAG 召回结果如何进入 Prompt，DSL 校验失败后能不能自动修正，这些是架构和业务边界问题，需要我自己判断。

我通常会先把任务拆成很小的模块，比如“给 DSL Validator 增加未知指标校验”“给权限模块增加行级过滤条件注入”“给 Rerank 链路补一个耗时统计”。然后给 AI 明确输入输出、已有文件路径、不能改的边界和验收标准。AI 生成后，我会看它有没有破坏原有接口、异常路径是否完整、权限和安全有没有绕过，再通过测试或样例跑一遍。

**问题：举一个 AI 写错、你发现并修正的例子。**

可以这样答：

可以举 DSL 校验或权限注入这类例子。比如 AI 初稿容易只校验 DSL 的 JSON 结构是否符合 Pydantic Schema，但忽略业务语义校验：metric 是否注册、dimension 是否属于当前 data_source、filter 操作符和字段类型是否匹配。这个时候如果只看结构，DSL 是合法的，但后面生成 SQL 时会出错，甚至可能引用不存在的字段。

我的处理方式是把校验拆成两层：第一层是结构校验，保证 DSL 格式正确；第二层是语义校验，基于注册表检查指标、字段、权限和 limit 上限。这样 AI 可以帮我写部分样板代码，但校验边界和失败策略必须由我确定。失败后也不是简单让模型再试一次，而是把错误原因带回 correct_dsl，让它带着补充召回上下文修正。

**问题：没有 AI，你能不能维护这个项目？**

可以这样答：

可以。AI 帮我提高开发效率，但项目的核心链路我能按模块讲清楚：API 入口、Agent/Graph 编排、RAG 召回、DSL 生成、DSL 校验、权限注入、语义解析、SQL 构建、安全扫描、执行和审计。  

如果现场要改一个小需求，比如给 DSL 增加一个 `time_range` 字段，我会先改 DSL Schema，再改生成 Prompt 的约束和样例，再补校验规则，最后看 SQLBuilder 是否需要把它展开成时间过滤条件。这个过程不是靠 AI 记忆，而是靠对链路的理解。

### 不要这么说

- 不要说“基本都是 AI 写的，我负责调 Prompt”。
- 不要只强调效率，要讲 Review、测试、边界和失败处理。
- 不要把 AI 生成的代码天然当成正确代码，尤其是权限、安全、SQL 构建这类模块。

## 3. 性能指标可信度

### 总回答口径

性能指标一定要讲口径。我不会把局部评测说成全量生产指标。比如 800ms 到 80ms，更准确的说法是：在相同候选规模、相同问题集或局部链路下，用 BGE-Reranker 替代 LLM 粗排后，重排序环节耗时明显下降，模型调用成本也下降。生产环境的整体耗时还会受向量库、数据库、网络、缓存、并发和数据规模影响。

### 详细回答模板

**问题：800ms 到 80ms 是怎么测出来的？**

可以这样答：

我会先说明这个数据的起止范围。这里比较的是重排序环节，不是整个自然语言查数请求的端到端耗时。原来如果用 LLM 对候选 Schema、指标、术语做粗排，需要把候选内容拼到 Prompt 里，让模型判断相关性，延迟和 token 成本都比较高。后来改成 BGE-Reranker 后，同样是对 TopN 候选做相关性排序，推理更轻量，耗时会明显下降。

这个数据适合说成“评测集或局部链路压测结果”。如果面试官继续追问，我会补充口径：候选集大小、是否缓存 embedding、是否包含模型冷启动、机器环境、统计的是平均值还是 P95。没有完整生产压测记录时，我不会说这是生产全链路稳定 P95。

**问题：准确率 90% 怎么定义？**

可以这样答：

准确率不能笼统说，要看评测维度。NL2DSL 里我更倾向拆成几类指标：Semantic 看指标、维度、过滤条件是否理解正确；Planning 看复杂问题是否拆解合理；Execution 看 SQL 能否执行成功、结果是否符合预期；Governance 看权限、脱敏、审计是否覆盖。  

如果说“整体准确率约 90%”，我会说明这是在某个评测集或开源样例集上的综合结果，不代表所有业务域。真实落地里更重要的是建立评测集和回归门禁：新增规则或 Prompt 改动后，不能只看几个 demo 问题，要跑固定问题集，看哪些类型提升、哪些类型退化。

**问题：成本下降 90% 是不是夸大？**

可以这样答：

这个要限定在模型调用成本或重排序环节成本上。用 LLM 做 rerank 时，每次都要把候选文本和排序指令发给大模型，token 成本和延迟都高；换成专门的 reranker 后，重排序不再依赖通用大模型调用，所以这个环节的调用成本会明显下降。  

但我不会说整个系统成本下降 90%。完整系统还有 embedding、向量检索、数据库执行、服务部署和运维成本。更严谨的说法是：在重排序环节，用 BGE-Reranker 替代 LLM 粗排后，模型调用成本和延迟显著下降。

### 不要这么说

- 不要说“生产环境稳定 80ms”，除非你有完整压测数据。
- 不要把局部 rerank 成本下降说成整套系统成本下降。
- 不要只报准确率数字，要能解释评测集、评分维度和失败样本处理。

## 4. RAG 与向量库选型

### 总回答口径

我会把检索链路拆成三层讲：向量检索解决语义相似问题，关键字检索解决短词、字段名、枚举值这类精确匹配问题，Rerank 负责把召回候选重新排序。Milvus Lite 是开源项目里为了轻量演示和本地部署使用的向量库；Qdrant 或 Elasticsearch 如果出现在技能清单里，要说明它们来自其他实践或技术覆盖，不和当前项目技术栈混在一起。

### 详细回答模板

**问题：为什么用 Milvus Lite，不用 Elasticsearch？**

可以这样答：

开源项目的重点是展示 NL2DSL 查询链路，所以我选择 Milvus Lite 是因为它轻量、部署简单，适合本地演示向量语义召回。它主要负责召回 Schema、指标、术语和历史样例这类语义上下文。  

Elasticsearch 更适合倒排索引、日志检索、复杂关键字检索和过滤聚合。如果是在生产系统里，完全可以是混合检索：ES 做字段名、表名、枚举值、日志类精确检索，向量库做语义召回，最后用 reranker 统一排序。开源项目没有把所有生产组件都堆进去，是为了保持可运行和可讲清楚。

**问题：RAG 召回错了，后面怎么发现？**

可以这样答：

RAG 召回不是唯一防线。比如用户问“华东近7天销售额最高的5个商品”，RAG 会召回销售额指标定义、华东地区值、商品维度、时间字段和类似历史样例。LLM 生成 DSL 后，系统还会做 DSL 校验：metric 是否注册、dimension 是否属于当前数据源、filter 字段和值是否合法、order_by 是否在输出字段里。  

如果召回到了不存在的字段或指标，DSL 校验能直接拦截。如果召回到的是合法但业务口径不合适的指标，这更难，需要靠语义层配置、历史样例、评测集和人工维护来发现。我的理解是，RAG 召回质量最终要通过评测集和线上反馈闭环改进，不能只靠 Prompt。

**问题：向量库里每条记录存什么？**

可以这样答：

我会把记录分类型存。比如 schema 类型记录表名、字段名、字段描述、所属业务域；metric 类型记录指标名称、别名、业务解释、计算口径和适用数据源；term 类型记录业务术语、同义词、映射对象；history 类型记录历史问题和标准 DSL。  

metadata 里至少要有 domain、type、name、data_source、version 或 enabled 这类字段，方便召回后过滤和解释。不能只存一段自然语言文本，否则后面 DSL 校验和语义解析很难知道这个候选到底是什么对象。

### 不要这么说

- 不要把 Milvus Lite、Qdrant、Elasticsearch 说成同一个项目里都用了。
- 不要说“RAG 能解决幻觉”，更准确是 RAG 降低幻觉，后面还要有校验和评测。
- 不要只讲向量相似度，要讲 metadata、过滤、rerank 和失败处理。

## 5. 大数据与 Spark 真实性

### 总回答口径

大数据这块要讲成 NL2DSL 的上游治理底座，而不是孤立吹一个大平台。自然语言查数要可靠，必须知道有哪些表、字段、指标、维度、枚举值、术语和权限，这些都需要元数据加工链路提前沉淀。Spark SQL 主要用于离线抽取、清洗、聚合和质量统计，把底层数据资产加工成语义层和检索层可消费的结构。

### 详细回答模板

**问题：元数据加工平台具体加工什么？**

可以这样答：

我会把它拆成输入、加工、输出三层。输入包括数据库元数据、表字段 comment、指标配置、维表或字典表、业务术语、权限策略以及部分历史查询样例。加工过程包括字段标准化、字段质量统计、枚举值抽取、指标口径聚合、业务域归属、敏感字段标记和质量评分。输出可以是元数据宽表、指标元数据表、术语表、字段值样例表、权限配置表，以及同步到向量库的可检索文本。

它和 NL2DSL 的关系是上游支撑：RAG 召回要用这些内容，DSL 校验要用注册表，权限注入要用权限策略，评测集也可以从历史问题和标准 DSL 中沉淀。

**问题：Spark SQL 任务你具体写过什么？**

可以这样答：

可以举元数据宽表加工这个例子。任务会按业务域和数据源抽取表、字段、类型、comment、分区信息，再关联指标配置、术语别名、敏感字段规则和质量统计结果，最后生成一张面向查询引擎使用的宽表。  

质量统计可以包括空值率、重复率、枚举值 TopN、字段覆盖率、分区完整性、数据量波动。维度枚举值优先来自字典表或维表，同步不到时再考虑离线 DISTINCT 或 TopN 采样；高基数字段和敏感字段不能盲目全量抽枚举。

**问题：你优化过什么 Spark 问题？**

可以这样答：

可以按真实经历选一个例子讲。如果没有特别夸张的数据，就不要硬报数字。回答结构可以是：某个元数据加工任务一开始会扫描过多历史分区，或者大表 join 时 shuffle 较大，导致任务耗时不稳定。我会先看 Spark UI 的 stage 耗时、shuffle read/write、task 倾斜和输入分区数，判断是分区过滤没下推、join key 倾斜，还是中间结果重复计算。

优化方式可以包括：增加业务日期分区过滤、只处理增量分区、复用中间宽表、把小维表广播、把高频字段枚举抽取拆成独立任务。最后用任务耗时、shuffle 数据量和失败重跑次数来验证是否改善。

### 不要这么说

- 不要只说“写 Spark SQL 清洗数据”，要讲清输入表、输出表、字段和下游用途。
- 不要硬编数据量和优化百分比。
- 不要把“元数据加工”讲成和 NL2DSL 无关的大而泛平台，要讲它如何支撑 Schema 召回、指标召回、DSL 校验和权限注入。

## 6. 代码现场讲解

### 总回答口径

现场讲代码时，我会按三条路线准备：API 到 Graph、DSL 到 SQL、RAG 到 Rerank。这样面试官无论从入口、核心模型还是检索链路切入，我都能讲清楚模块职责、数据流和失败处理。讲代码时不要只说目录名，要能说出请求进来后哪些对象被创建、State 里传什么、每个节点读写什么字段。

### 详细回答模板

**问题：你怎么从入口讲完整链路？**

可以这样答：

我会从 FastAPI 的查询接口开始讲：接口接收用户问题、用户身份、业务域等参数，组装成查询请求后进入 Agent 或 Graph。Agent 层负责意图识别、复杂问题拆解、子查询调度和结果解释；Graph 层负责单个查询从 DSL 到 SQL 执行的稳定链路。

Graph 的典型节点可以按顺序讲：clarification、decompose、rag_retrieve、generate_dsl、validate_dsl、correct_dsl、permission_check、resolve_semantic、build_sql、scan_sql、sandbox_check、execute_sql、audit_log。每个节点都围绕同一个 State 读写，比如 question、retrieved_context、dsl、sql、permission、result、error、trace。

**问题：如果让你现场加一个 DSL 字段，你怎么改？**

可以这样答：

我会先判断这个字段属于语义层、执行层还是展示层。比如加 `time_range`，首先要改 DSL Schema，让结构层能表达；然后改 Prompt 约束和 few-shot，让 LLM 知道什么时候生成它；再改 DSL Validator，检查时间格式和字段归属；最后看 SemanticResolver 或 SQLBuilder 是否要把它展开成具体时间字段过滤条件。  

如果这个字段还影响评测，就要补标准 DSL 样例和回归用例。不能只在模型输出里加一个字段，否则后面校验、权限、SQL 构建都可能断掉。

**问题：项目里最能体现你能力的代码怎么讲？**

可以这样答：

我会优先讲 DSL 校验和修正闭环，或者权限注入加 SQL 安全扫描。因为这类代码体现的不是简单调用模型，而是把模型输出限制在可治理范围里。  

比如 DSL 校验不是只校验 JSON 格式，还要校验 data_source 是否存在、metric 和 dimension 是否注册、filter 操作符和字段类型是否匹配、limit 是否超过上限、order_by 是否合法。校验失败后，如果是语义不清或召回不足，可以进入 correct_dsl，带着错误原因重新召回上下文并修正；如果是权限拒绝或危险 SQL，就必须终止，不能靠重试绕过去。

### 不要这么说

- 不要只背目录结构，要能讲请求流和数据流。
- 不要说“这个 AI 生成的我没细看”。
- 不要把所有失败都说成“重试一下”，权限和安全类失败必须终止。

## 7. 生产落地边界

### 总回答口径

生产落地边界要谨慎讲。我会先说明公司侧和开源侧不同：公司侧是围绕真实数据治理和智能问数场景做业务实践，具体上线范围和内部数据不方便展开；开源侧是个人抽象实现，重点展示核心架构和工程能力。对于上线规模、准确率、成本、用户量这些指标，如果没有可公开证据，就不硬说。

### 详细回答模板

**问题：这个项目到底有没有上生产？**

可以这样答：

我会分两层说。公司侧是面向真实业务问题做的智能问数和数据治理能力建设，涉及自然语言查数、指标口径、权限控制、审计追踪等环节；但具体上线范围、接入业务域、数据规模和内部指标，不适合在面试里展开。  

开源侧是我为了展示技术方案做的抽象实现，能够跑通 API、Agent/Graph、RAG、DSL 校验、权限、安全、评测等核心链路，但它不等同于公司生产系统。它的价值是让我可以公开讲代码结构和架构取舍，同时不泄露公司内容。

**问题：如果面试官说这只是 Demo，你怎么回应？**

可以这样答：

我会承认开源项目确实不是生产系统一比一复刻，但它不是只做一个页面 demo。它重点复现的是企业级智能问数里最关键的工程问题：LLM 不直接生成 SQL，而是生成 DSL；DSL 要经过结构和语义校验；权限要在查询语义层注入；SQL 执行前要做安全扫描和沙箱预检；链路要有审计和评测。

生产系统会有更多组织权限、数据源适配、灰度发布、监控告警和运维能力，这些开源项目可以简化。但核心思想和模块边界是可验证的，面试时我也可以打开代码讲。

**问题：系统失败时怎么处理？**

可以这样答：

失败要分类处理。语义不清，比如用户问“最近销售怎么样”，缺少指标或时间范围，可以追问澄清；RAG 召回不足或 DSL 校验失败，可以进入修正链路，带着错误原因重新召回和生成；SQL 执行失败可以根据错误类型判断是否调整 DSL 或返回可解释错误。  

但权限拒绝、敏感字段越权、危险 SQL、沙箱预检风险高，这些不能重试绕过，必须终止并记录审计。这个边界很重要，因为企业场景里安全和治理比“尽量回答出来”更重要。

### 不要这么说

- 不要把开源项目说成完整生产系统。
- 不要硬编接入多少业务域、多少用户、多少 QPS。
- 不要为了显得智能，说系统所有失败都能自动修好。

## 8. Java 后端基本盘

### 总回答口径

我会把 Java 后端经验讲成 AI 项目落地的工程基础。AI Agent 或 NL2DSL 最后还是一个线上系统，要处理接口、权限、数据库、缓存、消息、日志、监控、部署、降级和问题排查。Java 经验帮助我在做 AI 应用时，不只关注模型效果，也关注稳定性、可观测性和异常闭环。

### 详细回答模板

**问题：你最近讲 AI，Java 基础还熟吗？**

可以这样答：

熟。只是最近项目的 AI Agent 链路更多用 Python 实现，但我之前的 Java 后端经验仍然是基本盘。我做过消息队列、WebSocket 推送、多线程导入、MySQL/Redis、Zookeeper 服务发现、Docker Compose 部署和线上问题排查。  

这些经验迁移到 AI 项目里也很直接，比如查询链路要有超时控制、审计日志、异常分类、权限校验、缓存策略和降级方案。LLM 能力只是系统的一部分，真正上线还要靠后端工程把它托住。

**问题：RabbitMQ 消息不丢和幂等怎么讲？**

可以这样答：

我会从生产端、Broker、消费端和业务幂等四层讲。生产端用 confirm 确认消息发送成功；队列和消息做持久化；消费端使用手动 ack，处理成功后再确认；失败消息进入重试或死信队列。  

幂等要靠业务唯一键，比如抓拍记录 ID、告警 ID 或消息 ID，数据库层可以用唯一索引或状态机防止重复处理。消息队列只能提高可靠性，不能替代业务幂等。线上如果出现积压，我会看生产速度、消费速度、队列堆积、消费者异常、数据库写入耗时和下游接口延迟，再决定扩容消费者、优化批量写入、限流或临时降级。

**问题：线上 CPU 飙高怎么排查？**

可以这样答：

我会先确认是单机问题还是集群普遍问题，再看进程 CPU、线程状态和最近发布变更。Java 服务里可以用 top 找到高 CPU 进程，再用 `top -H` 或 Arthas `thread` 找热点线程，看线程栈是在业务循环、序列化、正则、数据库轮询，还是 GC。  

如果是接口慢或某个方法耗时高，可以用 Arthas `trace` 看调用耗时，用 `watch` 看关键入参和返回，用日志和监控确认是否和某类请求相关。临时止血可能是限流、重启、关闭开关或扩容；长期修复要回到代码、SQL、缓存或线程池配置上。

### 不要这么说

- 不要给人感觉 Java 经验只是简历凑数。
- 不要只背八股，要结合消息积压、底库导入、WebSocket 权限推送、现场部署这些经历讲。
- 不要把 AI 项目和后端工程割裂开，应该强调 AI 应用最终也要靠稳定系统落地。
