# 高宇 NL2DSL 简历面试参考答案

> 用法建议：这份文档不是逐字背诵稿，而是面试回答框架。涉及公司真实数据、上线规模、性能指标、准确率等内容时，建议按你能证明、能讲清的口径表达。

## 一、开场与项目总览

### 1. 你先用 3 分钟介绍一下自己，重点讲讲最近这个 NL2DSL 项目。

我有 8 年后端和数据工程经验，早期主要做 Java 后端、高并发数据接入、消息队列、算法服务集群和现场稳定性保障；最近几年更多转向企业级数据智能和大模型应用方向。

最近重点做的是一个面向数据治理平台的智能问数项目，我把它抽象成 NL2DSL：用户用自然语言提问，系统不是让大模型直接生成 SQL，而是先生成结构化 DSL。DSL 经过字段、指标、权限、安全、语义层校验后，再由系统构建 SQL 执行。

这个项目的核心价值是把大模型能力和企业数据治理结合起来。传统 NL2SQL 容易出现 SQL 幻觉、权限绕过、指标口径不一致和审计困难的问题，而 NL2DSL 通过语义层、权限注入、DSL 校验、SQL 安全扫描和链路审计，把查询过程变得可控、可解释、可追踪。

我在里面主要负责 Agent 查询链路、LangGraph 状态编排、RAG 召回、DSL 校验、权限注入、SQL 构建、自动化评测和开源项目沉淀。

### 2. 你这份简历定位是 AI Agent / NL2DSL / 大数据工程师，你自己觉得最核心的竞争力是什么？

我的核心竞争力是工程落地能力比较完整：既懂 Java 后端和线上稳定性，也做过 Spark SQL、元数据加工和数据质量；最近又把这些经验迁移到大模型应用里，做了 NL2DSL、RAG、Agent 编排和评测体系。

所以我不是只会调 LLM API，也不是纯算法方向，而是能把企业数据治理、后端工程、大数据加工和 AI Agent 串成一条可落地的链路。

### 3. 智能数据查询平台是公司项目还是个人开源项目？两者之间是什么关系？

建议回答时主动区分：

公司项目是实际业务场景中的智能数据查询平台，主要面向业务人员自然语言查数。个人开源项目 `nl2dsl-engine` 是我基于工作中的问题意识和个人理解做的抽象与复现，重点沉淀了 NL2DSL 架构、DSL 校验、RAG、权限治理、审计和评测框架。

公司项目和开源项目不是简单等同关系。公司项目偏业务落地，开源项目偏技术抽象和可展示实现。面试时我可以通过开源项目讲清架构思想和代码实现，但不会把公司内部细节、数据和业务配置放出来。

### 4. 你在公司项目里负责哪些模块？开源项目里又是怎么复现或沉淀的？

公司项目里我主要参与智能问数核心链路，包括关键词提取、Schema/字段/指标召回、Rerank、SQL/DSL 生成、链路日志、评测和性能优化。

开源项目里我把这些能力抽象成更清晰的 NL2DSL 架构：FastAPI 提供接口，LangGraph 组织查询管道，RAG 召回语义层上下文，Pydantic 做 DSL 校验，SQLAlchemy 构建 SQL，sqlglot 做方言处理，并补了权限、审计、评测和多领域配置。

### 5. 这个项目解决的真实业务问题是什么？用户是谁？使用场景是什么？

解决的是业务人员查数门槛高的问题。传统上业务要查一个数，需要知道表名、字段名、指标口径，或者找数据开发帮忙写 SQL。智能问数希望让业务直接问“华东近7天销售额最高的商品”，系统自动理解指标、维度、过滤条件和权限，返回结果。

用户主要是业务运营、数据分析、管理人员，也包括数据治理平台中的数据消费方。典型场景是经营分析、指标查询、报表探索、异常排查和临时取数。

### 6. 你说“面向数据治理平台”，具体接入的是哪些治理资产？

主要接入这些治理资产：

- 指标口径：比如销售额、GMV、订单数的标准计算方式。
- 维度定义：地区、商品、用户类型、时间等维度及其物理字段映射。
- 数据源定义：主表、关联表、Join 关系、可用指标和维度。
- 术语词典：业务别名，比如“流水”映射到 GMV。
- 权限策略：行级权限、列级权限、敏感字段和脱敏规则。
- 历史样例：历史问题和标准 DSL，用于 RAG few-shot。

### 7. 你做的是 NL2SQL 还是 NL2DSL？为什么简历里强调 DSL？

从用户视角看，它是自然语言查数，最终确实会执行 SQL；但从系统架构看，我更强调 NL2DSL，因为中间多了一层结构化 DSL。

传统 NL2SQL 是自然语言直接生成 SQL，SQL 是自由文本，不好校验、权限不好注入、审计也不清晰。NL2DSL 是先生成结构化 DSL，DSL 里表达指标、维度、过滤、排序、分页等语义，再由系统负责生成 SQL。这样安全性、可控性和可治理性更好。

### 8. 这个项目目前做到什么程度？是 Demo、内部工具、生产系统，还是开源验证项目？

建议按真实情况回答：

公司侧是业务场景下的智能查询平台，承担真实业务查询链路。个人开源项目是我对该类系统的技术抽象和验证实现，已经包含 API、Agent/Graph 查询管道、DSL 校验、权限、安全扫描、RAG、审计、评测和前端展示等模块。

如果被追问生产规模，不要硬编。可以说：开源项目主要用于架构展示和面试讲解；公司项目的上线范围和指标以内部实际为准，不方便展开内部数据。

## 二、NL2DSL 架构设计

### 1. 为什么不直接让 LLM 生成 SQL，而要先生成 DSL？

因为 SQL 是自由文本，直接生成 SQL 有几个问题：

- 不好校验：字段、指标、函数、Join 是否合法，需要解析 SQL 才知道。
- 权限不可控：SQL 生成后再改字符串注入权限，容易漏掉子查询、UNION 等场景。
- 方言复杂：MySQL、PostgreSQL、ClickHouse 等语法差异大。
- 审计困难：很难从 SQL 里还原用户到底想查什么业务指标。

DSL 是结构化语义契约。LLM 只负责生成受约束的结构，系统负责校验、权限、优化和 SQL 构建。这样可以把大模型的不确定性限制在可控范围里。

### 2. DSL 里包含哪些核心字段？metrics、dimensions、filters 分别代表什么？

核心字段一般包括：

- `data_source`：使用哪个业务数据源。
- `metrics`：要计算什么指标，比如销售额、订单数。
- `dimensions`：按什么维度分组或展示，比如地区、商品。
- `filters`：过滤条件，比如地区=华东、时间=近7天。
- `order_by`：排序规则。
- `limit`：返回条数。
- `post_process`：TopN、占比、趋势、同比环比等后处理。

metrics 是被聚合的值，dimensions 是切分和筛选数据的维度，filters 是查询条件。

### 3. DSL 到 SQL 的转换链路是怎样的？

大致流程是：

自然语言输入 -> RAG 召回语义上下文 -> LLM 生成 DSL -> DSL 结构校验 -> 指标/字段语义校验 -> 权限注入 -> 语义解析 -> SQLAlchemy 构建标准 SQL -> sqlglot 做方言处理 -> SQL 安全扫描 -> 沙箱预检 -> 执行 SQL -> 返回结果和审计日志。

### 4. DSL 校验具体校验哪些内容？

主要校验：

- data_source 是否存在。
- metric 是否注册。
- dimension 是否注册。
- filter 字段是否是合法维度。
- 操作符和字段类型是否匹配。
- limit 是否超过上限。
- order_by 字段是否在输出字段中。
- 是否访问敏感列或未授权指标。
- DSL 结构是否符合 Pydantic Schema。

### 5. LLM 生成了不存在的字段或指标怎么办？

第一步在 DSL 校验阶段拦截。比如指标未注册、字段不存在，会产生明确错误。

第二步进入修正链路：根据错误信息提取关键词，做定向 RAG 召回，把更准确的指标、维度、术语上下文补给 LLM，让它重新生成 DSL。

如果重试后仍不通过，就返回可解释错误或触发澄清，不会继续构建 SQL。

### 6. 指标口径是由 LLM 决定，还是由系统注册表决定？

由系统注册表决定。LLM 只能选择指标 alias，比如 `sales_amount`，不能自己发明 `SUM(pay_amount)` 的口径。

真正的指标表达式来自语义层配置，例如 `sales_amount = SUM(pay_amount)`。这样可以保证所有查询使用统一口径。

### 7. “销售额”这种业务指标如何映射到底层 SQL 表达式？

流程是：

用户说“销售额” -> 术语和指标召回找到 `sales_amount` -> LLM 在 DSL 里生成 metric alias -> SemanticResolver 根据注册表把 alias 展开成 `SUM(pay_amount)` -> SQLBuilder 生成 SQL。

关键点是：LLM 负责识别意图，系统负责口径展开。

### 8. 如果用户问“华东近7天销售额最高的5个商品”，系统完整执行流程是什么？

系统会先判断这个问题没有歧义，然后 RAG 召回：

- 销售额指标定义。
- 华东对应的地区编码或枚举值。
- 近7天的时间解析规则。
- 商品维度字段。

LLM 生成 DSL：metric 是销售额，dimension 是商品，filters 包含地区=华东和日期>=近7天，order_by 是销售额倒序，limit 是 5。

然后系统校验 DSL，注入用户权限，解析指标为 SQL 表达式，构建 SQL，做安全扫描和沙箱预检，执行后返回 Top5 商品和销售额，同时记录 trace 和审计日志。

### 9. 你提到 10+ 个 LangGraph 节点，能按顺序画一下流程吗？

可以按这个顺序讲：

`clarification -> decompose -> rag_retrieve -> generate_dsl -> validate_dsl -> correct_dsl -> permission_check -> resolve_semantic -> build_sql -> scan_sql -> sandbox_check -> execute_sql -> verify_dsl -> audit_log`

其中 `correct_dsl`、`sandbox_check`、`execute_sql` 都有条件分支。比如 DSL 校验失败会进修正，沙箱风险高会走人工审核，SQL 执行失败可以走简化 DSL 重试。

### 10. LangGraph 在这里解决了什么问题？不用 LangGraph 可以吗？

不用 LangGraph 也可以用普通 pipeline 写，但 LangGraph 的优势是状态流转、条件分支、失败重试和链路可观测更清晰。

这个项目不是简单一次请求调用 LLM，而是有歧义检测、RAG、DSL 校验、修正、权限、安全、执行、审计等多个状态。LangGraph 适合把这些节点编排成可维护的状态机。

### 11. Agent 层和 Graph 层为什么要分开？

Agent 层处理“查什么”，比如意图识别、复杂查询拆解、子查询调度、结果聚合和解释。

Graph 层处理“怎么查”，也就是单个查询从 DSL 到 SQL 执行的稳定链路。

分开后，复杂查询编排和底层执行可以独立演进。Agent 改意图识别，不影响 DSL 校验和 SQL 构建；Graph 做安全治理，也不关心上层是单查询还是多查询。

### 12. 复杂查询拆解后，多个子查询之间如何并行、串行或聚合？

Agent Planner 先识别意图，比如 compare、trend、ranking、proportion。Dispatcher 根据意图拆成子查询。

没有依赖的子查询可以并行执行，有依赖的顺序执行。每个子查询都走 Graph 管道，最后 Aggregator 根据意图做 diff、growth_rate、trend_direction、ranking 等聚合。

### 13. Graph 节点之间传递的 State 结构大概长什么样？

State 一般包含：

- 原始 question。
- domain / user_id / tenant_id。
- 检索上下文。
- 当前 DSL。
- SQL。
- 执行结果。
- 权限信息。
- trace。
- 错误信息。
- 重试次数。

核心是所有节点只读写自己负责的字段，避免节点之间强耦合。

### 14. 节点失败后怎么处理？哪些失败可以重试，哪些必须终止？

DSL 生成失败、校验失败、RAG 召回不足、SQL 执行失败属于可重试或可修正问题。

权限拒绝、危险 SQL、安全扫描失败、敏感字段越权、达到最大重试次数属于必须终止。

原则是：语义不确定可以澄清或修正，安全和权限问题不能靠重试绕过。

### 15. correct_dsl 是怎么工作的？

correct_dsl 会读取 DSL 校验错误，比如“指标不存在”或“字段不存在”，然后从错误里提取关键词，做定向 RAG 召回，把可能正确的指标、维度或术语补充给 LLM，让它重新生成 DSL。

它不是盲目让 LLM 再试一次，而是带着错误原因和补充上下文修正。

### 16. 如何避免 DSL 修正陷入死循环？

通过最大重试次数和进展检测控制。

比如 `dsl_attempts` 每次重试递增，超过上限直接返回错误。如果新 DSL 和旧 DSL 没有变化，也认为没有进展，提前终止。

### 17. SQLAlchemy 和 sqlglot 分别解决什么问题？

SQLAlchemy 负责用结构化方式构建 SQL，避免字符串拼接，提高安全性和可维护性。

sqlglot 负责 SQL 方言解析和转换，比如将标准 SQL 转成不同数据库可执行的语法，也可辅助 SQL 检查。

### 18. sqlglot 方言转换在什么场景下有价值？

当同一套 DSL 查询引擎要支持 MySQL、PostgreSQL、ClickHouse、SQLite 等不同数据库时，日期函数、分页、字符串函数、引号规则可能不同。sqlglot 可以降低多方言适配成本。

## 三、RAG、向量检索与 Rerank

### 1. 你的 RAG 检索召回哪些内容？

主要召回：

- Schema：表、字段、字段描述、主键和 Join 关系。
- Metrics：指标名、业务口径、计算表达式。
- Terms：业务术语和别名，比如流水、GMV。
- History：历史问题和标准 DSL 样例。
- Permissions：必要时给权限校验提供上下文。

### 2. 为什么用 Milvus Lite？为什么不是 Elasticsearch？

开源项目里主要是向量语义检索，所以用了 Milvus Lite，轻量、部署简单，适合本地和开源演示。

Elasticsearch 更适合倒排索引、关键词检索和日志检索。NL2DSL 开源项目目前没有使用 Elasticsearch，关键词召回主要是 jieba 分词加向量库/本地逻辑实现。

### 3. 你项目里到底有没有 Elasticsearch？

开源项目没有 Elasticsearch。简历里如果问到，我会明确说明：公司项目或其他实践里可能有 ES 场景，但这个开源 NL2DSL 以 Milvus Lite、BGE、jieba 和 MySQL/SQLite 为主。

### 4. jieba 关键词检索和向量检索分别适合什么场景？

关键词检索适合短词、精确匹配和业务术语，比如 GMV、销售额、华东。

向量检索适合语义相似，比如用户说“业绩”“流水”“成交金额”，系统要召回销售额或 GMV。

两者结合可以兼顾精确性和泛化能力。

### 5. BGE Embedding 和 BGE Reranker 的作用分别是什么？

BGE Embedding 把文本转成向量，用于初步召回 TopK 候选。

BGE Reranker 是 Cross-Encoder，用 query 和候选文本一起打分，用于对初召回结果精排。Embedding 更快，Reranker 更准但更贵，所以一般先召回再精排。

### 6. Reranker 为什么能替代 LLM 粗排？

LLM 粗排成本高、延迟大、输出不稳定。Reranker 是专门做相关性排序的模型，输入 query 和候选文本，输出相关性分数，延迟和成本更可控。

在候选数量不大的情况下，Reranker 能稳定完成语义相关性排序，比每次调用 LLM 判断更工程化。

### 7. “800ms 降到 80ms、成本降 90%”怎么测？

建议回答：

这是在同一批评测问题、相同候选规模下，对比“LLM 粗排”和“BGE-Reranker 精排”的平均耗时和调用成本得到的结果。统计方式是记录每次排序节点的耗时，取平均值和 P95。

如果面试官追问生产数据，就说明：具体数值来自评测集或实验链路，生产环境会受模型部署、机器配置和候选数影响。

### 8. 多关键词召回为什么会有性能问题？

如果一个问题拆出多个关键词，每个关键词都串行做 embedding 和向量检索，会导致延迟累加，同时连接池和向量库请求压力增加。

优化方式是批量 embedding、并发检索、热点结果缓存和减少无效关键词。

### 9. 热点关键词 Embedding 缓存怎么设计？

缓存 key 可以是 `domain + normalized_keyword + embedding_model_version`。

value 是 embedding 向量或召回结果。需要设置 TTL 或版本号失效机制，当模型版本或语义配置更新时避免旧缓存污染。

### 10. 如果 RAG 召回错了，后续链路怎么发现？

可能在几个环节暴露：

- DSL 校验失败，比如字段不存在。
- SQL 构建失败，比如指标无法展开。
- 结果验证失败，比如结果没有回答用户问题。
- 用户反馈纠错。
- 自动化评测低分。

链路追踪会记录 RAG context，方便回溯是不是召回阶段出了问题。

### 11. 向量库里每条记录存什么？

通常存：

- id。
- text：可嵌入的文本描述。
- vector。
- type：metric、dimension、term、history 等。
- name / alias。
- domain。
- metadata：来源表、字段名、指标表达式、业务描述等。

不是只存原始字段名，而是存更容易被语义检索命中的描述文本。

### 12. Schema 召回和指标召回应不应该放同一个 collection？

最好分开。Schema、metrics、terms、history 的文本长度、检索策略、更新频率和排序权重都不同。分 collection 可以更好地控制召回比例和权重，也方便排查问题。

### 13. 业务术语“流水”“GMV”“销售额”怎么处理？

通过 terms 术语词典和 metrics 指标注册结合处理。

比如“流水”作为术语别名映射到 `gmv`，`gmv` 再通过指标注册表展开成 `SUM(pay_amount)`。LLM 不直接决定口径，只选择语义 alias。

### 14. 字段取值召回怎么避免扫大表？

优先使用字典表、维表、枚举配置或离线加工好的高频值表。对于必须从事实表抽取的字段，做离线 DISTINCT 或 TopN 采样，不在查询时直接扫大表。

敏感字段和高基数字段要加入黑名单或采样限制。

### 15. 字段值有几百万个时怎么做召回？

不能全部塞进 Prompt。一般做：

- 高频值 TopN。
- 最近值样本。
- 字典表。
- 前缀/关键词检索。
- 分层索引。
- 只对必要字段做取值召回。

如果值域太大，还可以触发澄清或要求用户提供更明确条件。

### 16. RAG 召回结果如何注入 Prompt？有没有长度控制？

按类型分块注入：指标、维度、术语、历史样例分开。每类限制 TopK，总 token 控制在预算内。

重要原则是：基础 schema 和注册指标是权威上下文，RAG 只是增强，不能让 RAG 覆盖系统注册表。

### 17. RAG 召回不足时，LLM 会发生什么问题？

常见问题是发明字段、选错指标、过滤条件不准确、Join 关系错误、时间理解偏差。

所以后面需要 DSL 校验、语义解析、权限检查和执行验证兜底。

### 18. 如果用户问了系统没有注册过的指标，应该回答错误、追问，还是猜一个？

不能猜。可以返回“该指标未注册”或触发澄清，让用户选择相近指标。企业数据场景里指标口径比回答流畅更重要。

## 四、数据治理、权限与安全

### 1. 什么叫语义层治理模型？

语义层治理模型就是把业务可理解的指标、维度、术语、权限和物理数据库之间建立标准映射。

用户说“销售额”，系统知道它是 `sales_amount`，底层是 `SUM(pay_amount)`；用户说“华东”，系统知道对应地区编码；用户无权看某些区域或敏感字段，系统在 DSL 层注入限制。

### 2. 指标、维度、数据源、术语、权限策略分别如何配置？

一般用 YAML 或数据库表配置：

- metrics：指标名、表达式、描述、单位、数据源。
- dimensions：维度名、物理字段、枚举值、描述。
- data_sources：主表、Join 关系、可用指标和维度。
- terms：业务别名到指标/维度的映射。
- permissions：用户、角色、租户、行过滤、敏感列和脱敏规则。

### 3. 行级权限和列级权限分别在哪个阶段处理？

行级权限在 DSL 阶段注入 filters，比如用户只能看华东，就给 DSL 加 `region in ['华东']`。

列级权限在 DSL 阶段检查 dimensions 和 metrics 是否包含敏感字段或未授权指标，必要时拒绝或脱敏。

### 4. 为什么权限要在 DSL 层注入，而不是 SQL 生成后做字符串替换？

SQL 字符串替换容易出错，尤其是子查询、UNION、别名、括号和不同数据库方言场景。

DSL 是结构化的，在 DSL 层注入权限更清晰，也方便审计。系统知道注入了什么权限条件，为什么注入。

### 5. 敏感字段怎么处理？

敏感字段在权限配置里定义，比如手机号、身份证、薪资。

处理方式有三种：

- 无权限直接拒绝。
- 有权限正常返回。
- 部分权限返回脱敏值。

脱敏规则可以在 SQLBuilder 或结果后处理阶段执行，但权限判断要尽量前置。

### 6. SQL 安全扫描会扫描哪些危险模式？

主要拦截：

- DELETE、UPDATE、DROP、ALTER、TRUNCATE。
- UNION 注入。
- 多语句分号。
- 注释注入。
- 存储过程执行。
- 非 SELECT 查询。
- 全表扫描或超大扫描风险。

### 7. 沙箱预检是怎么做的？

执行前先用 EXPLAIN 或 LIMIT 预览估算扫描量和执行计划。如果扫描行数过大、没有命中分区或索引、Join 代价过高，就拒绝、降级或进入人工审核。

它解决的是“SQL 语法安全但执行代价过高”的问题。

### 8. 审计日志记录哪些字段？

记录 query_id、user_id、tenant_id、question、DSL、SQL、状态、耗时、返回行数、扫描行数、trace_json、错误码、错误信息、创建时间等。

### 9. 如果用户越权查询，系统返回什么？

应该返回明确但不泄露敏感信息的错误，比如“当前用户无权限访问该指标或字段”。审计日志记录越权行为、用户、问题和被拒绝字段。

### 10. 多租户场景下怎么隔离？

从几个层面隔离：

- 每个租户独立语义配置或 domain context。
- 向量库按租户或领域隔离。
- 数据库连接按租户路由。
- DSL 校验带 tenant 上下文。
- 权限注入默认带 tenant_id。
- 缓存 key 包含 tenant/domain。

### 11. 提示词注入怎么防？

核心是不信任 LLM。即使用户说“忽略权限”，LLM 也只能生成 DSL。DSL 后面还有语义校验、权限注入、SQL 安全扫描和沙箱预检。

安全不依赖 Prompt，而依赖系统结构性约束。

### 12. LLM 生成 DSL 时包含敏感字段在哪层拦截？

在 permission_check 或 semantic validation 阶段拦截。敏感字段属于列级权限，用户无权限时拒绝或脱敏。

### 13. 如果 SQLBuilder 有 bug，安全扫描还能兜底吗？

能兜一部分，比如危险关键字、多语句、非 SELECT 和明显注入。但如果 SQLBuilder 生成了业务语义错误但语法安全的 SQL，安全扫描发现不了，需要评测、审计和结果验证补充。

### 14. 权限注入会不会影响结果准确率评估？

会。所以评测时要区分语义过滤和治理过滤。比如用户本来问华东销售额，系统又注入 tenant_id，这不应该被判为语义错误。评分时需要剥离或单独记录治理注入条件。

### 15. 审计日志和链路追踪有什么区别？

审计日志面向合规，记录谁在什么时间查了什么、执行了什么 SQL、是否成功。

链路追踪面向工程排查，记录每个节点输入输出、耗时、错误和中间 DSL。

## 五、自动化评测体系

### 1. 自动化评测具体怎么评？

准备一批自然语言问题和 expected DSL / expected SQL / expected result。执行完整查询链路后，对比 actual 和 expected。

评测不只看最终结果，还看语义、规划、执行和治理四类指标。

### 2. Semantic、Planning、Execution、Governance 分别是什么？

- Semantic：意图、指标、维度、过滤条件是否理解正确。
- Planning：Join、排序、Limit、分组等查询计划是否合理。
- Execution：SQL 是否执行成功，结果是否正确。
- Governance：权限、脱敏、审计是否生效。

### 3. DSL 生成质量如何量化？

把 DSL 拆成多个维度评分：metric 是否匹配、dimension 是否匹配、filter 字段和操作符是否匹配、order_by 和 limit 是否正确。每个维度有权重，最后加权得到总分。

### 4. SQL 执行成功率和结果准确率怎么计算？

SQL Success 是 SQL 是否能执行成功。

Result Accuracy 是执行结果是否和预期结果一致，可以比较行数、指标值、排序、TopN、分组结果等。

### 5. 权限注入、脱敏、审计覆盖怎么测？

设计专门用例：

- 用户无权限访问某区域，应自动注入过滤条件。
- 用户访问敏感字段，应拒绝或脱敏。
- 每次查询后必须生成 audit log。

评测时检查 DSL、SQL、结果和审计表。

### 6. 基线对比和回归门禁怎么做？

先保存一个稳定版本的评测结果作为 baseline。每次改 RAG、Prompt、DSL 校验、Optimizer 或 SQLBuilder 后，重新跑评测。

如果 overall score 下降、关键维度下降超过阈值、新增失败用例或执行错误，就阻断合并。

### 7. 新增优化规则怎么验证没有弄坏已有能力？

用相同测试集跑改动前后对比，看新增通过用例和新增失败用例。还要看每个维度的 diff，确认优化规则没有误改正确 DSL。

### 8. 测试集怎么构造？

可以由三部分组成：

- 人工设计核心场景。
- 线上历史问题脱敏后抽样。
- 典型失败案例沉淀。

每个用例最好只测试一个主要能力，方便定位。

### 9. 评测失败时如何定位问题？

看 trace：

- RAG context 错，说明召回问题。
- LLM 原始 DSL 错，说明 Prompt 或上下文问题。
- validate_dsl 失败，说明语义层或 DSL 生成问题。
- build_sql 失败，说明 SQLBuilder 或语义解析问题。
- execution 错，说明数据库、方言或数据问题。
- governance 错，说明权限配置或注入逻辑问题。

## 六、数据资产与语义层元数据加工平台

### 1. 这个大数据项目和 NL2DSL 是什么关系？

它是 NL2DSL 的上游治理数据底座。NL2DSL 要准确理解自然语言，需要知道有哪些表、字段、指标、维度、枚举、术语和权限。这些资产不能临时靠 LLM 猜，需要通过数据资产加工链路提前沉淀。

### 2. 元数据加工平台产出的数据给哪些模块使用？

给这些模块用：

- Schema 召回。
- 指标召回。
- 术语召回。
- 字段值召回。
- DSL 校验。
- 权限注入。
- 审计分析。
- 自动化评测数据集构造。

### 3. 业务表、字段、字段注释、指标口径、维度枚举、术语别名怎么加工？

业务表和字段来自数据库元数据；字段注释来自数据库 comment 或人工补充；指标口径来自指标配置；维度枚举来自字典表、维表或离线 DISTINCT；术语别名来自业务维护和用户反馈。

加工后统一落到元数据表，再同步成配置和向量索引。

### 4. Spark SQL 离线任务大概跑什么逻辑？

主要跑：

- 抽取表结构和字段信息。
- 统计字段空值率、重复率、值域分布。
- 抽取维度枚举 TopN。
- 聚合指标和业务域元数据。
- 生成元数据宽表。
- 输出质量报告和异常字段清单。

### 5. 元数据宽表长什么样？

核心字段包括：

`domain、table_name、column_name、column_type、column_comment、business_desc、metric_alias、dimension_alias、value_samples、is_sensitive、data_source、update_time、quality_score`

### 6. 指标元数据表怎么设计？

可以包含：

`metric_id、metric_name、metric_alias、business_desc、expr、unit、data_source、time_field、owner、enabled、version、created_at、updated_at`

关键是指标要有唯一 alias 和标准计算表达式。

### 7. 维度枚举值怎么采集？

优先级：

1. 字典表或维表同步。
2. 人工配置。
3. 离线 DISTINCT。
4. 高频 TopN 采样。

高基数字段和敏感字段不做全量枚举。

### 8. 字段注释质量差怎么办？

先做质量评分，比如过短、拼音缩写、纯英文缩写、无业务含义都标为低质量。

然后通过人工补充或 AI 辅助改写生成业务描述，但生产使用前必须人工审核。

### 9. 加工后的治理配置如何同步给向量库？

把指标、维度、术语、历史样例转成可嵌入文本，调用 embedding 模型生成向量，写入 Milvus collection。同步时保留 domain、type、name 等 metadata，并支持全量重建和增量更新。

### 10. 数据质量校验有哪些规则？

包括：

- 空值率。
- 重复率。
- 枚举值合法性。
- 数据量波动。
- 字段覆盖率。
- 主键唯一性。
- 分区完整性。
- 指标结果波动。
- 源表字段变更。

### 11. 大表 Join 性能问题怎么定位？

看 Spark UI、执行计划、Stage 耗时、Shuffle 数据量、Task 倾斜情况。重点看是否广播小表、Join key 是否倾斜、是否分区裁剪、是否扫描过多历史分区。

### 12. 分区扫描过大怎么优化？

增加时间分区过滤、分区裁剪、避免函数包裹分区字段、按业务域拆分任务、只处理增量分区。

### 13. 数据倾斜怎么判断和处理？

判断方式是看某些 task 明显慢、shuffle read 特别大。处理方式包括加盐、两阶段聚合、广播小表、过滤热点 key、拆分热点数据单独处理。

### 14. 历史数据重复计算怎么避免？

按分区增量处理，记录任务水位，使用幂等写入策略。历史分区只有在口径变更或修复数据时才重跑。

### 15. 任务失败后怎么重跑？如何保证幂等？

按业务日期和任务批次重跑。输出表采用先写临时表或临时分区，校验通过后再覆盖正式分区。避免重复 append。

### 16. 源表字段发生变化如何发现？

定时抽取数据库元数据，对比上一次 schema 快照，发现新增字段、删除字段、类型变化和 comment 变化，生成变更报告并触发语义层同步。

### 17. 指标口径变化，历史评测和线上查询怎么处理？

指标口径要做版本管理。新口径上线前跑评测集，确认影响范围。历史查询审计记录当时使用的指标版本，避免后续无法解释。

## 七、Vibe Coding / AI辅助开发

### 1. 你怎么用 AI 开发这个项目？

我不是直接让 AI 随机写代码，而是先写清需求和设计，把任务拆成小模块，比如 DSL 校验、权限注入、评测框架、RAG 检索。然后让 AI 生成初稿，我负责 Review、补测试、跑验证和调整架构。

### 2. AI 帮你做了哪些事情？哪些必须自己把关？

AI 适合做代码初稿、测试补齐、文档整理、错误排查思路和样板代码。

必须自己把关的是架构边界、业务口径、安全策略、数据权限、异常处理、性能取舍和最终代码质量。

### 3. 如何避免 AI 生成错误代码？

靠约束和验证：

- 任务拆小。
- 给出清晰接口和上下文。
- 先写测试或验收标准。
- Review 关键逻辑。
- 跑单元、集成、E2E 测试。
- 对安全和权限代码人工重点检查。

### 4. 如何设计 Prompt？

我一般会给 AI：

- 背景和目标。
- 输入输出。
- 文件路径和现有接口。
- 不允许改动的边界。
- 测试要求。
- 失败处理。
- 代码风格。

复杂任务会先让它写方案，再确认方案后写代码。

### 5. AI 生成的代码怎么 Review？

主要看：

- 是否满足接口契约。
- 是否破坏已有逻辑。
- 异常路径是否完整。
- 权限和安全是否绕过。
- 测试是否覆盖正向、反向和边界。
- 是否引入过度抽象。

### 6. 测试怎么补？

根据模块分层补：

- DSL 校验、权限规则、SQLBuilder 写单元测试。
- RAG、Graph、Agent 写集成测试。
- 自然语言到结果写 E2E 测试。
- 评测框架做回归门禁。

### 7. AI 改坏代码怎么办？

我会通过测试和 diff 发现问题。处理方式是缩小任务范围，回滚有问题的改动，重新给 AI 更明确的上下文，或者手写关键逻辑。

### 8. 如何拆分任务让 AI 更容易完成？

每个任务只做一个边界清晰的功能，比如“实现行级权限注入”或“给 DSL Validator 增加未知指标校验”。不要一次让 AI 完成整个系统。

### 9. AI 辅助写文档和写代码哪个更有效？

文档和测试样板更稳定，代码初稿也有价值，但复杂业务和安全逻辑必须人工把关。

### 10. Vibe Coding 和普通 Copilot 补全有什么区别？

Copilot 更偏局部补全；Vibe Coding 更像人机协作开发流程，包括需求澄清、方案设计、任务拆解、代码生成、测试、Review 和迭代。

## 八、Java 后端与线上稳定性

### 1. Java 做了 8 年，最近转 AI 应用，Java 基础还熟吗？

熟。AI 应用最后还是工程系统，Java 后端经验对我处理接口、消息队列、数据库、缓存、并发、部署和线上问题很有帮助。只是最近主项目的 AI Agent 部分更多用 Python 实现。

### 2. RabbitMQ 解决了什么问题？

主要解决高吞吐抓拍数据接入、异步解耦和削峰填谷。相机抓拍数据量大，直接同步处理容易拖垮主链路，通过 MQ 可以让接入、算法解析、告警处理和前端推送解耦。

### 3. 消息积压怎么排查？

看生产速率、消费速率、队列堆积、消费者异常日志、数据库写入耗时、下游接口延迟。处理方式包括扩容消费者、优化批量写入、增加预取控制、排查慢 SQL 和临时限流。

### 4. WebSocket 权限推送怎么设计？

用户连接时绑定 user_id、角色和权限范围。告警生成后根据区域、设备、组织等权限过滤，只推送给有权限的连接。连接信息保存在内存或 Redis，断线要清理。

### 5. 2000万静态底库导入怎么优化？

分批读取、批量写入、多线程处理、控制事务大小、避免一次性加载到内存。图片或大字段单独处理，失败批次可重试，导入过程记录进度。

### 6. 多线程导入如何控制？

用线程池控制并发数，按批次拆分数据。线程数根据 CPU、IO、数据库连接池决定。写库时控制 batch size，避免长事务和连接耗尽。

### 7. Zookeeper 在 SDK 算法服务集群化里做什么？

用于服务注册、发现、健康检查和负载均衡。算法 SDK 服务启动后注册到 Zookeeper，调用方动态发现可用节点，服务扩容或下线时自动感知。

### 8. Docker Compose 负责哪些模块部署？

可以编排业务服务、算法服务、数据库、缓存、MQ、Nginx 等组件，统一网络、端口、环境变量和启动顺序，方便现场部署。

### 9. 现场最常见线上问题是什么？

常见有消息积压、服务宕机、接口超时、算法服务不可用、数据库慢查询、磁盘空间不足、网络异常、机器资源不足、数据延迟。

### 10. Arthas 用过哪些命令？

常用 `dashboard` 看 JVM 状态，`thread` 看线程，`jad` 反编译，`watch` 看方法入参返回值，`trace` 看调用耗时，`stack` 看调用栈，`heapdump` 辅助内存分析。

### 11. RabbitMQ 如何保证消息不丢？

生产端 confirm，队列和消息持久化，消费端手动 ack，失败重试或死信队列，关键业务做好幂等。

### 12. 消费端幂等怎么做？

用业务唯一键、消息 ID、数据库唯一索引或状态机控制。重复消息到达时先检查是否已处理。

### 13. Redis 用在哪里？

可用于热点数据缓存、会话或连接信息、权限缓存、分布式锁、限流计数、临时任务状态等。

### 14. MySQL 大表查询如何优化？

建合适索引、避免全表扫描、控制返回字段、分页优化、按时间分区、冷热数据拆分、慢 SQL 分析、EXPLAIN 看执行计划。

### 15. JVM 问题怎么排查？

先看 CPU、内存、GC、线程。用 Arthas、jstack、jmap、GC 日志定位。CPU 高看热点线程，内存高看对象分布，接口慢看 trace，死锁看 thread。

### 16. 算法 SDK 服务不可用如何降级？

可以做超时控制、重试、熔断、切换备用节点、消息暂存、告警延迟处理。不能让 SDK 不可用拖垮整个接入链路。

## 九、简历风险追问

### 1. NL2DSL 是 Vibe Coding 做的，你本人掌握多少？

AI 只是辅助开发工具，架构设计、模块拆分、业务边界、安全策略、测试验收和最终 Review 都由我负责。面试时我可以打开代码讲模块结构、关键链路和设计取舍。

### 2. 公司项目和开源项目是不是同一个？

不是完全同一个。公司项目是实际业务实践，开源项目是我基于同类问题做的个人抽象和沉淀，用于展示架构和工程能力。公司内部数据、配置和业务细节没有放到开源项目。

### 3. 数据资产与语义层元数据加工平台真实吗？

建议按真实情况说。如果这是你基于公司数据平台/NL2DSL 上游链路总结出来的项目，就说它是围绕智能问数所需的元数据和语义层治理加工能力，不要夸大成独立大型平台。

### 4. 性能指标有没有实验数据？

回答要谨慎：这些数据来自评测集或局部链路压测，对比的是相同问题集、相同候选规模下的耗时。生产数据要看部署环境和业务规模。

### 5. Qdrant 和 Milvus Lite 怎么解释？

开源项目使用 Milvus Lite；Qdrant 是我在其他向量检索实践或公司项目中接触的组件。简历技能清单里列的是技术覆盖，项目技术栈以项目段落为准。

### 6. Spark 具体写过哪些任务？

准备回答：元数据宽表加工、字段质量统计、枚举值抽取、指标数据聚合、分区增量处理、数据质量报告。最好能准备一个 SQL 示例。

### 7. 能现场打开 GitHub 项目讲代码结构吗？

可以。建议讲：

- `nl2dsl/agent`：Agent 编排。
- `nl2dsl/graph`：LangGraph 查询管道。
- `nl2dsl/dsl`：DSL 模型和校验。
- `nl2dsl/rag`：Milvus/BGE/Rerank。
- `nl2dsl/permission`：权限。
- `nl2dsl/sql_engine`：SQL 构建和执行。
- `nl2dsl/evaluation`：评测。
- `web`：前端展示。

## 十、最建议重点准备的 10 个答案

### 1. 3分钟完整介绍 NL2DSL 项目

按“业务问题 -> 架构方案 -> 我的职责 -> 结果和沉淀”讲，不要一上来堆技术栈。

### 2. 为什么 NL2DSL 比 NL2SQL 更适合企业数据治理

核心点：DSL 可校验、权限可注入、指标口径可控、SQL 可构建、审计可追踪。

### 3. 自然语言查询完整链路

用户问题 -> Agent/Graph -> RAG -> DSL -> 校验 -> 权限 -> 语义解析 -> SQL -> 安全 -> 执行 -> 审计。

### 4. DSL Schema 和校验

准备好 data_source、metrics、dimensions、filters、order_by、limit、post_process 的例子。

### 5. RAG 召回方式

准备好 schema、metrics、terms、history 四类召回的用途和示例。

### 6. 权限与安全

行级权限注入 filters，列级权限检查敏感字段，SQL 安全扫描拦截危险语句，沙箱预检控制扫描量。

### 7. 自动化评测

Semantic、Planning、Execution、Governance 四维评分，配合 baseline 和回归门禁。

### 8. 元数据加工如何支撑 NL2DSL

元数据加工提供 Schema、指标、维度、术语、枚举、权限，是 RAG、DSL 校验和权限注入的上游数据。

### 9. Vibe Coding 质量控制

AI 负责提效，你负责架构、边界、Review、测试和质量。准备一个具体案例。

### 10. 亲手解决的复杂问题

优先准备 Rerank 优化、DSL 修正闭环、权限注入、评测回归四选一。回答结构：问题背景 -> 根因定位 -> 解决方案 -> 验证结果 -> 复盘。
