# RAG 检索链专项（已实现）

> **证据边界**：本文只讲**已经写在代码里**的检索链路，每条结论都有 `file:line` 证据，可以说"我做过"。
> 「检索层评估」「RRF 融合」「Query 改写」等**未实现**内容，见 [RAG 召回评估与优化设计题](../04-设计题/RAG召回评估与优化设计题.md)。

---

## 0. 三句话（开场口径）

1. **我的 RAG 是"结构化知识库型"**：知识源是治理配置（指标、维度、术语、历史样例），不是 PDF 文档，所以没有文档解析和切分，一条记录 = 一个语义实体。
2. **检索链是"四集合召回 → 精排 → 阈值 → 空召回回退 → 预算裁剪"**，不是一次向量搜索。
3. **我能量化的是端到端 DSL 正确率**；检索层本身（Recall@K）还没量化——那是我下一步要补的。

## 一、索引侧：三份 YAML → 四个集合

`nl2dsl/rag/sync.py`

| YAML | 集合 | 每条记录 |
|---|---|---|
| `metrics.yaml` | `schema` | 指标 + 维度 + **join 关系**（三类混装） |
| `metrics.yaml` | `metrics` | 只有指标定义 |
| `terms.yaml` | `terms` | 术语 + **每个别名单独一条** |
| `history.yaml` | `history` | 问题 → DSL 的 few-shot 样例 |

文本模板（`sync.py:64` / `:116` / `:141`）：

```
指标: sales_amount, 计算: SUM(pay_amount), 说明: 含税销售额
维度: region, 字段: region_code, 说明: 销售区域
表关联: orders (orders) 可以 INNER JOIN customer_dim ON customer_id
术语: GMV, 别名: 流水, 成交总额, 说明: ...
问题: 查华东销售额
DSL: {"data_source": "orders", ...}
```

三个实现细节：

1. **术语别名单独入索引**（`sync.py:124-131`，`text = "流水 -> gmv"`）——把同义词扩展前移到索引期，用户说"流水"能直接向量命中。
2. **history 只 embed 问题**（`sync.py:144`）——要匹配的是"新问题 vs 旧问题"，DSL 只作展示。
3. **ID 用 md5 前 15 位转 int64**（`sync.py:37-40`）——Milvus 要求整型主键，重复同步天然幂等。

**更新方式**：`auto_sync()`（`sync.py:205`）对比 YAML mtime 与状态文件，按需增量同步。

**Embedding**：`bge-base-zh-v1.5`，`normalize_embeddings=True`，**COSINE** 度量（`embedder.py:23-41`、`store.py:28-35`）。

## 二、召回侧：四集合，两套策略

`retriever.py:36` 定义 `COLLECTIONS = ["schema", "metrics", "history", "terms"]`，但召回时**故意区别对待**（`_coarse_retrieve`，`retriever.py:154`）：

| 集合 | 召回方式 | 理由 |
|---|---|---|
| `schema` / `metrics` / `terms` | jieba 关键词逐词检索 + 整句向量兜底 | 短命名实体，精确 > 语义 |
| `history` | 只做整句语义检索 | 长文本，"问题像不像"才有意义 |

关键词通道实现（`retriever.py:93-112`）：

1. 启动时从向量库 `name` 字段和 text 里抽 2-8 字中文短语，**动态构建关键词表**；
2. 全部 `jieba.add_word(freq=1000)` 注册进自定义词典（`retriever.py:84-91`）——保证"客单价""让利"不被切碎；
3. 查询时 `jieba.cut` → 过滤停用词（含"查询/多少"这类意图词）→ 大小写不敏感匹配。

> 为什么这一步关键：通用分词会把"客单价"切成"客/单价"，向量检索立刻崩。把业务词灌进词典，是**用工程手段补模型的中文业务词短板**。

## 三、检索链五步

`retrieve_hybrid()`（`retriever.py:191-244`），默认 `coarse_k=10, keyword_top_k=3, threshold=0.5, top_k=5`：

```
① 粗召回：每集合关键词通道 + 语义通道各召回，按 id 去重合并（关键词优先）
② 精排：CrossEncoder 逐集合独立打分，降序排序
③ 阈值：丢弃 rerank_score < 0.5
④ 回退：某集合全被过滤 → 保留原始排序前 3 条
⑤ 截断：每集合最终保留 top_k=5
```

三个设计意图：

- **逐集合独立精排**：不同集合文本长度差异大，分数不可比，混排会失真。
- **精排失败降级**（`retriever.py:219-223`）：reranker 异常时给所有候选 0.5 中性分，保持原顺序、不丢结果。
- **空召回回退 top3**（`retriever.py:234-236`）：防止阈值卡太死导致上下文为空。

## 四、上下文组装：优先级 + 预算 + 分区

`build_context()`（`retriever.py:262-323`）：

| 优先级 | section | 为什么在这 |
|---|---|---|
| 1 | terms | 决定 metric alias 选谁，错了整条查询废掉 |
| 2 | schema | 决定可用字段与 join |
| 3 | metrics | 与 schema 有冗余，可牺牲 |
| 4 | history | 只是 few-shot 参考 |

- **join 单独成区**：`type == "join"` 的记录抽出来放最前，并提示"涉非主表字段必须加 joins"。
- **token 预算**：`max_chars=4000`，超预算时**按 section 从尾部逐条减**，减到能放下；一条都放不下就停止加后续 section。
- **格式化**：每段有固定标题（【可用指标】【业务术语映射】…），prompt 里明确"alias 必须用映射表右边的值"。

> 这段是最容易被忽略、收益却最大的部分：**同样的检索结果，组装顺序不同，LLM 选错率差很多。**

## 五、这个实现的已知边界（不是提案，是实现本身的局限）

| 边界 | 说明 | 影响 |
|---|---|---|
| **阈值 0.5 未校准** | `retriever.py:232` 是拍的，没做过分数分布分析 | 若某类查询普遍打 0.2-0.4，永远走回退分支，等于精排失效 |
| **只增不删** | 增量同步按 mtime，YAML 里删掉的实体，旧向量不清理 | 会召回已废弃字段 |
| **逐词 embed** | `retrieve_by_keywords` 每个关键词单独 embed（`retriever.py:144`） | 最坏 3 词 × 4 集合 = 12 次 embedding 调用 |
| **无检索层指标** | 只有端到端覆盖脚本 | 无法区分"没召回"还是"召回了没用对" |
| **Milvus Lite 不可上生产** | 单文件嵌入式，无副本、无并发扩展 | 只适合开发与演示 |
| **单轮** | 每次查询独立检索，无会话上下文 | 指代类问题无法处理 |

> 主动说这六条，比等面试官挖出来强。它们全部是**实现局限**，不是"没做"——性质不同。

## 六、相关追问（只回答"你怎么做的"这一类）

**Q1：为什么 history 走整句语义，其他走关键词？**
> "短实体（指标名、维度名、术语）需要精确匹配——`region` 和 `region_code` 语义几乎一样，向量分不开，关键词能；整句问题则需要语义相似，因为用户问法千变万化，字面几乎不重叠。"

**Q2：术语别名为什么要单独入库？**
> "等于把同义词扩展前移到索引期。用户说'流水'，向量能直接命中'流水 -> gmv'这条记录，不用在查询时再跑一次改写。"

**Q3：jieba 是怎么用的？**
> "不是默认分词。启动时把向量库里所有实体名和中文短语抽出来，`add_word` 灌进自定义词典，权重给到 1000，保证业务词不被切碎；查询时再过滤停用词和查询意图词。"

**Q4：Rerank 的作用？**
> "粗召回是双塔，query 和 doc 分开编码，精度有限；CrossEncoder 把两者拼起来编码，能捕捉交互信息。代价是逐条推理，所以只能用在少量候选上——粗召回 10 条、精排留 5 条。"

**Q5：精排挂了怎么办？**
> "降级给中性分 0.5，保持原顺序继续走。宁可排序差一点，也不能因为一个可选组件挂掉导致整个查询失败。"

**Q6：上下文超预算怎么处理？**
> "不是截字符串，是按 section 逐条减——从尾部去掉整条记录，直到放得下。字符串截断会把一条指标定义切成半句，模型反而更容易幻觉。"

**Q7：怎么保证不同集合的分数可比？**
> "不保证，也不比较。每个集合独立精排、独立取 top_k，最后按固定优先级组装成 section。跨集合比分数本身就没有意义。"
