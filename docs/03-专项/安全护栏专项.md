# 安全护栏专项（已实现）

> **证据边界**：本文只讲**已实现**的护栏（10 层防御 + 代码审计出的 7 个真实缺陷），有 `file:line` 证据。
> 「认证体系」「AST 级 SQL 校验」「PII 识别」「限流熔断」等**未实现**内容，见 [认证与 SQL 护栏加固设计题](../04-设计题/认证与SQL护栏加固设计题.md)。

---

## 0. 三句话（开场口径）

1. **核心不是"拦住所有攻击"，而是"把不可信的东西限制在可校验的结构里"**——LLM 只出 DSL，不出 SQL；SQL 由代码构建，不由模型拼。
2. **护栏是多层同心圆，每层独立失效**——任何一层被绕过，下一层还能兜住；最外层永远是人审和审计。
3. **失败要 fail-closed，不能 fail-open**——这是我代码审计里发现最该修的一条。

---

## 一、10 层防御

```
用户问题
  ├─ L0 身份与租户 ────── 从请求体取 user_id / tenant_id（⚠ 无认证）
  ├─ L1 输出约束 ──────── strict json_schema + temperature=0 + Pydantic
  ├─ L2 DSL 校验 ──────── 注册表白名单（指标/维度/数据源）+ 语义校验
  ├─ L3 治理规则 ──────── optimizer G001 / G002（⚠ 实际空转）
  ├─ L4 权限注入 ──────── 行级过滤 + 列级检查（⚠ fail-open）
  ├─ L5 SQL 构建 ──────── SQLAlchemy 表达式（参数绑定）+ 注册表表达式权威
  ├─ L6 SQL 扫描 ──────── 5 条正则：DML/DDL、注释、UNION、多语句
  ├─ L7 沙箱预检 ──────── EXPLAIN + LIMIT 10 预览 + 无 WHERE 检测
  ├─ L8 执行 ──────────── 只读连接（⚠ 无 statement_timeout）
  ├─ L9 人工复核 ──────── human_review + interrupt_before + checkpointer
  └─ L10 审计 ─────────── nl2dsl_audit_log（DSL/SQL/trace/错误码）+ 凭证抹除
```

> 口径：**"这不是一层防护，是十层。每一层都假设上一层已经被绕过。"**

## 二、逐层实现

### L1 输出约束：把模型关进 schema

`llm/client.py:47` `generate_structured()`：

```python
"temperature": 0,
"response_format": {"type": "json_schema",
                    "json_schema": {"name": "dsl_response", "strict": True, "schema": schema_dict}}
```

- **strict json_schema**：输出被约束在 DSL 结构上，不是自由文本
- **temperature=0**：最大化确定性
- 兜底 `generate_json_object()`：不支持 strict 的端点降级为 json_object
- 再往下有 post_processor + `RetryChain`（校验失败带错误重试，最多 3 次）

> 价值：把"模型可能输出任意文本"的开放问题，变成"模型必须输出这个 JSON"的封闭问题。

### L2 DSL 校验：白名单 + 语义规则

`dsl/validator.py:43` 三道白名单：data_source 必须存在、metric.alias 必须在注册表、dimension 必须在注册表（且属于该 data_source 或可经 join 到达）。

`dsl/semantic_validator.py` 区分 error / warning：

- **error（阻断 + 触发修正）**：数值算子给了非数值、`between` 不是两元素、`in` 不是列表、having 缺 metrics、同字段冲突条件
- **warning（只记日志）**：未知字段、值不在已知域

> 这个划分是刻意的：**未知字段可能是合理的（新加的列），但类型不符一定有问题。**

### L3 治理规则：本意是"致命拒绝"

`optimizer/rules/governance.py` 两条规则都 `is_fatal=True`：

- **G001 敏感字段越权**：命中敏感字段且无脱敏规则 → Reject
- **G002 指标未授权**：用户角色不在指标 `allowed_roles` 里 → Reject

设计意图：**在 DSL 层拒绝，比在 SQL 层拦更早、更容易审计。**

### L4 权限：行级注入 + 列级检查

`permission/row_level.py`：把用户 `row_filters` 和 `tenant_id` 注入 DSL 的 filters。
`permission/column_level.py`：`check()` 遍历 dimensions 查敏感列；`mask()` 按规则脱敏一行。

### L5 SQL 构建：用表达式，不用字符串拼接

`sql_engine/builder.py:205-236`：

```python
if f.operator == "=":
    return col == aligned        # SQLAlchemy 表达式 → 绑定参数
elif f.operator == "in":
    return col.in_(aligned)
```

**过滤值永远走绑定参数，不存在值注入。**

两条附加安全属性：

1. **注册表表达式权威**：`_metric_expr()` 优先取注册表 `SUM(pay_amount)`，**忽略 LLM 猜的 field**（`builder.py:42-55`）
2. **limit 硬上限**：`DSL.limit = Field(default=100, le=10000)`

### L6 SQL 扫描：最后一道正则

`sql_engine/scanner.py`，全文 19 行、5 条规则：

| 规则 | 拦截 |
|---|---|
| `\b(DELETE\|UPDATE\|DROP\|INSERT\|ALTER\|CREATE\|TRUNCATE)\b` | 写操作 |
| `/\*.*?\*/` | 块注释 |
| `--[^\n]*` | 行注释 |
| `\bUNION\b` | UNION 注入 |
| `;\s*\w+` | 多语句 |

> 口径：**"我知道它是 5 条正则，不是 AST 校验——它的定位是'最后一道廉价兜底'，真正的防线在 L2/L5。"**

### L7 沙箱预检

`query/sandbox.py`：

1. `EXPLAIN QUERY PLAN` 估扫描行数（SQLite 专用，`scan_count*1000` 启发式），超 `max_scan_rows=100000` 记风险
2. `LIMIT 10` 预跑实测耗时，超 `max_exec_time_ms=5000` 记风险
3. 无 `WHERE` → 记"可能全表扫描"

风险非空 → `passed=False` → 路由到 `human_review`。

### L9 人工复核

`compile(checkpointer=..., interrupt_before=["human_review"])`——沙箱判风险时图会**停住等人批准**，批准后从检查点继续。

> 这是最接近"企业级"的一环：**机器不确定时，把决定权交回人。**

### L10 审计

`audit/logger.py` 的 `nl2dsl_audit_log`：`query_id / user_id / tenant_id / question / dsl_json / sql_text / status / rows_scanned / rows_returned / trace_json / error_code`。

- UPSERT 用 `COALESCE(excluded.x, x)`，避免异常分支二次写入清空已存 DSL
- `get_query(tenant_id=...)` 把租户过滤下沉到 SQL，**跨租户记录直接返回 None**，不泄露存在性
- 异常信息落审计前抹掉连接串和 `password=`/`api_key=` 明文（`api_factory.py:320-334`）

## 三、代码审计发现的 7 个真实缺陷（按严重度）

> 这一节是本文最有价值的部分：**主动说出来 + 给出修法，比被面试官挖出来强十倍。**

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | **无认证、无鉴权** | `api_factory.py:265` `user_id` 直接从 body 取；`/api/v1/admin/*` 无保护 | 任何人冒充任意用户/租户 |
| 2 | **租户隔离靠调用方自报** | `tenant_id` 也是 body 字段（只有非空校验） | 改字段就跨租户 |
| 3 | **行级权限 fail-open** | `row_level.py:8-11`：`if not user_perm: return dsl` | 未登记用户 = 全量可见 |
| 4 | **G001/G002 永久空转** | `governance.py:24` 读 `sensitive_fields`，配置里叫 `sensitive_columns`；`governance.py:86` 读 `metric_permissions`，配置里没有 | 两条 fatal 规则从未触发 |
| 5 | **脱敏未接线** | `ColumnLevelSecurity.mask()` 在 `nl2dsl/` 全包无调用点 | 敏感字段要么被拒、要么原样返回 |
| 6 | **列级检查只覆盖 dimensions** | `column_level.py:15-20` 只遍历 `dsl.dimensions` | 敏感字段写进 metrics/filters/order_by 就绕过 |
| 7 | **filter 字段未做白名单 → text() 逃生口** | `semantic_validator.py:86` 未知字段只是 warning；`builder.py:119-124` 字段含空格或 CASE 关键字就 `text()` 原样拼接 | 客户端直传 DSL 时可用 `OR` 绕行级过滤 |

**已实现的修法（局部改动，改完可验证）**：

1. `row_level.inject()` 改 fail-closed：查不到权限直接 `PermissionError`
2. G001 改读 `sensitive_columns`；`permission_config` 传整个 permissions 文件（`engine.py:200` 现在只传 `users` 子 dict）
3. 主链路执行结果返回前调用 `mask()`
4. 列级检查扩到 metrics.field / filters.field / order_by.field
5. filter 字段未注册 → **error 而非 warning**
6. `text()` 只接受注册表来源的表达式，不接受 DSL 原始输入

> 剩余第 1、2 条是架构级（要动网关/认证），不在应用层解决。

## 四、相关追问（只回答"你怎么做的"）

**Q1：LLM 生成的 SQL 你怎么敢执行？**
> "因为 LLM 不生成 SQL。它只出 DSL——受 strict json_schema 约束的 JSON，只含注册表里的指标/维度/数据源。SQL 由 SQLBuilder 用 SQLAlchemy 表达式构建，过滤值走绑定参数。"

**Q2：SQL 扫描只靠正则够吗？**
> "不够，它只是最后一道廉价兜底。真正的防线在 DSL 白名单和 builder 的参数化构建。正则容易被编码/注释绕过，正确做法是 AST 校验（还没做）。"

**Q3：行级权限怎么注入？**
> "从 permissions 配置取用户 row_filters 和 tenant_id，追加到 DSL filters，再由 builder 编译成 WHERE。"

**Q4：你的沙箱真的隔离吗？**
> "不是沙箱，是预执行探针：EXPLAIN 估行数、LIMIT 10 预跑测耗时、检测无 WHERE，超阈值打风险标记交人审。真隔离要独立只读副本 + 容器 + 资源组，没做。"

**Q5：审计日志能篡改吗？**
> "能。现在是普通表，可以 UPDATE/DELETE。防篡改要链式哈希 + 只追加 + WORM 归档。admin 审计接口目前也没有鉴权。"

**Q6：越权怎么测？**
> "目前只有单测覆盖权限函数，没有系统性对抗用例集。应该有：敏感字段直查、跨租户、表达式注入三类，期望 deny，任何 allow 算回归失败。"
