# 上下文工程专项（已实现）

> **证据边界**：本文只讲**已实现**的上下文组装与状态管理，有 `file:line` 证据。
> 「多轮会话」「记忆分层」「澄清闭环」「指代消解」等**未实现**内容，见 [多轮记忆与澄清闭环设计题](../04-设计题/多轮记忆与澄清闭环设计题.md)。

---

## 0. 三句话（开场口径）

1. **我的项目是单轮系统**：一次请求 = 一个问题 = 一个 LangGraph thread，没有会话记忆。
2. **但上下文工程做了**：不是"塞更多"，而是按优先级分配 **4000 字符预算**，超预算时按语义单元裁剪。
3. **多轮和记忆是明确缺口**：checkpointer 我只用来做人工复核的暂停恢复，没当成对话记忆。

---

## 一、上下文只有一个注入点

```
question ──► RAGRetriever.build_context(query, top_k=5, max_chars=4000)
                     ├─ terms   （术语映射，最强约束）
                     ├─ schema  （指标 + 维度 + join）
                     ├─ metrics （指标定义）
                     └─ history （相似历史样例）
                     ▼
            build_prompt() ──► 【上下文】+【用户问题】+【强制要求】
```

四个 section 的**优先级是硬编码的**（`retriever.py:286-292`）：

| 顺序 | section | 为什么 |
|---|---|---|
| 1 | terms | 决定 metric alias 选谁，错了整条查询废掉 |
| 2 | schema | 决定可用字段与 join |
| 3 | metrics | 与 schema 冗余，可牺牲 |
| 4 | history | 只是 few-shot 参考 |

**超预算处理**（`retriever.py:308-321`）：按 section **逐条减**，从尾部去掉整条记录直到放得下；连 1 条都放不下就停止加后续 section。

> "截断"和"按语义单元裁剪"是两件事。字符串截断会把一条指标定义切成半句，模型反而更容易幻觉。

---

## 二、状态里没有对话历史

`QueryState`（`graph/state.py:57-94`）全部字段：

| 类别 | 字段 |
|---|---|
| 输入 | `question` / `domain` / `user_id` / `tenant_id` / `data_source` |
| 改写 | `original_question` / `rewrite_reason` / `entity_hints` |
| 中间产物 | `ambiguities` / `plan` / `confidence` / `explanation` / `dsl` / `dsl_attempts` / `sql` / `sandbox_result` / `complexity` |
| 输出 | `data` / `status` / `error` / `error_code` |
| 元信息 | `query_id` / `started_at` / `llm_used` / `reference_date` / `trace` |

**没有 `messages`，没有 `history`，没有 `session_id`。**

唯一沾边的是 `original_question`——不是对话历史，而是 `decompose` 改写前保留的原句，用于审计。

> 口径：**"state 是为单次查询设计的，这是有意的：每个节点需要确定输入，混入对话历史会让 DSL 校验失去确定性。"**

---

## 三、checkpointer 是"暂停—恢复"，不是记忆

```python
# engine.py
self._checkpointer = InMemorySaver()

# graph/builder.py
compile(checkpointer=checkpointer, interrupt_before=["human_review"])
```

服务对象是 **HITL**：沙箱判定有风险 → 图停在 `human_review` → 返回 `pending_review` → 人工审批后调 `/api/v1/query/resume`（`api_factory.py:1355`）用 `query_id` 恢复。

关键：**`thread_id = query_id`**（`api_factory.py:847/980/1076/1275`）——每次新查询都是新线程，不复用上一次 state。

> 典型"能力具备但用错地方"：checkpointer 天然支持会话记忆，我把它用成了任务恢复。

---

## 四、澄清是单向的

`query/clarification.py` 是**规则驱动**（不是 LLM）：

| 类型 | 触发 | 选项 |
|---|---|---|
| `time_missing` | 含"趋势/增长/同比"，无时间范围 | 本月 / 上月 / 最近7天 / 最近30天 / 全部 |
| `metric_ambiguous` | 含"销量""客户数" | 支付订单量 / 发货数量 / 完成数量 … |
| `dimension_ambiguous` | 含"地区""时间" | 收货地址 / 发货仓库 / 注册地 … |
| `comparison_ambiguous` | 含"增长/同比"，没说基准 | 环比上月 / 同比去年 / 不对比 |

链路到澄清就结束（`graph/builder.py:173-180`：`clarification → END`），返回选项给前端。**没有"用户选项 → 回灌 → 继续查询"的接口**，用户只能把选项拼进问题重新问一遍。

---

## 五、子查询共享的是基础状态，不是上下文

`agent/dispatcher.py:136` `dispatch_sub_queries(sub_queries, domain_context, base_state)`：

- 每个子查询从 `base_state` 复制一份（question / user_id / tenant_id / domain），独立跑一次图；
- 独立子查询 `asyncio.gather` 并行，`Semaphore(MAX_PARALLEL_SUB_QUERIES)` 限流；
- 子查询之间**不共享召回上下文**，各自重新检索。

> 有意为之：子查询语义可能完全不同（"对比华东和华南"），共享上下文反而污染。

## 六、这个实现的已知边界

| 边界 | 说明 |
|---|---|
| 单轮 | 无会话状态，指代类问题无法处理 |
| 无压缩 | 只有按条裁剪，没有摘要 |
| 澄清单向 | 无回灌接口 |
| checkpointer 内存版 | 进程重启即失忆，不能多实例共享 |
| 子查询不共享上下文 | 相同语义重复检索，有少量浪费 |

## 七、相关追问（只回答"你怎么做的"）

**Q1：上下文优先级怎么定？**
> "按'错了会怎样'排。术语错了，metric alias 就错，整条查询废掉；schema 错了直接报错；metrics 和 schema 冗余可牺牲；history 只是参考品。"

**Q2：超长怎么处理？**
> "按 section 逐条减，不是截字符串。因为一条指标定义被切成半句，模型反而更容易幻觉。"

**Q3：为什么 state 里没有消息列表？**
> "state 是为单次查询设计的。每个节点需要确定输入——DSL 校验不该因为前面聊了 10 轮而改变行为。对话上下文应该在上游收敛成一个完整问题再进图。"

**Q4：检查点用内存有什么问题？**
> "进程重启就丢，不能多实例共享。生产要换 SqliteSaver 或 PostgresSaver，键是 thread_id。现在只够单机演示和 HITL。"

**Q5：子查询的上下文怎么隔离的？**
> "每个子查询从基础状态复制一份独立跑图，各自重新检索。不共享召回结果，避免互相污染。"
