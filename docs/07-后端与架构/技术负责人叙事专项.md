# 技术负责人叙事专项（对标 JD 第 17–18 条）

> **证据边界**：本文教你「如何**诚实地**把 8 年开发经验讲成技术负责人的可迁移能力」，不是教你编一段带团队的经历。
> 你现在是**核心开发 / 模块负责人**，不是正式的团队管理者。这个事实不用藏，藏不住。
>
> **怎么读**：第 1 节先解决"身份怎么定位"，第 3 节是六个高频问题的答题框架，第 6 节是不能碰的红线。

---

## 1. 先解决定位问题：技术负责人的两条轨道

很多人以为"技术负责人"就是"管人的"，其实分两条完全不同的轨道：

| 轨道 | 英文 | 核心职责 | 衡量标准 |
|---|---|---|---|
| **技术负责人（技术线）** | Tech Lead | 架构设计、技术选型、方案评审、攻坚 | 系统是否合理、难题是否解决 |
| **团队负责人（管理线）** | Engineering Manager | 人员、绩效、招聘、团队建设 | 团队产出、人员成长 |

那个 JD 写的是「研发团队技术管理」+「研发计划与项目推进」——**偏技术负责人 + 兼职项目管理**，不是纯 HR 管理。

### 1.1 你可以诚实主张的三件事

```
① 我做过技术方案的主导者：NL2DSL 的分层架构、DSL 契约、评测体系是我设计的
② 我做过复杂系统的落地负责人：50+ 台机器的现场系统，从部署到线上运维
③ 我做过质量把关：测试规范、代码评审、发布流程
```

### 1.2 你不能主张的一件事

```
❌ "我管过 10 人团队" —— 一旦被追问"怎么定绩效、怎么处理低绩效、怎么招聘"，立刻露馅
```

### 1.3 正确的说法模板

> "我没有正式带过一个团队，但我做的是**模块负责人 + 技术把关**的角色：方案我定、评审我做、线上问题我兜、新人我带过。团队管理这块（绩效、招聘、梯队）是我要补的，但技术决策和项目推进我有实际经验。"

**这句话的价值**：主动交底 + 强调可迁移部分，比含糊其辞可信一百倍。

## 3. 六个高频问题 + 答题框架

### 3.1 "你怎么做任务分解？"

**框架：WBS + 依赖 + 风险**

```
① 按交付物拆，不是按人拆
   ❌ "张三做接口，李四做前端"
   ✅ "用户认证模块 / 查询链路 / 权限体系 / 审计"

② 每个任务拆到 2 人日以内（超过就继续拆）

③ 标依赖：谁阻塞谁
   权限体系 → 依赖认证模块（必须先做认证）

④ 标风险：不确定的单独列
   "Milvus 集成" → 高风险，先做 1 天技术验证

⑤ 三点估算：乐观 / 最可能 / 悲观，取 (O + 4M + P) / 6
```

**你的真实案例**：NL2DSL 拆成"DSL 模型 → 校验 → 权限 → SQL 构建 → 扫描 → 沙箱 → 审计"，每个是独立可测的模块；**校验放在构建之前**，因为它是硬依赖。

### 3.2 "你怎么做代码评审？"

**框架：分级 + 清单 + 卡点**

```
【分级】—— 定了级，才不会所有意见都吵成一样重
P0 必须改：安全漏洞、正确性 bug、性能问题、事务边界错
P1 建议改：可读性、命名、重复代码
P2 可改可不改：风格、个人偏好

【清单】
□ 边界条件：null / 空集合 / 超长输入
□ 异常处理：抛了没接？接了没记日志？吞了异常？
□ 事务边界：跨服务调用是否在事务内？
□ 并发安全：共享变量、双重检查、锁粒度
□ 资源释放：连接、流、线程池
□ SQL：是否走索引、是否 N+1
□ 日志：关键路径有没有、敏感信息有没有打出来
□ 测试：新增逻辑有没有用例

【卡点】
P0 未修复 → 不合入（CI 阻断）
```

**你的真实经验**：可以直接说"我的测试是自动化跑的，不是靠人工点"——这比"我认真 review"有说服力。

### 3.3 "你怎么跟踪进度？"

**框架：里程碑 + 燃尽 + 风险台账**

```
① 里程碑看板：每个模块 设计/开发/联调/测试/上线 五态
② 每日/每周同步：只看"昨天做了什么、今天做什么、有没有阻塞"
③ 燃尽图：剩余工作量 vs 剩余时间，两条线分叉就预警
④ 风险台账：
   风险 | 概率 | 影响 | 应对 | 负责人 | 状态
   Milvus 不稳定 | 中 | 高 | 降级到内存存储 | 我 | 监控中
⑤ 偏差处理：偏差 > 20% 立即上报，不说"能赶上"
```

> 关键态度："**我不喜欢说'应该是能赶上'，我会说'按当前速度还差 3 天，要么砍范围要么加人'**"——这是负责人该有的表达方式。

### 3.4 "你怎么带新人？"

**框架：任务阶梯 + 代码即教学 + 反馈节奏**

```
第 1 周：环境跑起来 + 读一个最小链路（不求懂全部）
第 2~3 周：改一个边界清晰的小需求（有现成测试兜底）
第 4 周起：独立负责一个模块（我给设计建议，不给代码）

关键动作：
· 代码评审当教学：不只说"这样不对"，说"为什么"和"换个写法会怎样"
· 任务难度略高于能力：太简单没成长，太难就崩
· 每周一次 1:1：问"哪里卡住"比问"进度如何"有用
```

**诚实版**：如果你只带过 1-2 个新人，就说"我带过 1 个新人从改 bug 到独立负责模块"——具体数字比"带过团队"可信。

### 3.5 "线上出事故你怎么处理？"

**框架：止血 → 定位 → 复盘 → 改进 → 验证**

```
① 止血第一（0~10 分钟）：回滚 / 降级 / 切流，别急着查根因
② 定位（10~60 分钟）：看监控、看日志、看变更记录
   原则：先怀疑最近一次变更（90% 事故来自变更）
③ 复盘（24 小时内）：时间线 → 5 Why → 根因 → 改进项
④ 改进项必须可验证：谁、什么时候、怎么证明改好了
⑤ 跟踪：两周后回看，改进项有没有落地
```

**你的真实素材**：50+ 台机器、日抓拍 1000 万级的现场运维，处理过消息积压、接口超时、服务异常、数据延迟——**这就是"事故处理"的一手经验，直接讲**。

### 3.6 "你怎么做技术选型？"

**框架：约束 → 候选 → 对比维度 → 验证 → 决策记录**

```
① 先列约束：团队会什么、要跑多久、数据量、预算、能不能停机
② 候选 2~4 个（不要 1 个，也不要 10 个）
③ 对比维度：能力、成本、学习曲线、社区、可运维性
④ 高风险的先做 1 天 PoC 验证
⑤ 写 ADR（架构决策记录）：为什么选它、放弃了什么、什么情况下会重选
```

**你的真实案例**：NL2DSL 为什么"LLM 只出 DSL 不出 SQL"——这就是一次完整的技术选型，有约束（可治理）、有替代方案（直接生成 SQL）、有决策理由（可校验/可审计）。**这个案例含金量比任何管理术语都高。**

## 4. 项目管理：JD 第 18 条怎么答

| 问题 | 答法要点 |
|---|---|
| **怎么估工作量** | 三点估算 + 历史类比（"上次类似模块 5 人日"）+ 留 20% buffer |
| **需求变更怎么办** | 记录 → 评估影响 → 让产品决定砍范围还是延时间 → **书面确认** |
| **敏捷怎么跑** | 两周迭代：需求梳理 → 排期 → 开发 → 演示 → 回顾；DoD 定义"什么算完成" |
| **跨团队协作** | 明确接口人 + 契约先行（先定 API/数据格式）+ 联调计划 |
| **版本交付** | 发布清单 + 回滚方案 + 灰度策略 + 交付文档 |

**DoD（完成的定义）示例**——这个细节能让面试官眼前一亮：

```
□ 代码合入主干
□ 单元测试通过且覆盖率不低于阈值
□ 代码评审通过（P0 已修复）
□ 部署到测试环境并验证
□ 文档更新（接口/配置/运维手册）
□ 监控埋点已配置
```

## 5. 一段可背的自述（诚实版，约 90 秒）

> "我 8 年做后端，最近三年在数据治理和 AI 应用方向。我的角色更接近**技术负责人**而不是纯执行：NL2DSL 这套架构是我设计的——把'LLM 直接生成 SQL'改成'LLM 生成 DSL、系统负责校验执行'，核心考虑是让查询可治理、可审计。
>
> 在质量上我比较较真，测试是自动化的，评测有基线门禁，改坏了 CI 会拦。
>
> 在协作上，我做过方案评审、代码评审，也带过新人从改 bug 到独立负责模块；早期在人脸项目做过 50 多台机器的现场系统，从部署、扩容到线上问题都是我兜。
>
> 说到缺的部分：我没有正式带过团队，绩效、招聘、梯队建设这些是我要补的。技术决策和项目推进我有实际经验，管理方法我在系统学。"

**为什么这么讲有效**：

- 有具体动作（架构怎么改、门禁怎么拦）；
- 有数字（8 年、3 年、50 台）；
- **主动交底缺口**——这反而建立信任。

## 6. 红线：这四句话绝对不能讲

| 不能说 | 为什么 |
|---|---|
| "我管理过 N 人团队" | 追问绩效/招聘/冲突处理立刻露馅 |
| "我负责整个项目的技术决策" | 追问"你否决过谁"答不上来 |
| "我带团队从 0 到 1" | 0 到 1 需要讲招聘和建制，你没做过 |
| "我用 Seata 做过分布式事务" | 技术上会被追问细节（分支事务、回滚日志） |

**替换说法**：

| 想表达 | 诚实说法 |
|---|---|
| 我管团队 | 我做模块负责人，负责方案和评审 |
| 我负责架构 | 我主导了 X 系统的架构设计，评审由我和团队一起过 |
| 我带人 | 我带过 1-2 个新人从改 bug 到独立负责模块 |
| 我做分布式事务 | 我用本地消息表 + MQ 实现过最终一致 |

## 7. 补课清单（两周，按优先级）

| 优先级 | 补什么 | 方式 |
