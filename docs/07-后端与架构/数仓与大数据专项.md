> **定位**：data agent 岗问大数据，问的不是"你能不能当数据工程师"，而是"**你在数据环境里干过活吗**"。
> 本文按「基础 → 高频问题 → 你的故事 → 话术」组织，目标是能被追问三层而不卡。
>
> **你的真实素材**：简历里的「数据资产与语义层元数据加工平台」（Java + Spark SQL + Yarn + HDFS）、NL2DSL 的 `configs/metrics.yaml` 治理模型。
> **如实交底**：原生数仓对接（Hive/Doris/ClickHouse）你没做过，只做过 MySQL/SQLite。这部分只能讲原理和设计，不能讲经验。

## 一、先搞清楚：这题在考什么

面试官问大数据，想确认三件事：

| 想确认的 | 对应的问法 |
|---|---|


你只需要准备第二行。

## 二、数仓基础（必须先懂，否则后面全听不懂）

### 2.1 数仓分层：ODS / DWD / DWS / ADS

```
┌─────────────────────────────────────────────────────────┐
│  ODS  贴源层                                             │
│  原样同步业务库，不做加工，保留全量历史                    │
│  表名特征：ods_order、ods_user                            │
│  作用：可回溯、可重跑                                     │
└────────────────────────┬────────────────────────────────┘
                         │ 清洗、去重、规范化、维度关联
                         ▼
┌─────────────────────────────────────────────────────────┐
│  DWD  明细层                                             │
│  一条业务事件一行，字段统一、枚举翻译、脏数据剔除           │
│  表名特征：dwd_order_detail、dwd_pay_event                │
│  作用：**最常被 AI 查询的一层**（明细可聚合）              │
└────────────────────────┬────────────────────────────────┘
                         │ 按主题聚合（宽表）
                         ▼
┌─────────────────────────────────────────────────────────┐
│  DWS  汇总层                                             │
│  按天/按主题预聚合，比如"每日每地区销售额"                 │
│  表名特征：dws_sales_1d、dws_user_1d                      │
│  作用：加速查询，但**维度组合被固定**，AI 容易查不到想要的组合│
└────────────────────────┬────────────────────────────────┘
                         │ 面向应用定制
                         ▼
┌─────────────────────────────────────────────────────────┐
│  ADS  应用层                                             │
│  直接服务报表/大屏/接口                                   │
│  表名特征：ads_sales_report、ads_dashboard_xxx            │
│  作用：口径已经写死，AI 一般**不该直接查这层**             │
└─────────────────────────────────────────────────────────┘
```

**为什么 data agent 必须懂这个**：

| 问题 | 答案 |
|---|---|
| AI 应该查哪一层？ | **DWD 为主**（明细可自由聚合），DWS 为辅（已知组合快） |
| 为什么不查 ADS？ | ADS 是给固定报表用的，维度被写死，AI 问别的组合就查不到 |
| 为什么这个知识点重要？ | 客户问"为什么查出来的数跟报表对不上"——很可能你查 DWD，报表读 ADS，口径不同 |

> **这是一个高频追问的答案**：口径不一致，常常不是 AI 算错，是**数据源层不同**。

### 2.2 维度建模：星型模型（和你的语义层直接对应）

```
                    ┌──────────────┐
                    │  dim_date    │  日期维
                    └──────┬───────┘
                           │
┌──────────────┐    ┌──────▼────────┐    ┌──────────────┐
│ dim_product  │────│  fact_order   │────│  dim_customer│
│  产品维       │    │   订单事实表   │    │   客户维      │
└──────────────┘    └──────┬────────┘    └──────────────┘
                           │
                    ┌──────▼───────┐
                    │  dim_region  │  地区维
                    └──────────────┘
```

| 概念 | 是什么 | 在你项目里对应什么 |
|---|---|---|
| **事实表** | 存"发生了什么"，每行一个业务事件 | `order_fact`（`data_sources.orders.table`） |
| **度量（measure）** | 事实表上可聚合的数值 | `SUM(pay_amount)` → **`metrics.yaml` 的 `expr`** |
| **维度表** | 存"从什么角度看"，属性集合 | `product_dim` / `customer_dim` |
| **维度（dimension）** | 维度表上的属性 | `brand`、`region` → **`metrics.yaml` 的 `dimensions`** |
| **外键关联** | 事实表 → 维度表的 join key | `data_sources.*.joins` 里的 `on` |

> **这是整份文档最重要的一句话**：
> **你的语义层（metrics + dimensions + joins）本质上就是维度建模的一份"可执行声明"。**
> 懂了这句话，"指标口径怎么治理"这类问题就都能答。

**追问：星型和雪花什么区别？**
> 星型：维度表不再拆，直接挂在事实表上（查询快，冗余多）。
> 雪花：维度表继续规范化（省空间，join 多）。
> 数仓实践**用星型为主**，因为 OLAP 场景查询性能优先。

### 2.3 分区：data agent 最容易闯的祸

**分区**就是按某个字段把数据切成目录：

```
hdfs://warehouse/dwd_order_detail/dt=2026-11-01/part-00000
hdfs://warehouse/dwd_order_detail/dt=2026-11-02/part-00000
```

**分区裁剪（partition pruning）**：SQL 里带了 `WHERE dt = '2026-11-01'`，引擎只扫那个目录。

**没有分区谓词 = 扫所有目录 = 全表扫描**。一张 10 亿行的表，可能烧掉几千块和几分钟。

```sql
-- ❌ 灾难：扫全表
SELECT SUM(pay_amount) FROM dwd_order_detail WHERE region = '华东'

-- ✅ 正确：先裁分区
SELECT SUM(pay_amount) FROM dwd_order_detail
WHERE dt BETWEEN '2026-11-01' AND '2026-11-07' AND region = '华东'
```

> **这是一个必答题**："AI 生成的 SQL 会不会全表扫？"——答案必须是"我会在 DSL 校验层强制要求时间/分区谓词，没有就拒绝"。

**分区 vs 分桶**：

| | 分区 | 分桶 |
|---|---|---|
| 按什么切 | 字段值（日期/地区） | 哈希（如 `user_id` 取模） |
| 存成什么 | 目录 | 文件 |
| 作用 | **裁剪扫描范围** | 加速 join / 采样 |
| data agent 关心吗 | **非常关心** | 不太关心 |

## 三、12 个高频问题详解

每题按「考察点 → 答法 → 追问」写。

### Q1. 你们接的是什么数仓？

**考察点**：你有没有真实的数仓语境。

**答法**：

> "开源版我接的是 SQLite/MySQL，生产上是 MySQL 关系库。数仓这块我做过上游——用 Spark SQL 加工表、字段、指标、术语这些元数据，产出语义层配置。所以我知道数仓长什么样，但原生对接 Hive/Doris 是我要补的。"

**追问：如果让你接 Hive，要改哪里？**

> "改三处：① 执行模型从同步改成异步（Hive 是提交作业，分钟级）；② 元数据不能靠反射，要从 Hive Metastore 同步；③ 沙箱的 EXPLAIN 要换成 Hive 的统计信息估算。DSL 层和权限注入层不用动。"

### Q2. Text2SQL 的方言差异怎么处理？

**考察点**：你接过几种库，有没有踩过坑。

**具体坑（能背三个就够）**：

| 差异点 | MySQL | Hive / Spark | Presto | ClickHouse |
|---|---|---|---|---|
| 日期格式化 | `DATE_FORMAT(d,'%Y-%m')` | `date_format(d,'yyyy-MM')` | `date_format(d,'%Y-%m')` | `formatDateTime(d,'%Y-%m')` |
| 字符串拼接 | `CONCAT` / `\|\|` | `concat` | `concat` / `\|\|` | `concat` |
| 整数除法 | 得小数 | **得整除**（要转 double） | 得小数 | 得小数 |
| NULL 排序 | NULL 最小 | NULL 最大（默认） | 可配置 | NULL 最后 |
| 分页 | `LIMIT n OFFSET m` | 老版本不支持 OFFSET | 支持 | 支持 |

**答法**：

> "不靠人写方言分支，靠一层方言转换。我用 sqlglot 把标准 SQL 转成目标引擎的写法，用友商的话说叫 transpile。但它不能保证 100% 正确，所以我会加一层回归测试：同一批 DSL 在各引擎上生成的 SQL 都要能被解析通过。"

**追问：转译出错了怎么办？**

> "两个兜底：① 生成后先 AST 解析一遍，解析不过直接拒；② 评测集里加多引擎用例，改一次跑一次。"

### Q3. 表很大怎么办？

**考察点**：成本意识。

**答法（四层）**：

```
① 生成前：强制分区谓词（DSL 校验层就拦）
② 生成后：估算扫描量（EXPLAIN / dry-run），超阈值拒绝
③ 执行前：沙箱预跑 LIMIT 10，测耗时
④ 执行中：超时 kill、异步提交、结果缓存
```

**追问：客户就是要查三年数据怎么办？**

> "给两条路：要么按天跑批出货（离线报表），要么让他明确接受成本——把预估的扫描量和耗时先报给他，他确认后再跑。**关键是不能让成本在用户不知情的情况下产生。**"

### Q4. 数据是 T+1 还是实时？延迟怎么办？

**考察点**：你有没有处理过"数据是空的"这类投诉。

**答法**：

> "多数客户是 T+1。所以我加了一个 `check_data_freshness` 能力——查数据的最新分区，用户问的时间范围超出数据范围时直接告诉他'数据只到 X 月 X 日'，而不是返回一个空结果让他猜。"

**为什么这个答案加分**：它把"技术能力"变成了"产品体验"。

### Q5. 指标口径怎么保证一致？

**考察点**：这是语义层的核心命题。

**答法**：

```
口径的唯一来源 = 指标注册表（metrics.yaml）
       ↓
所有查询都从注册表取表达式，不允许模型自由发挥
       ↓
模型只负责"选哪个指标"，不负责"指标怎么算"
```

具体到你的项目：

> "我的 DSL 里 metric 只存 alias，物理表达式从注册表取——**LLM 猜的 field 会被忽略**（`builder.py:_metric_expr`）。这样同一个指标永远只有一种算法。"

**追问：注册表本身错了怎么办？**

> "那是治理问题，不是系统问题。但我会让每条口径带来源和负责人，改的时候能追溯。"

### Q6. 怎么防全表扫描？

**答法**：

> "三道：① DSL 校验层要求必须有时间/分区谓词，没有就拒绝；② SQL 生成后做 AST 校验，检查 WHERE 里有没有分区字段；③ 沙箱用 EXPLAIN 估算扫描量，超阈值转人工。"

**注意**：这题如果你答"限制 LIMIT"，会被追问——**LIMIT 不减少扫描量**，只是减少返回行数。这是个常见错误。

### Q7. 大表 join 会不会爆？

**答法**：

> "会。三个约束：① join 表必须在 data_sources 里声明过，不能自由 join；② 限制 join 深度（比如最多 3 张表）；③ SQL 生成时按表大小排序，小表优先（我项目里有 `size` 字段做 join 重排）。"

**追问：join 错了怎么办？**

> "join 路径来自配置而不是模型猜，所以'join 错'等同于'配置错'，是可控的治理问题。"

### Q8. 行列权限在数仓里怎么落地？

**答法（双层）**：

```
应用层：DSL 层注入 tenant_id + row_filters（我做的）
数据层：数仓原生策略兜底
        · Hive → Ranger / Sentry（row filter + column masking）
        · Doris → 内置 RBAC + ROW POLICY
        · PostgreSQL → RLS
        · MaxCompute → label 权限
```

**为什么双层**：应用层精确（知道用户意图），数据层兜底（应用有 bug 也漏不出去）。

### Q9. 数仓分层了解吗？

**答法**（见 2.1）：ODS → DWD → DWS → ADS，重点说清**AI 该查哪一层**。

**加分句**：

> "AI 问数我会优先落 DWD，因为明细可自由聚合；DWS 只在维度组合固定时用；ADS 基本不碰——那是给固定报表的。"

### Q10. 元数据从哪来？

**答法**：

> "不是靠数据库反射（几千张表会超时），是离线同步：Hive Metastore / Glue / 数据字典平台 → 落成元数据表 → 供语义层和检索用。我用 Spark 做过这个加工。"

**追问：为什么要离线而不是实时？**

> "元数据变化频率是小时/天级，实时没意义；而且反射的代价远高于收益。"

### Q11. Doris 和 ClickHouse 怎么选？

**考察点**：选型判断力（不需要都用过）。

| 维度 | Doris | ClickHouse |
|---|---|---|
| 定位 | MPP 分析型数据库，偏"数据库" | 列存 OLAP 引擎，偏"查询加速器" |
| Join | 强（支持多表复杂 join） | 弱（大表 join 要小心） |
| 并发 | 高（适合 BI 多用户） | 中高（单查询快） |
| 数据更新 | 支持 upsert | 弱（多为 append） |
| 生态 | MySQL 协议兼容 | 自有协议 |
| 场景 | **多表分析、BI 并发** | **大宽表单表聚合、日志分析** |

**答法**：

> "如果是问数场景——多表 join、多用户并发、要更新维度——我更倾向 Doris。如果是超大规模宽表的单表聚合、日志分析，ClickHouse 更快。AI 问数大概率是多表 join，所以 Doris 更合适。"

### Q12. 数据倾斜怎么处理？（只有写了 Spark 才问）

**现象**：某个 task 跑了一小时，其他几分钟。

**原因**：join key 或 group by key 分布不均（null 值、超级大客户）。

**解法**：

| 方法 | 做法 |
|---|---|
| 过滤 null | 倾斜 key 常常是 null，先剔掉再 union 回来 |
| 加盐（salting） | 给倾斜 key 加随机后缀，打散到多个 task |
| 广播小表 | 小表 broadcast 避免 shuffle |
| 拆分热点 | 把大客户单独处理 |

> **如果你只是"用 Spark SQL 做加工"而不是"调优 Spark 作业"，可以诚实说**："我用到的是 Spark SQL 的批处理能力，倾斜问题我了解原理但没深度调优过。"

## 四、引擎选型速查

| 引擎 | 延迟 | 适合 | 成本模型 | 一句话 |
|---|---|---|---|---|

## 五、成本与性能控制（data agent 独有的重点）

这是**最能体现你懂 data agent** 的一节——数据工程师不管这个，但 AI 应用必须管。

### 5.1 为什么 AI 场景成本风险特别高

```
人写 SQL：看一眼就知道"这张表大，得加分区"
模型写 SQL：不知道表多大，可能生成一条扫全表的查询
用户点一下：可能触发 100 条这样的查询
```

**成本失控的三个来源**：模型不知道数据量、用户不知道单价、系统没有拦截。

### 5.2 六道成本控制

| 关卡 | 做法 | 拦住什么 |
|---|---|---|
| **① 分区强制** | DSL 校验要求时间谓词 | 全表扫描 |
| **② 扫描量估算** | EXPLAIN / dry-run 拿到预估字节数 | 超阈值查询 |
| **③ 行数上限** | DSL 的 `limit ≤ 10000` | 巨量返回 |
| **④ 超时** | 单查询 30s，超时 kill | 卡死的查询 |
| **⑤ 结果缓存** | 相同 DSL 的 hash 命中缓存 | 重复查询 |
| **⑥ 并发限流** | 租户级 QPS + 队列 | 打爆集群 |

### 5.3 一个能讲的具体设计

```python
def estimate_scan_bytes(sql: str, engine: str) -> int | None:
    """估算扫描量。不同引擎手段不同。"""
    if engine == "hive" or engine == "spark":
        # EXPLAIN 后从 statistics 拿 totalSize
        plan = execute(f"EXPLAIN {sql}")
        return _parse_total_size(plan)
    if engine == "clickhouse":
        return _parse_parts(f"EXPLAIN ESTIMATE {sql}")
    if engine == "doris":
        return _parse_rows(f"EXPLAIN {sql}")
    return None      # 估不出来 → 走保守策略：强制加时间窗
```

> **面试价值**：能说出"估不出来就走保守策略"，比说"我们有限制"高级得多。

## 六、异步执行模型（数仓特有，必问）

### 6.1 为什么必须异步

```
MySQL：发出去 → 50ms 返回   → 同步没问题
Hive ：提交作业 → 3 分钟 → 返回 → 同步接口一定超时
```

### 6.2 异步三件套

```
① 提交：拿到 job_id（Livy / Kyuubi / JDBC / 云 SDK）
② 轮询：查状态 RUNNING / SUCCEEDED / FAILED，带进度
③ 取结果：分页拉取，或从 OSS/S3 下载
```

### 6.3 对 API 的影响

```
POST /api/v1/query  →  返回 {job_id, status: "running"}
GET  /api/v1/jobs/{id} →  返回进度
GET  /api/v1/jobs/{id}/result → 返回数据
```

或者用 SSE 推送进度（你项目已经有 `/api/v1/query/stream`）。

**追问：用户关了页面怎么办？**

> "作业继续跑完写结果，前端再打开能查到。所以要有结果表 + 过期清理策略。"

## 七、你的三个故事（每个 2 分钟，必须能讲）

### 故事 1：元数据加工（证明你懂数仓）

```
背景：客户有一堆业务库，表名和字段名都很随意，AI 没法直接用
做法：用 Spark SQL 加工
      输入：information_schema + 数据字典 + 人工维护的口径表
      加工：关联清洗 → 聚合成元数据宽表（表/字段/指标/术语/权限）
      输出：落到配置和检索索引，供语义层消费
难点：大表 join 慢 → 分区裁剪 + 谓词下推 + 中间结果复用
价值：AI 有了"数据字典"，才能把口语映射到字段
```

### 故事 2：大表查询控制（证明你有成本意识）

```
问题：用户一句话就触发查询，可能扫几亿行
做法：
  ① 生成前：DSL 校验要求时间谓词
  ② 生成后：估算扫描量，超阈值拒绝
  ③ 执行前：LIMIT 10 预跑测耗时
  ④ 执行中：超时 kill
效果：贵查询在生成阶段就被劝退，而不是跑完才发现
```

### 故事 3：方言差异（证明你接过不止一种库）

```
问题：同一份 DSL 要在不同库上都能跑
做法：sqlglot 做方言转换 + AST 校验兜底
踩的坑：
  · 日期格式化各库不同（%Y-%m vs yyyy-MM）
  · Hive 整数除法是整除，要显式转 double
  · NULL 排序位置不同
验证：评测集里加多引擎用例，改一次跑一次
```

## 十、话术速查

| 被问 | 一句话 |
|---|---|
| 你们接什么数仓 | "开源版 MySQL/SQLite；数仓这块我做上游元数据加工，原生对接是我要补的" |
| AI 查哪一层 | "优先 DWD，明细可自由聚合；ADS 是给固定报表的，基本不碰" |
| 口径怎么保证一致 | "指标只存 alias，表达式从注册表取，模型猜的 field 会被忽略" |
| 会不会全表扫 | "DSL 校验层强制要求时间谓词，没有就拒绝——LIMIT 不减少扫描量" |
| 方言差异怎么办 | "sqlglot 转译 + AST 校验兜底 + 多引擎回归用例" |
| 大表 join 会爆吗 | "join 路径来自配置，不自由 join，限制深度，小表优先" |
| 成本怎么控 | "分区强制 + 扫描量估算 + 行数上限 + 超时 + 缓存 + 限流" |
| 数仓为什么要异步 | "Hive 提交作业分钟级，同步接口一定超时，必须 job_id + 轮询" |
| 权限怎么落地 | "应用层 DSL 注入 + 数据层 Ranger/RLS 兜底，双保险" |
| 数据延迟怎么办 | "查最新分区，超出数据范围直接告诉用户，而不是返回空结果" |

## 十一、一句话总结

> **data agent 岗的大数据问题，考的是"你知不知道自己在对什么系统发查询"。**
> 知道数仓分层（该查哪层）、知道分区裁剪（成本从哪漏）、知道方言差异（为什么换个库就崩）、知道异步模型（为什么接口会超时）——**这四件事讲清楚，就够了**。
