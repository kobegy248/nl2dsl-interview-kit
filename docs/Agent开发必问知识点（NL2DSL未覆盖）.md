## 一、记忆系统 Memory（⭐⭐⭐ 必问）

### 是什么

Agent 的"记忆"分三层，和 NL2DSL 的 checkpointer 是两回事：

| 记忆类型 | 存什么 | 怎么实现 | 生命周期 |
|---------|--------|---------|---------|
| 短期记忆 | 当前对话历史 | 塞进上下文窗口 | 一次会话 |
| 长期记忆 | 跨会话的用户画像、偏好、历史结论 | 向量库检索后注入 | 跨会话 |
| 工作记忆 | 当前任务的中间结果、已完成的步骤 | 状态变量 / scratchpad | 一次任务 |

**关键区别：LangGraph 的 `InMemorySaver`（checkpointer）是"状态持久化"，用于中断恢复，不是"记忆"**——它只记录状态快照，不做检索、不做遗忘、不做跨会话复用。

### 面试怎么问

- "你们 Agent 怎么做多轮对话记忆？"
- "长期记忆怎么实现？怎么更新、怎么防止记错？"
- "对话历史超长（超过上下文窗口）怎么办？"
- "记忆和 checkpointer 有什么区别？"

### 怎么答（要点）

- 短期记忆：滑动窗口 + 超长时摘要/截断；LangChain 有 `SummaryMemory`、`BufferMemory`。
- 长期记忆：把重要结论/用户偏好向量化存库，每次对话按相关性检索注入；要回答"写入时机、去重、过期、遗忘"。
- 工作记忆：LangGraph 的 state 本身就是工作记忆。
- 记忆的工程难点：**遗忘（遗忘策略）、一致性（新旧信息冲突）、隐私（记忆里存了什么敏感信息）**。

### 和简历的关系

NL2DSL 有 `InMemorySaver` + `/query/resume`（`engine.py:73`、`api_factory.py:1373`），这是**状态恢复**，不是记忆。面试要能说清区别，并能讲"如果要加多轮记忆，我会在 state 里加对话历史字段 + 用向量库存长期记忆，检索后注入 prompt"。

## 二、规划与反思范式（⭐⭐⭐ 必问）

### 是什么

Agent 的经典范式，NL2DSL 是"定制 pipeline"，不是这些标准范式：

| 范式 | 核心思想 | 一句话 |
|------|---------|--------|
| **ReAct** | Reasoning + Acting 交替 | "思考→行动→观察"循环，边想边做 |
| **Plan-and-Execute** | 先规划后执行 | 先列完整计划，再逐步执行 |
| **Reflexion** | 执行后反思 | 失败后反思教训，存进记忆，下次改进 |
| **Self-Refine** | 自我修正 | 对自己的输出反复 critique + 改进 |

### 面试怎么问

- "你用过 ReAct 吗？和你们项目的规划有什么区别？"
- "Plan-and-Execute 和 ReAct 各自适合什么场景？"
- "Agent 执行失败怎么自我反思和改进？"

### 怎么答（要点）

- ReAct：适合"探索型、步骤不确定"的任务；Plan-and-Execute：适合"步骤可枚举、依赖清晰"的任务，效率更高（少调用 LLM）。
- NL2DSL 的"意图识别→拆子查询→调度→聚合"更接近 **Plan-and-Execute** 思想，但它是**配置/规则驱动的确定性规划**，不是 LLM 自由规划——这是为了治理和可预期。
- Reflexion：把失败教训写回记忆，NL2DSL 的 `dsl_attempts` + 校验失败重试算一个**局部反思**的雏形（有重试有修正，但没有跨会话的记忆沉淀）。

### 和简历的关系

可以这样讲："我们的规划是确定性的 Plan-and-Execute 变体，用意图识别 + 规则拆子查询，而不是让 LLM 自由做 ReAct——因为查询场景强治理、强审计，自由规划会带来不可控。反思方面有 DSL 校验失败自动修正 + 执行失败降级重试。"

## 三、多智能体协作 Multi-Agent（⭐⭐⭐ 高频）

### 是什么

多个 Agent 分工协作，NL2DSL 是"单 Agent 编排 + Graph 执行"，不是多智能体系统。

| 协作模式 | 代表框架 | 特点 |
|---------|---------|------|
| 对话式（peer-to-peer） | AutoGen | Agent 之间直接对话、互相调用 |
| 角色分工（Role-based） | CrewAI | 每个 Agent 有角色+目标+任务 |
| 层级式（Supervisor） | LangGraph Supervisor | 一个 supervisor 分派给 worker |
| SOP 流水线 | MetaGPT | 模拟软件公司 SOP |

### 面试怎么问

- "你们是多 Agent 架构吗？"
- "多 Agent 怎么协调？怎么防止死循环和成本爆炸？"
- "什么场景需要多 Agent，什么场景单 Agent 就够？"

### 怎么答（要点）

- 核心要答：**多 Agent 的价值是"角色解耦 + 各自上下文隔离 + 并行"，代价是"通信开销 + 死循环 + token 成本倍增"**。
- 死循环防护：最大轮数、超时、无进展检测（连续 N 轮结果没变化就终止）。
- 判断标准：**任务能清晰拆成几个独立子任务且各自需要不同专业上下文 → 多 Agent；否则单 Agent + 工具就够**。

### 和简历的关系

NL2DSL 的"Agent 层（orchestrator + dispatcher）+ Graph 层"是**单 Agent 多子任务**，不是多 Agent。可以这样讲："我们是单 Agent 拆子查询并行执行的模式，比多 Agent 更可控；多 Agent 的 supervisor-worker 模式我理解，适合需要异构上下文隔离的场景。"——诚实区分，别把单 Agent 说成多 Agent。

## 四、大模型基础与微调（⭐⭐ 基础必问）

### 是什么

应用层岗位通常要求"了解原理，不一定要会训练"，但基础概念必须能答：

- **Transformer**：自注意力（self-attention）、Q/K/V、多头注意力、位置编码
- **微调**：SFT（全参监督微调）、LoRA（低秩适配，只训小矩阵）、QLoRA（量化+LoRA）、RLHF/DPO（对齐人类偏好）
- **推理优化**：量化（INT8/INT4）、KV cache、vLLM、投机解码

### 面试怎么问

- "讲讲注意力机制？"
- "LoRA 的原理？为什么能省资源？"
- "RLHF 和 SFT 什么区别？"
- "你们为什么用 API 而不自己微调？"

### 怎么答（要点）

- 注意力：每个 token 对序列里其他 token 求相关性权重（Q·Kᵀ），加权求和得到上下文表示。
- LoRA：冻结原模型权重，在旁路加低秩矩阵（A·B），只训练 A/B，参数量从百万级降到几十万，可插拔。
- RLHF vs SFT：SFT 学"模仿好答案"，RLHF 用奖励模型学"人类偏好排序"，后者对齐更强但更复杂、不稳定。

### 和简历的关系

你是**纯应用层**（调 API、Prompt、Agent 编排），没有微调经验。面试要诚实："我做的是应用层落地，微调了解原理（LoRA/RLHF）但没实际训练过；选 API 是因为业务场景强调快速迭代和可控，微调的必要性在于……"——**别假装做过训练**。

## 五、高级 RAG（⭐⭐ 高频）

### 是什么

NL2DSL 是"基础 RAG"（embedding 召回 + 关键词 + reranker），高级 RAG 技术没覆盖：

| 技术 | 解决什么问题 |
|------|-------------|
| **查询改写 Query Rewriting** | 用户问得模糊 → 改写/扩展成更利于检索的 query |
| **HyDE** | 先用 LLM 生成"假设答案"，用假设答案的 embedding 检索（缓解 query-doc 语义鸿沟） |
| **多路召回 + RRF 融合** | 向量 + 关键词 + 结构化多路召回，用 Reciprocal Rank Fusion 融合排序 |
| **Graph RAG** | 知识图谱 + RAG，回答"全局性问题"（实体关系、多跳） |
| **Agentic RAG** | 用 Agent 决定"检索什么、检索几次、要不要改写" |

### 面试怎么问

- "检索召回率低怎么优化？"
- "HyDE 是什么？什么时候用？"
- "你们 RAG 是怎么评估的？"

### 怎么答（要点）

- 召回优化优先级：**查询侧（改写/扩展）→ 检索侧（多路召回 + rerank）→ 索引侧（chunk 策略、embedding 模型）**。
- RAG 评估三个维度：**上下文相关性（召回准不准）、答案忠实度（有没有幻觉）、答案相关性（有没有答对）**。
- NL2DSL 已有：多路召回（向量+关键词）+ BGE-Reranker，这是扎实的基础，高级部分（查询改写/HyDE/GraphRAG）是扩展方向。

### 和简历的关系

可以这样讲："我们做了向量+关键词混合召回 + BGE-Reranker 精排，把重排从 800ms 降到 80ms。查询改写、HyDE、Graph RAG 这些是后续可扩展方向，我理解原理但当前版本没引入，因为语义层的 Schema/指标召回已经通过治理配置保证了较高的召回质量。"

## 六、Agent 评估与 LLM-as-judge（⭐⭐ 高频）

### 是什么

NL2DSL 的评测偏"DSL 生成质量"，通用 Agent 评估还缺一块：

- **端到端任务成功率**：完整任务做对没（不是单步对）
- **轨迹评估 Trajectory Evaluation**：过程对不对，不只是结果对不对（中间步骤是否合理、有没有走弯路）
- **LLM-as-judge**：用 LLM 给结果/过程打分（省人工，但需防 judge 偏差）

### 面试怎么问

- "你们怎么评估 Agent 质量？"
- "LLM-as-judge 靠谱吗？怎么防止 judge 本身有偏？"
- "评估只看最终结果够吗？"

### 怎么答（要点）

- 评估要拆两层：**最终结果正确 + 过程轨迹合理**。只看结果会漏掉"结果碰巧对但过程错"的情况。
- LLM-as-judge 的坑：**位置偏差（偏爱靠前的答案）、长度偏差（偏爱长答案）、自我偏好（偏爱自己模型风格）**。缓解：给 judge 明确 rubric、多 judge 投票、和人工标注校准。
- 项目里 `confidence.py` 的"LLM 判断 DSL 是否回答问题"是 **LLM-as-judge 的一个雏形**（用在置信度评分，不是评测）——可以当桥梁讲。

### 和简历的关系

可以这样讲："我们有 4 类 12 维度的评测体系（Semantic/Planning/Execution/Governance），覆盖了 DSL 质量到治理合规；LLM-as-judge 的思想我在置信度模块里用过（让 LLM 判断 DSL 是否回答了问题）。轨迹评估和多 judge 投票是进一步的方向。"

## 七、安全与护栏 Guardrails（⭐⭐）

### 是什么

NL2DSL 的"SQL 扫描 + 权限"是针对**查询安全**的护栏，LLM 通用安全没覆盖：

- **提示注入 Prompt Injection**：用户/检索内容里藏指令，劫持 LLM（直接注入=用户输入，间接注入=检索到的文档里藏指令）
- **越狱 Jailbreak**：绕过安全限制
- **输出护栏 Output Guardrails**：对 LLM 输出做校验/拦截（内容安全、格式校验、危险操作拦截）

### 面试怎么问

- "你们怎么防提示注入？"
- "RAG 检索到的内容被注入了怎么办？（间接注入）"
- "LLM 输出怎么保证安全？"

### 怎么答（要点）

- 分层防线：**输入侧**（清洗用户输入、隔离指令与数据）+ **检索侧**（对召回文档做可信度/来源校验）+ **输出侧**（输出护栏，校验格式/内容/危险操作）。
- 关键认知：**LLM 无法可靠区分"指令"和"数据"，所以安全不能只靠 prompt，要靠系统层约束**。
- NL2DSL 的 SQL 扫描/沙箱/权限注入**本质就是"输出护栏"**——不信任 LLM 的输出，系统层强制校验。这个思想可以直接迁移到 LLM 通用安全。

### 和简历的关系

可以这样讲："我们的安全哲学是'不信任 LLM 输出，系统层强制校验'——SQL 扫描、沙箱预检、权限注入都是这个思想的落地。这套'输出护栏'思路可以直接迁移到通用 LLM 安全：提示注入靠输入清洗和检索可信度校验，越狱靠输出护栏拦截。"

## 八、上下文工程 Context Engineering（⭐）

### 是什么

- **上下文窗口管理**：长对话超窗口时的截断/摘要/滑窗策略
- **上下文压缩**：把冗长历史压缩成摘要，节省 token
- **Prompt Cache**：缓存稳定的前缀（system prompt、工具定义），省 token 省延迟

### 面试怎么问

- "上下文超长怎么办？"
- "怎么降低 prompt 成本？"

### 怎么答（要点）

- 超长处理：滑动窗口（丢最早）+ 摘要（LLM 压缩）+ 检索式（只取相关历史）。
- Prompt cache：把 system prompt、few-shot 例子、工具定义放前面固定不动，缓存命中后增量 token 大幅减少。
- NL2DSL 可迁移：system prompt（DSL_SYSTEM_PROMPT）+ 治理配置注入都是"稳定前缀"，天然适合 cache。

## 九、成本与延迟优化（⭐）

### 是什么

- **模型路由 Model Routing**：简单问题用小模型，复杂问题用大模型
- **批处理 / 并发**：独立子任务并行
- **缓存**：prompt cache、结果缓存

### 面试怎么问

- "怎么降低 LLM 成本和延迟？"
- "你们 reranker 那 800ms→80ms 是怎么做到的？"

### 怎么答（要点）

- NL2DSL 已有两个降本案例可讲：**① BGE-Reranker 替代 LLM 粗排（800ms→80ms，成本降 90%）**；**② 子查询并行执行（asyncio.gather）**。
- 模型路由是扩展方向：简单意图（如"查销售额"）走规则生成器/小模型，复杂意图才走大模型——项目里 `generator_mode`（rule/llm）已经预留了这个切换点。

## 学习优先级建议

| 优先级 | 模块 | 理由 |
|--------|------|------|
| **第一梯队（必背）** | 记忆、规划反思、多智能体 | Agent 岗几乎必问，且项目完全没覆盖，最容易露怯 |
| **第二梯队（重点补）** | 大模型基础、高级 RAG、Agent 评估 | 基础必问 + 高频追问 |
| **第三梯队（能答要点即可）** | 安全护栏、上下文工程、成本优化 | 中频，且项目里已有可迁移的经验（SQL 护栏、reranker 降本） |

**三条纪律（和主文档一致）：**
1. 项目没做的，**诚实说没做 + 讲清原理 + 给出设计思路**，别冒充。
2. 微调/训练类经验，你是应用层，**明确说"了解原理未实操"**。
3. 每个盲区都要能"借项目的桥"讲——记忆借 checkpointer、反思借 dsl_attempts、LLM-as-judge 借 confidence.py、安全借 SQL 护栏，这样盲区也能落回你的真实项目。
