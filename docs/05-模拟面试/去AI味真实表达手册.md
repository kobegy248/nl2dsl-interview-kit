# 去 AI 味：真实表达手册

> **问题**：背得太熟、结构太工整、词太书面，面试官一听就知道是准备好的稿子。
> **目标**：听起来像一个**刚从这个项目里走出来的人**在聊自己干过的事，而不是在朗读文档。
>
> **用法**：先看第一节认出自己有哪几种"AI 味"，再按第二节的对照改口，最后用第六节录音自检。

---

## 一、面试官怎么识别"背的"（10 个特征）

对着自查，中 4 条以上就危险了。

| # | 特征 | 具体表现 |
|---|---|---|
| 1 | **结构太工整** | "首先…其次…最后…"，每段长度差不多 |
| 2 | **词太书面** | 赋能、闭环、抓手、颗粒度、沉淀、对齐 |
| 3 | **句子全完整** | 没有停顿、没有重复、没有自我修正 |
| 4 | **什么都对** | 每个决策都英明，没有一次判断失误 |
| 5 | **金句太密** | 每句都想让人记住，反而假 |
| 6 | **没有具体名词** | 全是"系统""模块""能力""方案"，没有"orders 表""那个报错" |
| 7 | **情绪太平** | 讲事故也像念报告，没有"当时挺慌的" |
| 8 | **从不犹豫** | 难题也秒答，像提前知道题目 |
| 9 | **过渡词书面** | "综上所述""总的来说" |
| 10 | **没有废话** | 真人有口头禅、有"怎么说呢" |

## 二、五条最有效的改写原则

### 原则 1：把"首先其次最后"换成"最早→后来→所以"

**AI 味**：

> "首先，我将架构重构为两层；其次，通过 DSL 实现了可校验；最后，系统通过了审计。"

**人话**：

> "最早是让模型直接写 SQL 的。Demo 挺顺，一上生产就出事。后来我想明白了，问题不在模型，在我们把'想查什么'和'怎么查'混一块了。所以中间加了一层 DSL。"

**差别**：时间线代替逻辑线。人讲事情是按时间顺序讲的，不是按论点顺序。

---

### 原则 2：抽象名词换成具体场景

| 别这么说 | 这么说 |
|---|---|
| "权限控制存在漏洞" | "用户 u001 能查到华南的数据" |
| "部分指标存在歧义" | "财务和运营说的'销售额'不是一个东西" |
| "响应延迟较高" | "P95 二十秒，用户点完没反应" |
| "检索效果不理想" | "问'客单价'，召回来的是'单价'" |
| "数据质量有问题" | "字段名叫 amt_01，注释是空的" |

**规律**：**具体名词 = 可信度**。说不出具体名字，听起来就是没真碰过。

---

### 原则 3：一定要有"当时的判断"和不完美

这是最有效的一条。

```
完美版（假）：我发现是 A 问题，于是改成 B，解决了。
真人版（真）：我一开始以为是 A，查了两天才发现是 B。改完还有个小尾巴，C 又冒出来。
```

**三个必加的痕迹**：

| 痕迹 | 句式 |
|---|---|
| 走过的弯路 | "一开始我以为是…" |
| 反复 | "第一次没修好，第二次才…" |
| 不确定 | "这个数字我记得不太准，大概是…" |

---

### 原则 4：长短句混着来

AI 生成的句子长度很均匀。真人说话**短句多、偶尔一个长句**。

**AI 味**：

> "我在设计阶段就考虑到了权限注入的复杂性，因此采用了在 DSL 层进行行级过滤的方案，以确保权限控制的有效性。"

**人话**：

> "权限这块，我们是在 DSL 那层做的。行级过滤直接注进去。模型看不到这一层，所以它也绕不过去。"

**三个短句 + 一个中句**，节奏就活了。

---

### 原则 5：允许自己说"不知道"

AI 味最重的地方，就是**什么都懂**。

**参考句式**：

```
"这块我没做过，不敢乱说。但我的理解是…"
"这个我记得不太清了，好像是…"
"这个我不确定，得回去看下代码。"
"你说的是 XX 那个场景吗？如果是的话…"
```

**注意**：说"不知道"之后一定要接"但我知道什么"。**只承认不知道不接内容 = 真的不行。**

## 三、Before / After（全部用你的材料）

### 例 1：讲项目架构

**AI 味**：

> "我主导了 NL2DSL 系统的架构设计。首先，我将传统 NL2SQL 模式重构为两层架构；其次，通过 DSL 契约层实现了查询的可校验、可审计和可归因；最后，该系统成功通过了甲方安全审查，取数效率显著提升。"

**人话**：

> "这个系统最早是让大模型直接写 SQL。Demo 挺顺利，一上生产就出问题——它会编字段，还会绕权限。
> 我当时判断问题不在模型，是我们把'想查什么'和'怎么查'混在一起了。所以中间加了一层 DSL：模型只写'我要 GMV、按地区分'，剩下的交给系统。
> 改完这个，安全审计才过。取数也从 3 天变成 3 分钟。"

**改了什么**：

```
"首先其次最后"        → "最早…后来…所以"
"实现了可校验"        → "它会编字段，还会绕权限"
"效率显著提升"        → "3 天变成 3 分钟"
```

---

### 例 2：讲一个坑

**AI 味**：

> "在项目落地过程中，我们发现权限控制存在 fail-open 的风险，随后进行了针对性的优化，有效提升了系统的安全性。"

**人话**：

> "这个坑是我自己审出来的，挺低级的。
> 行级权限那段代码，我写的是查不到用户权限就直接放行——当时想法很朴素，就是别挡住人。
> 但安全上这等于没权限的人能看到全部数据。后来改成查不到就抛错。
> 挺容易犯的错，所以我后来定了个规矩：每条防护都得有'它真的会拦住'的测试。"

**改了什么**：

```
"存在 fail-open 的风险" → "查不到就直接放行"
"进行了针对性优化"      → "改成查不到就抛错"
缺"当时的动机"          → "想法很朴素，就是别挡住人"
```

---

### 例 3：回答"你们准确率多少"

**AI 味**：

> "我们的系统准确率达到了 90% 以上，处于行业领先水平。"

**人话**：

> "分情况。50 例全量跑下来是 69.7%，子集能到 86% 左右。
> 差在哪我清楚——多表 join 和术语歧义是两个主要瓶颈。
> 所以我不太愿意报一个笼统的准确率，那个数意义不大。"

**为什么这个版本更强**：

```
AI 味版本：数字漂亮，但面试官会想"真到 90% 了？"
人话版本：主动报低数，反而建立信任——"这人不会吹"
```

---

### 例 4：讲技术取舍

**AI 味**：

> "在方案选型上，我们综合考虑了多种因素，最终选择了 DSL 方案，因为它具有更好的可治理性。"

**人话**：

> "当时有三条路：微调模型、让 Agent 自己调 SQL 工具、或者加一层 DSL。
> 前两个我都否了。微调解决不了权限问题，换个客户还得重训；让模型自己调 SQL，等于把执行权交出去，出事没法归因。
> 所以选了 DSL——代价是模型不能随便写复杂逻辑了，但换来可校验。"

**关键差别**：**必须说"我否掉了什么"**。只说"最终选择了 X"听起来像别人定的。

---

### 例 5：讲失败

**AI 味**：

> "项目初期遇到了一些挑战，但通过团队努力最终克服了困难。"

**人话**：

> "第一版其实失败了。评测 95%，我们以为可以上了，结果业务方试用一周说一半答不对。
> 后来查出来，评测集是我自己照着系统能力出的题——我先知道注册表里有什么，再出题，那当然好答。
> 改成从线上审计表抽真实问句，分数一下掉到 70% 以下。虽然难看，但那才是真的。"

**为什么这个版本强**：**没人会在失败上讲得这么细，所以一细就真。**

## 四、禁用词表 vs 可用口头禅

### 禁用（一听就是 PPT 或 AI）

| 禁用 | 换成 |
|---|---|
| 赋能 | 帮他做成了 X |
| 闭环 | 从头到尾跑通了 |
| 抓手 | 从 X 入手 |
| 颗粒度 | 切到多细 |
| 对齐 | 先说清楚 / 商定 |
| 沉淀 | 写成了文档 / 留下来了 |
| 打法 | 做法 / 思路 |
| 底层逻辑 | 根本原因 |
| 组合拳 | 几个手段一起上 |
| 生态 | （基本没场景需要说） |
| 综上 / 总的来说 | （直接结束，不用过渡） |

### 可以少量用（技术行话，工程师本来就这么说）

```
链路、埋点、回放、兜底、防抖、幂等、灰度、打平、跑通、卡住、崩了
```

> 注意区分：**技术行话可以用**（显得是内行），**管理黑话要删**（显得在背 PPT）。

### 可用的口头禅（少量）

```
"其实"        "说实话"        "怎么说呢"
"反正"        "就"            "然后"
"这个"        "当时"          "后来"
```

**频率控制**：一句话里最多一个。全篇每句都有 = 变成了新的 AI 味。

## 五、节奏：停顿、语速、留白

### 三个具体的停顿技巧

| 场景 | 怎么做 |
|---|---|
| **被问难题** | 先说"这个我想一下"，停 2 秒再答——**秒答反而像背的** |
| **讲完关键判断** | 停 1 秒，看对方反应——留给对方追问的窗口 |
| **讲到坑的时候** | 稍慢一点，加一句"当时挺意外的" |

### 语速

```
讲架构：中速，稳
讲坑：  稍慢，像在回忆
讲数字：稍快，干脆
反问：  放慢，显得在认真想
```

### 留白

**别一次把话讲满。** 讲完一个判断，停下来看对方的眼睛——如果他想问，让他问。这比你把所有细节一次性倒完要好。

## 六、三个高频问题的"人话版"

### Q："你最大的技术挑战是什么？"

**别答**："本系统的核心技术挑战在于……"（AI 味）

**这么答**：

> "最难的其实是权限。不是技术上难，是它牵涉面太广——模型生成的东西要能被权限拦住，还得让人看得懂为什么拦。
> 我们绕了好几版才定下来在 DSL 层做。中间还踩了个坑，我自己的代码是 fail-open 的。"

---

### Q："如果让你重做一遍？"

**别答**："我会在架构上做更完善的规划。"（空话）

**这么答**：

> "两件事。
> 第一，一开始就建评测集。我中途才建，前面改了很多次都是凭感觉，浪费不少时间。
> 第二，工具调用第一版就该做进去，让模型能自己确认字段存不存在，而不是等校验失败再修。"

---

### Q："你有什么问题问我？"

**别答**："没有了，谢谢。"（浪费机会）

**这么答**：

> "两个。
> 一是这个岗位现在最大的技术难题是什么？
> 二是团队里 AI 和数据的边界怎么划？我之前的项目是自己两头都做，想了解下这边怎么分工。"

---

## 七、录音自检清单（6 条）

录一遍你的 2 分钟版本，然后对着听：

```
□ 1. 有没有出现"首先/其次/最后"？        → 有就换成时间线
□ 2. 有没有"赋能/闭环/抓手"？             → 全删
□ 3. 有没有说"我一开始以为是…"？          → 没有就加一句
□ 4. 句子里有没有具体名词（字段名/报错/时间）？ → 全是抽象词就重写
□ 5. 句子长度是不是都很均匀？              → 改成长短交错
□ 6. 有没有一处说"我不太确定"？            → 没有就加
```

**中 3 条以上，重录一遍。**

## 八、一个反直觉的结论

> **去 AI 味，不是"讲得差一点"，是"讲得像有个人在里面"。**

具体就是三件事：

```
① 有时间线（最早/后来/现在），不是有论点和论据
② 有具体名词（字段名、报错文本、几点钟），不是有抽象概念
③ 有不确定和走错过，不是有完美答案
```

**记住一句话**：**你不需要证明自己没犯过错，你需要证明自己犯过错还把它修好了。**

## 九、最后：什么时候"AI 味"反而是优点

有些场合需要结构化表达：

| 场合 | 要不要结构化 |
|---|---|
| **系统设计题**（画图讲架构） | ✅ 要，结构清楚是加分 |
| **自我介绍** | 🟡 半结构（有主线，但别分点） |
| **讲项目经历** | ❌ 不要，按时间线讲 |
| **讲坑和失败** | ❌ 绝对不要，越像聊天越好 |
| **回答"你怎么看 X"** | 🟡 可以先给结论再展开 |

> **一句话**：**讲"发生过的事"用叙事，讲"怎么设计"用结构。**
