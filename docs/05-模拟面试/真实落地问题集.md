# 真实落地问题集（面试讲"坑"用）

> **为什么需要这份**：面试官判断"你是不是真做过"的核心手段，不是听你讲架构，是**问你踩过什么坑、当时怎么判断的、最后怎么修的**。
> 架构讲得再漂亮，没有事故故事 = 听起来像背的。
>
> **用法**：每个坑按「现象 → 当时的判断 → 真正原因 → 怎么修 → 教训」讲，2 分钟内讲完一个。
> **诚实标记**：每个故事标了来源——`【线上】`是在生产/联调里遇到的，`【自查】`是我做代码审计时发现的。**别把自查说成线上事故**，被追问细节会穿。

---

## 0. 讲坑的四段式（这是标准结构）

```
① 现象：我当时看到什么异常
② 当时的判断：我以为是 X（← 这段最重要，暴露真实思考）
③ 真正原因：其实是 Y
④ 怎么修 + 教训
```

**为什么"当时的判断"必须有**：如果你说的每句话都是对的，那不是经历，那是文档。**真实的经历里一定有"我猜错了"这一段。**

## 一、冷启动期

### 坑 1：业务方说"销售额"，但三个部门三个定义

**【线上】**

**现象**：系统上线第一周，财务说"你算的销售额比我们报表少了 8%"。

**当时的判断**：我以为是 SQL 写错了，或者数据同步延迟。

**真正原因**：财务的"销售额"= 含运费不含退款；运营的"销售额"= 支付金额；业务的"销售额"= 下单金额未扣优惠。**三个部门说的不是同一个指标，但都叫"销售额"。**

**怎么修**：不是改代码，是**建立"指标注册表 + 口径负责人"制度**——每个指标必须写明表达式、口径说明、负责人。系统只认注册表，不认"销售额"这个词。

**教训**：

> **问数系统最大的敌人不是模型幻觉，是业务口径不一致。** 技术能解决"映射"，解决不了"三个部门各说各话"。所以我把"口径治理"当成产品能力做，不是当成配置项。

**能证明的能力**：业务理解、治理意识、知道技术边界在哪。

---

### 坑 2：字段名全是 `amt_01`、`flag_a`

**【线上】**

**现象**：RAG 召回率极低，问"华东销售额"，召回到的是一堆无关字段。

**当时的判断**：以为 embedding 模型不行，差点去换模型。

**真正原因**：客户的表字段名是 `amt_01`、`amt_02`、`flag_a`，**没有注释**。向量化的文本本身就没有语义，换什么模型都没用。

**怎么修**：先在数据侧补语义——用 Spark 跑字段画像（空值率、基数、样本值），再让 LLM 猜字段含义生成候选注释，**人工只做确认**。注释补上之后，召回率立刻就上来了。

**教训**：

> **RAG 的效果上限由"被索引的文本有多好"决定，不是由模型决定。** 检索不准的时候，先看你的文本里有没有语义，别急着换 embedding。

**能证明的能力**：知道"数据质量决定模型效果"、会用 Spark 做画像。

## 二、生成质量

### 坑 3：模型编了一个不存在的字段

**【线上】**

**现象**：生成的 SQL 报 `Unknown column 'gmv_amount'`。

**当时的判断**：以为是数据库 schema 变了。

**真正原因**：模型把 `gmv` 和 `sales_amount` 两个指标名混在一起，编出了 `gmv_amount`。

**怎么修**：三重约束

```
① prompt 里塞可用指标清单（但清单会漏）
② 生成后白名单校验：alias 必须在注册表里，否则报错
③ 校验失败后带错误信息重试，最多 3 次
```

**教训**：

> **不能靠 prompt 让模型"不要编"，要靠校验让它"编了也没用"。**
> 这是我把架构从"直接生成 SQL"改成"生成 DSL + 校验"的最初动因。

**能证明的能力**：约束设计思想（这是 P7 叙事的核心）。

---

### 坑 4：JSON 解析失败——模型加了 markdown 代码块

**【线上】**

**现象**：偶尔报 `JSONDecodeError`，日志里看到模型返回：

````
```json
{"data_source": "orders", ...}
```
````

**当时的判断**：以为是温度太高，把 temperature 从 0.1 调到 0。

**真正原因**：温度不是根因，是**输出格式没有强约束**。模型看到 prompt 里有代码块示例，就学着加了代码块。

**怎么修**：两层

```
① 用 strict json_schema（response_format）从协议层约束输出
② 兜底：正则剥掉 ```json 包裹再解析
```

**教训**：

> **能靠协议约束的，不要靠 prompt 提醒。** 结构化输出要用 schema，不是靠"请你只输出 JSON"。

**能证明的能力**：懂结构化输出机制、有分层兜底意识。

---

### 坑 5：SQL 语法全对，但语义错了——"最近 7 天"

**【线上】**

**现象**：用户说"最近 7 天销售额"，系统算出 5 天的数据，用户投诉。

**当时的判断**：以为是数据延迟（数据只到 T-1）。

**真正原因**：模型把"最近 7 天"解析成了 `today-7 到 today`，但数据只到今天早上 8 点，**当天数据不全**。业务方期望的是"含今天在内的最近 7 个完整日"。

**怎么修**：把时间解析从"模型自由发挥"变成"确定性计算"——"最近 N 天"由代码按业务规则算，模型只负责识别"这是最近7天"这个意图。

**教训**：

> **凡是能被规则确定的，不要让模型算。** 时间、金额换算、分页这类，模型容易算错但代码不会。

**能证明的能力**：知道"哪些该交给模型、哪些该用代码"。

## 三、检索与上下文

### 坑 6：jieba 把"客单价"切成了"客/单价"

**【线上】**

**现象**：用户问"各品类的客单价"，召回到的是"单价"相关指标，答非所问。

**当时的判断**：以为是术语表没配 `客单价` 这个别名。

**真正原因**：术语表配了，但**分词先把"客单价"切碎了**，切成了"客"+"单价"，匹配时自然命中的是"单价"。

**怎么修**：启动时把注册表里所有实体名**动态灌进 jieba 自定义词典**（`add_word` + 高频权重），保证业务词不被切碎。

**教训**：

> **中文检索的第一个坑永远是分词，不是向量。** 术语表配了没用，因为它在分词之后才生效。

**能证明的能力**：做过真实中文检索、知道 pipeline 顺序的重要性。

---

### 坑 7：召回全部被阈值过滤，系统退化成随机结果

**【线上】**

**现象**：某些查询的上下文里一条指标定义都没有，但链路没报错。

**当时的判断**：以为是向量库挂了。

**真正原因**：精排阈值设了 0.5，但对这类短查询，**reranker 打分普遍在 0.2–0.4**——全部被过滤掉，触发了"空召回回退 top3"分支，拿回来的是按原始顺序的前 3 条（基本随机）。

**怎么修**：两个动作

```
① 加监控：回退触发率（当时发现高达 35%）
② 阈值不拍脑袋，用标注集扫一遍分数分布，取分位数
```

**教训**：

> **任何"兜底分支"都必须被监控。** 兜底默默生效的时候，系统看起来正常，实际已经失效了。
> 我后来把"回退率"做成看板指标，健康区间是 5%–15%。

**能证明的能力**：知道兜底不是万能、有监控意识。

---

### 坑 8：召回 10 条，只有 1 条有用，把真正的定义挤出预算

**【线上】**

**现象**：明明能召回到 `gmv` 的定义，但模型还是选错指标。

**当时的判断**：以为模型不听话。

**真正原因**：`build_context` 有 4000 字符预算。前面塞了 9 条低相关结果，**`gmv` 那条排第 10，被预算裁掉了**——模型根本没看到。

**怎么修**：

```
① 提阈值，减少低相关结果
② 调整组装顺序：terms（术语）优先级最高，schema 次之，history 最后
③ 超预算时按 section 逐条减，而不是截字符串
```

**教训**：

> **"召回率"高不代表"模型能看到"。** 预算是硬约束，垃圾会挤掉有用信息——所以 Precision 在预算紧的场景里和 Recall 一样重要。

**能证明的能力**：理解上下文预算、会做优先级设计。

## 四、权限与治理

### 坑 9：租户隔离失效——用户不在权限表里，直接放行

**【自查】**

**现象**：代码审计时发现，行级权限注入的逻辑是：

```python
user_perm = self._permissions.get(user_id)
if not user_perm:
    return dsl          # ← 没查到权限，原样返回
```

**当时的判断**（写这段代码时）：想着"没配置权限的用户，就当他是管理员吧，别挡住他"。

**真正原因**：**这是 fail-open（默认放行），安全设计上必须 fail-closed（默认拒绝）**。任何一个未登记的用户都能看到全量数据。

**怎么修**：

```python
if not user_perm:
    raise PermissionError(f"用户 {user_id} 未配置数据权限")
```

**教训**：

> **安全相关的默认值只有一个方向：拒绝。** 写"没查到就放行"的时候，等于给系统开了个后门。

**能证明的能力**：有安全直觉、会做代码审计。**这个坑非常适合主动讲**——它证明你会审查自己的代码。

---

### 坑 10：两条治理规则写了三个月，一次都没生效

**【自查】**

**现象**：做安全审计时发现，`governance.py` 里两条 `is_fatal=True` 的规则（敏感字段越权、指标未授权）**从来没触发过**。

**当时的判断**：以为是没有测试用例覆盖。

**真正原因**：**配置键不匹配**。代码读 `permission_config.get("sensitive_fields")`，但 `permissions.yaml` 里写的是 `sensitive_columns`——永远取到空字典，规则直接 `return no_issue`。

**怎么修**：统一配置键名，并加一条单测：**构造一个命中敏感字段的 DSL，断言规则抛错**。

**教训**：

> **"写了防护"和"防护生效"是两件事。** 每一条安全规则都必须有"它真的会拦住"的测试，否则就是自我安慰。

**能证明的能力**：严谨性、会写"验证防护有效"的测试。这个坑很高级，大多数候选人讲不出来。

---

### 坑 11：敏感字段从 metrics 绕过了列级检查

**【自查】**

**现象**：列级权限只检查 `dsl.dimensions`，但敏感字段如果写在 `metrics` 或 `filters` 里，就完全不被检查。

**当时的判断**：以为"敏感字段都是维度"。

**真正原因**：`salary` 这种字段既可能是维度，也可能是 `SUM(salary)` 这种度量，还能写进过滤条件。**只查 dimensions 等于漏了两条路。**

**怎么修**：检查范围扩到 `metrics[].field` / `filters[].field` / `order_by[].field`。

**教训**：

> **安全检查要问"还有哪些入径"，而不是"我检查了主路径"。** 攻击者永远走你没检查的那条路。

**能证明的能力**：威胁建模意识。

## 五、性能与成本

### 坑 12：一次查询三次 LLM 调用，P95 到 20 秒

**【线上】**

**现象**：用户抱怨"点了没反应"。压测发现 P95 延迟 20 秒。

**当时的判断**：以为是数据库慢。

**真正原因**：拆解耗时发现——生成 DSL 一次（3s）+ 置信度打分一次（2s）+ 结果自检一次（3s）+ 生成解释一次（2s），**光 LLM 就 10 秒**，加上精排和 SQL 执行。

**怎么修**：

```
① 非关键路径异步化：解释生成改成流式/后置
② 置信度打分合并进生成那次调用，不单独发
③ 精排从"逐条 CPU 推理"换成批量
```

**教训**：

> **LLM 应用要做"调用次数预算"**——每多一次调用，P95 就多几秒。设计节点的时候要问：这次调用能不能合并、能不能异步、能不能省掉。

**能证明的能力**：性能归因、成本意识（这是后端背景的优势）。

---

### 坑 13：生成的 SQL 扫全表，把数据库打满

**【线上】**

**现象**：某天下午数据库 CPU 100%，排查发现是问数系统的一条查询。

**当时的判断**：以为是并发太高。

**真正原因**：模型生成的 SQL **没有时间过滤条件**，`orders` 表几千万行全表扫。而且这类查询失败后会自动重试，形成雪崩。

**怎么修**：四道约束

```
① DSL 层强制要求时间谓词（没有就拒绝生成）
② 生成 SQL 后估算扫描行数，超阈值拒绝
③ 执行前 LIMIT 10 预跑，超时直接 kill
④ 失败不自动重试（避免雪崩）
```

**教训**：

> **让大模型写查询，最贵的不是 token，是"它不知道代价"。** 所以成本控制必须在系统层，不能在 prompt 层。

**能证明的能力**：成本控制、系统级防护。

## 六、评测与上线

### 坑 14：改了一个 prompt，其他用例全线崩

**【线上】**

**现象**：为了让"客单价"识别更准，改了一段 prompt，结果上线后"地区筛选"的准确率从 90% 掉到 60%。

**当时的判断**：以为改动只影响相关场景。

**真正原因**：**没有任何回归测试**——每次改 prompt 都是手工试几个 case 就上线。

**怎么修**：建评测集 + 回归门禁

```
① 固话 50 条用例（覆盖术语/多维度/时间/join/权限）
② 每次改动跑全量，输出对比报告
③ 关键维度下降超阈值 → 非零退出，阻断发布
```

**教训**：

> **LLM 应用改 prompt 就是改代码，但没有编译器帮你检查。** 所以评测集不是"加分项"，是替代编译器的必需品。

**能证明的能力**：工程严谨性、把 AI 当软件工程做。

---

### 坑 15：评测集自己造的数据，测出 95%，上线只有 60%

**【线上】**

**现象**：上线前评测 95%，业务方试用一周说"一半都答不对"。

**当时的判断**：以为是模型不稳定。

**真正原因**：评测集是**我照着系统能力写的**（我先知道注册表里有哪些指标，再出题），所以天然好答。真实用户的问题来自业务场景，用词完全不同。

**怎么修**：评测集的来源改成"真实问句"——从审计表抽样线上问题，人工标注期望结果。

**教训**：

> **"自己出题自己考"必然高分。** 评测集必须来自真实分布，否则就是自嗨。
> 这也是为什么我现在坚持看"50 例全量 69.7%"这个数，而不是最好的那个子集。

**能证明的能力**：诚实、懂评测方法论。

---

### 坑 16：用户说"结果不对"，但复现不了

**【线上】**

**现象**：用户截图说数字不对，但同样的问句我再跑一次，结果是对的。

**当时的判断**：以为是用户看错了。

**真正原因**：**LLM 是非确定性的**。同一句话，两次生成可能选出不同的指标。而且没有记录当时的 trace，无法回溯到底哪次、错在哪。

**怎么修**：节点级 trace + query_id

```
记录每个节点的：输入、输出、耗时、状态、生成的 DSL、最终 SQL、错误码
用户报错 → 拿 query_id → 直接拉到那次执行的完整链路
```

**教训**：

> **LLM 系统的"可观测性"不是监控，是"能回放"。** 没有 trace 的 AI 系统，出问题只能靠猜。

**能证明的能力**：可观测性设计、线上排查能力（后端强项）。

## 七、协作与交付

### 坑 17：甲方安全审查要求"每一步可追溯"，系统当时没有

**【线上】**

**现象**：项目准备验收时，甲方安全团队要求提供"查询链路审计"，我们只能提供最终 SQL。

**当时的判断**：以为给个日志文件就行。

**真正原因**：安全审查要的是**"谁在什么时候、基于什么理解、生成了什么、被哪道闸门拦过"**——完整链路，不是最终结果。

**怎么修**：补全 trace（节点级）+ 审计台账 + query_id 贯穿。补完之后，反而成了产品的卖点。

**教训**：

> **在 To B 场景，"能不能审计"经常比"准不准"更决定项目成败。** 我在设计时把审计当"附加功能"，实际上它是交付前提。

**能证明的能力**：To B 交付经验、知道甲方的真实红线。

---

### 坑 18：业务方拿系统结果和报表对比，发现数字不一样

**【线上】**

**现象**：业务方说"你这个数跟我的报表差 5%"。

**当时的判断**：以为是我们算错了。

**真正原因**：**数据源层不同**。我们查的是 DWD 明细层，报表读的是 ADS 应用层——ADS 里有预聚合和口径修正。

**怎么修**：在界面上明确标注"数据来源层"，并给业务方一张"口径对照表"。

**教训**：

> **答不上"为什么和报表不一样"，就会失去信任——哪怕你算的是对的。** 后来我把"数据源说明"做成产品的一部分。

**能证明的能力**：数仓理解、产品意识。

| 13 全表扫 | 系统级成本控制 |
| 14 prompt 回归 | 工程严谨 |
| 15 自嗨评测 | **诚实 + 评测方法论** |
| 16 复现不了 | 可观测性 |
| 17 审计要求 | To B 交付 |
| 18 和报表不一致 | 数仓理解 + 产品意识 |

## 九、怎么讲（节奏与避坑）

### 一次只讲一个，按四段式，控制在 2 分钟

```
① 现象（20 秒）—— 讲具体数字或报错，别讲"遇到了一些问题"
② 当时的判断（20 秒）—— 必须有"我以为…"，这是真实感的来源
③ 真正原因（30 秒）—— 技术细节，体现深度
④ 怎么修 + 教训（50 秒）—— 教训要能抽象成一条原则
```

### 三个禁忌

| 禁忌 | 为什么 |
|---|---|
| **不给"当时的判断"** | 听起来像事后总结，不像亲历 |
| **每个坑都秒解决** | 真实项目里一定有反复试错 |
| **只讲别人的锅** | 至少要有一个"我写错了"的坑（坑 9、10、11） |

### 最推荐主动讲的两个

**坑 9（fail-open）** 和 **坑 10（规则空转）**——因为它们证明**你会审查自己的代码**，这个能力在高级岗里非常稀缺。

讲法示范：

> "做安全审计时我发现自己的行级权限逻辑是 fail-open 的——查不到用户权限时直接放行。当时写的想法是'别挡住用户'，但安全上这等于开了个后门。后来改成查不到就抛错。
> 更尴尬的是另一条：两条治理规则写了三个月一次都没触发过，因为代码读的配置键和 yaml 里写的名字不一样。所以我后来定了个规矩——**每一条防护都必须有'它真的会拦住'的测试**。"

## 十、面试官验证真假的三个套路（提前准备）

| 套路 | 他怎么问 | 你怎么接 |
|---|---|---|
| **问细节** | "那个字段叫什么名字？""报什么错？" | 能说出具体的报错文本、字段名 |
| **问反复** | "第一次修好了吗？" | 必须是"没有，第二次才…" |
| **问责任** | "这是你发现的还是别人告诉你的？" | 诚实说"我自查发现的"或"线上报警后我排查的" |

**核心**：**细节 + 反复 + 责任归属**。三个都能答上，就是真经历过。

## 十一、一句话总结

> **架构证明你会设计，坑证明你真的做过。**
> 高级岗的面试官，往往在你讲完第一个坑之后，就已经决定要不要你了。
