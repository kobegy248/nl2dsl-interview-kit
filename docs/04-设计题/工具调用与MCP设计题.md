# 工具调用与 MCP：面试官会怎么一路追问（未实现 · 问答版）

> **证据边界**：NL2DSL 里**没有任何工具调用实现**（全仓无 `bind_tools` / `ToolNode` / `tool_call`）。
> - 现在是编排型 Agent：LLM 做规划和生成 DSL，执行走固定 Graph。
> - 本文的 schema 设计、旁路方案、工具清单、MCP server，都是设计，没落地。
> - 已实现的编排能力见 [Agent 编排专项](../03-专项/Agent编排专项.md)。
> - 面试口径："没做，但我知道该怎么做、什么时候该做。"

**怎么用**：先背第 0 节的问题树，再逐问看。每一问都按「他真正想问什么 → 一句话怎么答 → 继续追怎么展开 → 别说错」写。

## Q1：你们 Agent 支持工具调用吗？

**他真正想问的**：你分得清"编排型 Agent"和"工具型 Agent"，以及会不会吹。

**一句话怎么答**：

> 没有。我们是编排型 Agent——LLM 只做规划和生成 DSL，执行走固定链路。这不是能力缺失，是安全选择：SQL 要过校验、权限、扫描、沙箱四道闸。

**他继续追时怎么展开**：

两种 Agent 的区别：

| 类型 | LLM 干什么 | 执行谁负责 | 适合什么 |
|---|---|---|---|
| 编排型 | 规划、拆解、生成 DSL | 固定 Graph | 高风险、强治理场景 |
| 工具型 | 自己决定调哪个工具 | 模型驱动循环 | 探索、元数据查询 |

我们的场景是查数，查错了代价大，所以把"决策"和"执行"分开。

**别说错**："我们支持 Function Calling。"——仓库里没有 `tool_call`，一问代码就露。

## Q2：工具调用到底是什么？模型会执行函数吗？

**他真正想问的**：你知不知道"模型只出意图，代码负责执行"这个本质。

**一句话怎么答**：

> 模型不执行函数，它只输出"我想调哪个函数、参数是什么"，真正执行的是你的代码。执行完把结果回传，模型再接着回答。

**他继续追时怎么展开**：

用点菜打比方：

```
顾客（用户）：宫保鸡丁怎么做的？
服务员（模型）：我不知道配方，但厨房有配方册
              → 在单子上写"查配方：宫保鸡丁"   ← tool_call
厨房（你的代码）：翻配方册，把配方写出来        ← 执行工具
服务员（模型）：把配方转述给顾客                ← 最终回答
```

**关键理解**：服务员不会做菜，模型不会执行函数。它只是"知道该找谁要什么"。

分工表：

| 环节 | 谁做 |
|---|---|
| 决定调不调、调哪个、传什么参数 | 模型（输出 `tool_calls`） |
| 执行函数、访问数据库 | 你的代码 |
| 把结果交回模型 | 你的代码（追加 `role: "tool"` 消息） |
| 根据结果生成最终答案 | 模型 |

**别说错**："模型会调用函数。"——它只会"申请"，不会"执行"。

## Q3：一次调用，消息怎么流转？为什么请求两次？

**他真正想问的**：你看没看懂日志里的四条消息。

**一句话怎么答**：

> 四步：用户问题 → 模型返回申请单（tool_calls）→ 代码执行并把结果作为 tool 消息回填 → 再请求一次，模型给最终答案。所以是"一来一回"，不是一次调用。

**他继续追时怎么展开**：

```
① user：GMV 是怎么算的？
② assistant：content=null，tool_calls=[{id:"call_1", name:"get_metric_definition", arguments:"{\"metric_name\":\"GMV\"}"}]
③ tool：tool_call_id="call_1"，content="GMV = 已支付订单金额之和…"
④ assistant：content="GMV 是所有已支付订单金额之和，含运费，不含退款。"
```

代码骨架：

```python
messages = [{"role": "user", "content": question}]
resp = client.chat.completions.create(model=..., messages=messages, tools=tools)
msg = resp.choices[0].message

if msg.tool_calls:
    messages.append(msg)                      # 申请单要原样存回历史
    for call in msg.tool_calls:               # ⚠ 可能不止一个
        args = json.loads(call.function.arguments)   # ⚠ 是字符串
        result = TOOLS[call.function.name](**args)
        messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    resp = client.chat.completions.create(model=..., messages=messages, tools=tools)
```

三个马上会踩的坑：

| 坑 | 说明 |
|---|---|
| `arguments` 是字符串 | 模型生成的是 JSON 文本，要 `json.loads` |
| 必须带 `tool_call_id` | 一次可能调多个，靠它对应申请和结果 |
| 可能一次调多个 | 用 for 循环，别写死 `[0]` |

**加分点**：第二次请求要把**完整历史**发过去（问题 + 申请 + 结果），少一段模型就不知道发生了什么。

**别说错**："发一次请求就能拿到答案。"——工具调用是循环。

## Q4：怎么让模型选对工具？

**他真正想问的**：你知不知道 schema 本质上是 prompt。

**一句话怎么答**：

> schema 就是写给模型看的说明书：名字用"动词_名词"，描述写清"什么时候用、什么时候别用"，参数尽量用枚举。写得越清楚，模型选得越准。

**他继续追时怎么展开**：

模型能看到的只有三样：`name`、`description`、`parameters`。**没有函数体、没有代码。**

反面教材：

```json
{"name": "metric_tool", "description": "指标工具", "parameters": {"q": {"type": "string"}}}
```

三个问题：名字看不出干嘛、描述没说什么时用、参数是自由字符串（模型会瞎编）。

正面教材：

```json
{
  "name": "get_metric_definition",
  "description": "查询指标的定义和计算方式。当用户问某个指标怎么算、口径是什么时使用。注意：只查定义，不查数值。",
  "parameters": {
    "type": "object",
    "properties": {
      "metric_name": {
        "type": "string",
        "enum": ["GMV", "销售额", "客单价", "客户数"],
        "description": "必须从枚举里选，不要自创"
      }
    },
    "required": ["metric_name"],
    "additionalProperties": false
  }
}
```

**最有效的一招：参数用 `enum`。** 模型物理上没法传一个不存在的指标名——这是防幻觉最便宜的办法。

**自检方法**：把 schema 给一个不懂你系统的同事看，问"用户问 X，该调这个吗"。他答对了，模型大概率也能；他答不出来，模型也答不出来。

**错误信息也是 prompt**：

```python
# ❌ 模型看不懂，只能重复犯错
return {"error": "KeyError"}
# ✅ 告诉它有什么可选，下一轮能自己改
return {"error": "指标「GMV金额」不存在", "available": ["GMV", "销售额", "客单价"]}
```

**别说错**："description 随便写写就行。"——模型就是靠这句话决定调不调的。

## Q5：一次要调多个工具怎么办？

**他真正想问的**：你知不知道并行和串行的区别。

**一句话怎么答**：

> 三种形态：单次、并行、串行。互不依赖就并行（省时间），下一步依赖上一步结果就串行（循环）。

**他继续追时怎么展开**：

| 形态 | 场景 | 模型行为 |
|---|---|---|
| 单次 | 调一个就够 | 返回 1 个 `tool_call` |
| 并行 | 多个互不依赖的查询 | 一次返回多个 `tool_call` |
| 串行 | 下一步依赖上一步 | 调一个 → 看结果 → 再调下一个 |

例子：用户问"GMV 和客单价分别怎么算的"，模型一次返回两个申请，代码可以并发执行，再一起回填。

**加分点**：并行时要注意——**每个结果都要带自己的 `tool_call_id`**，不能合并成一条。

**别说错**："所有工具都并行跑。"——有依赖的会拿错数据。

## Q6：循环怎么控制？手写还是用框架？

**他真正想问的**：你知不知道无限循环和成本失控。

**一句话怎么答**：

> 手写核心就 20 行：调模型 → 有 tool_calls 就执行回填 → 没有再返回。必须有步数上限，一般 5–10 步，超了就强制收口。

**他继续追时怎么展开**：

```python
def run(question, tools, max_steps=6):
    messages = [{"role": "user", "content": question}]
    for step in range(max_steps):
        resp = llm.chat(messages, tools)
        if not resp.tool_calls:
            return resp.content              # 模型不调了 → 结束
        messages.append(resp)
        for call in resp.tool_calls:
            messages.append(execute(call))
    return "达到步数上限，先给你目前查到的结果"
```

手写 vs 框架：

| | 手写 | 框架（LangGraph ToolNode 等） |
|---|---|---|
| 优点 | 透明、好调试、依赖少 | 省代码、有现成状态管理 |
| 缺点 | 要自己处理重试/审计/超时 | 黑盒多，出问题难查 |
| 适合 | 工具少、逻辑简单 | 工具多、要并行/中断/恢复 |

**为什么必须有上限**：模型可能反复调同一个工具，或者在错误方向试很多次。没有上限，线上会卡死，成本也会失控。

**别说错**："让模型自己决定调几次。"——它不知道你的账单。

## Q7：工具失败了怎么办？

**他真正想问的**：你有没有把工具当"一定会坏的外部依赖"。

**一句话怎么答**：

> 五个必须处理：超时、临时失败、重复执行、参数错误、查不到。原则是——返回给模型能看懂的错，不要裸抛异常。

**他继续追时怎么展开**：

| 情况 | 怎么处理 |
|---|---|
| 超时 | 每个工具独立超时，返回"超时，请换方式" |
| 临时失败 | 只对幂等工具重试，指数退避 |
| 重复执行 | 幂等键，写操作不自动重试 |
| 参数错误 | 服务端二次校验，不信模型传的值 |
| 查不到 | 审计日志，记录谁在什么时候调了什么 |

```python
async def call_with_timeout(tool, args, timeout_s=5.0):
    try:
        return await asyncio.wait_for(asyncio.to_thread(tool.invoke, args), timeout=timeout_s)
    except asyncio.TimeoutError:
        return {"error": f"工具超时（{timeout_s}s），请换个方式"}
```

**为什么返回而不是抛异常**：抛异常会中断整个循环；返回错误信息，模型还有机会换个策略。

**什么叫幂等**：调 1 次和调 3 次结果一样。查指标定义是幂等的，`create_report` 不是。

**加分点**：工具调用最容易成为审计盲区——查询链路有审计，但工具不走那条链路，不单独埋点出事查不到。

**别说错**："失败了重试三次。"——写操作重试三次就是重复下单。

## Q8：MCP 是什么？和 Function Calling 什么关系？

**他真正想问的**：你会不会把两个不同层的东西混为一谈。

**一句话怎么答**：

> MCP 是"工具即服务"的协议标准：把工具做成独立服务，谁想用就按统一协议调。和 Function Calling 是上下两层——FC 管模型怎么表达调用意图，MCP 管工具怎么被发现和接入。

**他继续追时怎么展开**：

类比 USB：

- 以前每个设备一个专用接口；
- 现在都插 USB，电脑不用管是谁。

MCP 就是 AI 工具界的 USB。工具按 MCP 实现后，Cursor、Claude Desktop、你自己的 Agent 都能直接用。

三个概念（图书馆类比）：

| 原语 | 是什么 | 类比 |
|---|---|---|
| tools | 可调用的函数 | 借书、还书 |
| resources | 可读取的数据 | 书架上的书 |
| prompts | 可复用的模板 | 馆员准备好的书单模板 |

做工具调用只需要关心 `tools`。传输方式两种：本地用 stdio（子进程），远程用 HTTP。

什么时候需要 MCP：

| 情况 | 要不要 |
|---|---|
| 工具只在自己一个应用里用 | 不需要，直接函数调用 |
| 要给 IDE、多个 Agent 共用 | 需要 |
| 想对外提供能力 | 需要 |
| 多个项目重复实现同样的工具 | 需要 |

**别说错**："MCP 就是 Function Calling。"——一个是协议，一个是模型输出格式。

## Q9：你的项目该把什么做成工具？

**他真正想问的**：你会不会什么都想做成工具。

**一句话怎么答**：

> 只做"只读、幂等、不越权、模型需要动态决定调不调"的元数据查询。第一梯队：查指标口径、查维度、查维度取值。

**他继续追时怎么展开**：

三个判断条件，全中才做：

```
① 只读、幂等
② 不经过 DSL 校验链（不是查询执行）
③ 模型需要"动态决定要不要调"，不是每次都必调
```

**第一梯队（零风险，先做）**：

| 工具 | 作用 | 为什么适合 |
|---|---|---|
| `explain_metric` | 查指标口径 | 用户常问"怎么算的" |
| `list_dimensions` | 查可用维度 | 生成前探路，减少校验失败 |
| `sample_values` | 查维度取值 | 确认"华东"对应什么编码 |

共同点：查的是**元数据**，不是数据。不涉及行级权限，天然安全，而且是纯内存字典查询，毫秒级。

**第二梯队（ROI 最高）**：

| 工具 | 一句话价值 |
|---|---|
| `check_data_freshness` | "数据到几号了"——空结果时用户第一反应 |
| `explain_term` | "流水和销售额有什么区别"——术语歧义是最大损失来源 |
| `search_columns` | "有没有跟金额相关的字段"——用户不知道字段名时的救星 |
| `dry_run` | "这条查得通吗"——让错误在生成阶段暴露 |

四个加起来约 2.5 天，比做 SQL 执行工具安全得多、价值也高得多。

**不该做成工具的**：SQL 执行、任何写操作（建报表、发通知）。

**别说错**："把查询能力做成工具，让模型自己查。"——那就是把四道闸拆了。

## Q10：为什么 SQL 执行不能做成工具？

**他真正想问的**：你懂不懂"可校验的中间层"值多少钱。

**一句话怎么答**：

> 因为 SQL 是模型生成的自由文本，没有可校验的中间层。DSL 链路每一环都能单独拦、单独审计；直接执行 SQL 就全没了。

**他继续追时怎么展开**：

假设做了：

```
模型 → tool_call: run_sql("SELECT ...") → 直接执行
```

四个问题：

| 问题 | 后果 |
|---|---|
| SQL 是自由文本 | 没有可校验的中间层 |
| 权限只能靠 SQL 层拦 | 不如 DSL 层注入精确 |
| 出错分不清理解错、生成错、执行错 | 无法归因 |
| 模型可以反复试错 | 成本不可控 |

而固定链路是：

```
DSL（可校验）→ 校验 → 权限注入 → 优化 → 构建 SQL → 扫描 → 沙箱 → 执行
```

每一环都能单独拦下来、单独审计。**这就是"Agent 自主"和"系统可控"的分界线。**

**别说错**："加个只读账号就安全了。"——只读防不了越权读。

## Q11：怎么接进现有系统？

**他真正想问的**：你会不会为了加工具把主链路改烂。

**一句话怎么答**：

> 走旁路：在 plan 后面分一条岔路，工具只在这个分支里跑，跑完回 decompose。不改主链路、可以随时关、坏了不影响查询。

**他继续追时怎么展开**：

```
plan ─┬─ continue ──────────────────────► decompose（原链路，一个字不动）
      │
      └─ explore ─► tool_agent ─┬─ 有 tool_call ─► tools ─┐
                                 │                       │
                                 └─ 没 tool_call ─► decompose
                                          ▲              │
                                          └──────────────┘（执行完回模型）
```

"旁路"的三层含义：

| 含义 | 表现 |
|---|---|
| 不改主链路 | decompose 往后所有节点、边、校验都不动 |
| 可以随时关 | 一个开关，关掉后退化成原来的图 |
| 坏了不影响主流程 | 工具分支任何异常 → 回 decompose，查询照常 |

失败分两级：

```
工具级失败 → 把错误回填给模型，让它换个做法，循环继续
旁路级失败 → 放弃工具，回主链路，查询照常进行
```

**关键细节**：旁路里的中间消息**不进主链路**，只把整理好的文本（metadata_context）传下去。否则主链路状态会被工具对话污染。

**别说错**："把 plan 改成工具调用。"——那是替换主链路，赌工具一定好用。

## Q12：工具怎么防越权？

**他真正想问的**：你信不信模型传进来的参数。

**一句话怎么答**：

> 两道关：工具级 RBAC，控制这个角色能调哪些工具；参数级白名单，enum 加服务端二次校验。不信模型传的任何值。

**他继续追时怎么展开**：

- **工具级**：不是所有用户都能调 `sample_values`——如果某个维度是敏感字段，这个工具对他就不可见。
- **参数级**：`enum` 只是"劝"模型别乱传，服务端必须自己再验一遍。
- **结果级**：工具返回的数据也要过滤——别把用户无权看的字段名返回给他。

**加分点**：工具的结果也是 prompt 的一部分，可能被间接注入。所以工具返回的内容要当作不可信数据处理。

**别说错**："schema 里写了 enum，模型就不会传错。"——模型仍然可能传错，服务端必须验。

## Q13：这些你们做了吗？

**他真正想问的**：你会不会把设计说成实现。

**一句话怎么答**：

> 没做。仓库里没有 `bind_tools`、没有 `ToolNode`、没有 `tool_call`。现在的执行是固定 Graph，LLM 只出 DSL。

**他继续追时怎么展开**：

如果问"那你会先做哪个"：

> 先做 `explain_metric` 一个工具，走旁路接进去。它只读、幂等、查的是内存里的注册表，风险最低，又能立刻回答"这个指标怎么算的"这类高频问题。跑顺了再扩到 `sample_values` 和 `dry_run`。

**别说错**："我们规划中。"——面试官要听"你知道怎么做"，不是"你在规划"。

## 名词解释（大白话）

| 词 | 大白话 |
|---|---|
| 工具调用 | 模型说"我要查 X"，你的代码去查，再把结果给它 |
| `tool_call` | 模型写的"申请单"：调哪个函数、传什么参数 |
| `tool_call_id` | 申请单编号，用来把结果和申请对上 |
| schema | 写给模型看的工具说明书 |
| enum | 参数只能从固定几个值里选 |
| 并行 / 串行 | 一次调多个 / 一个接一个 |
| 幂等 | 调一次和调三次结果一样 |
| MCP | 让工具能被很多应用共用的协议，像 USB |
| 旁路 | 在旁边分一条岔路，不替换主流程 |
| 元数据 | 描述数据的数据：表结构、口径、枚举值 |

## 考前 1 分钟

- **一句话**：模型负责想调什么，你的代码负责安全地执行。
- **四步消息**：user → assistant(tool_calls) → tool(tool_call_id) → assistant。
- **三个坑**：arguments 是字符串、必须带 id、可能多个调用。
- **schema 三要素**：名字、何时用、参数枚举。
- **三种形态**：单次、并行、串行；循环要有上限。
- **五个工程问题**：超时、重试、幂等、校验、审计。
- **MCP 一句话**：工具即服务的 USB 接口，和 FC 是上下两层。
- **该做与不该做**：元数据查询可以做，SQL 执行不能做。
