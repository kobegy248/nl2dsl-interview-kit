# 语义层冷启动：面试官会怎么一路追问（未实现 · 问答版）

> **证据边界**：这篇里的做法，项目里**一个都没做**。
> - 现在只有一个脚本 `scripts/init_semantic.py`：抽表名、字段名、注释，再按字段名里有没有 `_amount`、`_price` 猜指标，生成一份 YAML。
> - `docs/business/10-semantic-layer.md` 里写过"给注释打分、AI 补描述"——那也是设计稿，代码里没有。
> - 指标配置基本只有"怎么算"和"中文名"，没有"谁签的字""什么时候签的""拿什么验的"。
> - 面试口径："我知道该怎么做，当时没做，原因是……"

**怎么用**：先背第 0 节的问题树，再逐问看。每一问都按「他真正想问什么 → 一句话怎么答 → 继续追怎么展开 → 别说错」写。

 └─ Q10 这些你们做了吗？

## Q1：客户没有指标口径，你们系统还能用吗？

**他真正想问的**：你知不知道自己的系统有前提，会不会硬吹"什么都能接"。

**一句话怎么答**：

> 能用，但要降级用。我们消费治理成果，不生产治理成果——客户没有口径，我不硬上，而是按他手册的完整程度，提供不同程度的功能。

**他继续追时怎么展开**：

先打个比方：语义层就是一本《公司黑话手册》，左边写业务的话，右边写数据库怎么算。客户没有口径，就是**这本手册是空的**。

手册空着硬上，会发生什么？系统会自己编一本，然后当官方手册用。编错一条，后面所有引用它的报表全错，而且不报错、数字看着还挺合理。

所以分四档：

| 档位 | 客户什么样 | 我们提供什么 | 敢承诺什么 |
|---|---|---|---|
| L0 | 只有库，没注释没指标 | 找表、看样本、预览 SQL | 只保证查得到，不保证口径对 |
| L1 | 有表结构、有注释 | 单表/多表统计问答 | 答案里写明"这个数怎么算的" |
| L2 | 有一部分指标 | 签过字的承诺一致，没签字的标"草稿" | 签字的保证，没签字的提前说 |
| L3 | 指标齐全、有权限有审计 | 完整经营问答 | 口径一致、权限受控、能审计 |

一句话：**不是能不能用，是敢承诺到哪一步。**

**别说错**："我们什么库都能接，AI 自己会理解。"——一听就是没交付过。

## Q2：那你怎么帮他建？第一步做什么？

**他真正想问的**：你有没有可执行的路径，还是只会说"先做治理"。

**一句话怎么答**：

> 三步：先摸底，再让机器写草稿，最后拿真实问题让人签字。第一步不是写指标，是搞清楚客户手里有什么。

**他继续追时怎么展开**：

**第一步：摸底，1–2 天。**

| 看什么 | 说明白点 | 看到说明什么 |
|---|---|---|
| 表名、字段名、注释 | 数据库自带的说明书 | 注释多，机器猜得准一点 |
| 字典表、维表 | 比如地区表、状态码表 | 能把"华东"翻译成 `HD` |
| 历史 SQL、BI 报表 | 以前人怎么查数 | 最值钱，能反推真实算法 |
| 指标手册、Excel | 有没有写下来的口径 | 有就直接抄，省一半事 |
| 敏感字段 | 手机号、身份证 | 决定能不能开放明细 |

最后出一页纸，结论就一句：**当前是什么水平，能提供什么，不能承诺什么。**

**第二步和第三步**（下面两问展开）：机器写草稿 → 人签字。

**别说错**："让客户先自己把指标整理好。"——这是甩锅，面试官会认为你没有交付能力。

## Q3：指标从哪来？让 AI 生成吗？

**他真正想问的**：你知不知道 LLM 生成的口径不可信，以及更好的来源是什么。

**一句话怎么答**：

> 按靠谱程度排四个来源：库内元数据、历史 SQL、业务文档，最后才是 LLM。LLM 只负责"起名字、补描述"，不负责"定算法"。

**他继续追时怎么展开**：

| 来源 | 能拿到什么 | 靠不靠谱 |
|---|---|---|
| 库内元数据 | 维度、枚举映射、join 草稿 | 高，但只能得到"有哪些字段" |
| **历史 SQL / BI 报表** | 指标候选：表达式 + 维度 + 频次 | **最高**，表达式是人真用过的 |
| 业务文档 / 指标手册 | 指标定义、同义词 | 中，有就直接抄 |
| LLM 推断 | 字段描述、指标命名 | 低，只能当草稿 |

历史 SQL 怎么反推？说人话：

> 把以前的查询一条条拆开 → 看它用了哪个字段、怎么加总、按什么分组 → 一样的归成一类 → 出现次数多的排前面 → 变成"指标候选"，后面附一句"这条是从 137 次查询里总结出来的"。

这样业务方看到的是"你们平时都这么查，我整理成一条了"，而不是"AI 觉得销售额应该这么算"。前者他愿意看，后者他不敢信。

**别说错**："让 AI 读一遍表结构，指标就都有了。"——AI 读不出"含不含退款"。

## Q4：AI 生成的，怎么保证是对的？

**他真正想问的**：你有没有认证机制，还是生成完就直接用。

**一句话怎么答**：

> 草稿和正式的分开放，草稿永远不进正式回答；每条指标要有人签字，签字要留四个凭证。

**他继续追时怎么展开**：

**先隔离。** 两条铁律：

| 类型 | 放哪 | 系统回答时能用吗 | 能进正式报表吗 |
|---|---|---|---|
| 草稿 | 单独文件/表 | 不能 | 不能 |
| 已认证 | 现在的指标配置 | 能 | 能 |

为什么？一旦草稿混进去，系统就会拿"猜的"当"定的"用，错了还没人知道。

**再签字。** 不是让人填 YAML，是拿 20–50 个真实问题让系统跑一遍，业务方只看三件事：算法对不对、字段对不对、结果对不对。

签完记四样东西：

- 谁签的字
- 什么时候签的
- 拿哪些问题验的
- 签完的结果是多少

没有这四样，就不算"已认证"，不能出现在正式问答里。

**最后防倒退。** 签过字的题存成"回归题库"，以后改口径先跑一遍，分数掉了就拦住。就像改完手册，拿以前考过新人的题再考一遍。

**别说错**："AI 生成完，人工抽查一下就行。"——抽查不是认证，没签字的口径不能对外承诺。

## Q5：没有历史 SQL 怎么办？

**他真正想问的**：你的方案是不是依赖一个客户可能没有的东西。

**一句话怎么答**：

> 退到"问题驱动的最小可用集"：不做全量字典，先收集 50 个真实问题，只定义这 50 个问题需要的 20 个指标，覆盖 80% 高频问题就够冷启动。

**他继续追时怎么展开**：

- 全量字典是第二年的事，第一年做不完，也没必要。
- 20 个指标怎么选？按问题频次排，不按业务模块排。
- 每个指标先做"够用版"：口径写清楚、字段映射对、有回归题，不追求覆盖所有边界情况。
- 剩下的长尾问题，走 L0/L1 模式：能查，但标"未认证"。

**别说错**："没有历史 SQL 就做不了。"——那是把方案绑死在一个前提上。

## Q6：客户不愿意出人签字怎么办？

**他真正想问的**：你会不会硬卖，或者把责任推给客户。

**一句话怎么答**：

> 那说明他现阶段更适合自助取数工具，不适合我们——诚实说边界比硬卖强。如果能接受，两个人两周就能完成第一轮。

**他继续追时怎么展开**：

算一笔账：一条指标 15 分钟，加上返工，20 条约 8–10 个工时，再加业务方排期，两周。

如果客户连这个投入都不愿意，说明他不需要"口径一致"，只需要"能查数"。那就别卖语义层，卖 BI 或者 NL2SQL 更合适。

**别说错**："签个字而已，很快的。"——把认证说得很轻松，等于承认你没做过。

---

## Q7：签完就完了吗？口径改了怎么办？

**他真正想问的**：你有没有版本和回归的概念。

**一句话怎么答**：

> 没完。指标带版本，改口径走变更单，旧报表锁旧版本，新报表用新版本，两边都跑回归。

**他继续追时怎么展开**：

- **版本**：每条指标记 version，改一次升一次。
- **变更单**：谁改、为什么改、影响哪些报表，写清楚。
- **回归**：签过字的题重跑，分数掉了拦住。
- **可追溯**：用户问"上周和这周数字为什么不一样"，能答出"因为 11 月 5 日改了退款口径"。

这是语义层相对纯 NL2SQL 最值钱的地方：**口径变更是可解释的，不是玄学。**

**别说错**："口径很少变。"——财务口径一年能改八次。

---

## Q8：能不能先上线再补签字？

**他真正想问的**：你懂不懂灰度，会不会拿用户当小白鼠。

**一句话怎么答**：

> 可以，但只能开 L0/L1 模式，而且答案必须显式标"未认证"。不能默默用草稿口径回答，那是把风险转嫁给用户。

**他继续追时怎么展开**：

- L0：只做探索取数，不承诺口径。
- L1：单表统计，答案回显算法。
- 未认证的一律标出来，让用户自己判断要不要用。
- 高风险场景（财务对账、对外报表）不开放未认证口径。

**别说错**："先上，出了问题再改。"——数据错了，用户不会给你"再改"的机会。

## Q9：NVIDIA 的 auto-ontology 不是能自动生成吗？

**他真正想问的**：你知不知道业界怎么做，会不会被一个开源项目问住。

**一句话怎么答**：

> 对，它就是"机器写草稿、人签字"，但也没跳过签字这一步。差别是它把"自动生成"做得很重，我们把"签字之后的权限、审计、评测"做得很重。

**他继续追时怎么展开**：

- 它从数据库信息、历史查询里自动生成业务词、算法、表之间怎么关联。
- 生成完，人在界面里用真实问题试，试对了点"认证"。
- 有个"这题能不能答"的检查：手册里没有这个词，就直接说答不了，不硬编。
- 做完通过 MCP 这类接口给别的 AI 助手用。

**共同点**：都不跳过人工认证。
**差异**：它做平台（10 种数据库、MCP、Helm），我们做引擎（治理、权限、评测）。

**别说错**："那个我们也能做。"——既低估工程量，又没讲清自己的取舍。

---

## Q10：这些你们做了吗？

**他真正想问的**：你会不会把设计说成实现。

**一句话怎么答**：

> 没做。现在只有一个很薄的脚手架：抽表结构、按字段名猜指标，生成 YAML 草稿。历史 SQL 反解、草稿/认证隔离、成熟度分级、回归题库，都还没有。

**他继续追时怎么展开**：

如果问"那你先从哪做"：

> 先做"草稿和认证隔离"和"用真实问题认证"这两件。因为它们不改架构，但能立刻把"AI 生成的口径被当真口径用"这个最大风险堵住。历史 SQL 反解可以第二步做，收益大但工作量大。

**别说错**："我们已经支持自动生成了。"——这是最容易翻车的一句。

## 名词解释（大白话）

| 词 | 大白话 |
|---|---|
| 语义层 | 一本翻译手册：左边业务的话，右边数据库怎么算 |
| 指标口径 | "销售额到底怎么算"的约定（含不含退货、含不含税） |
| 冷启动 | 手册是空的，从零把它编出来 |
| 草稿（draft） | 机器写的初稿，没人签过字 |
| 已认证（certified） | 业务方签字的版本，可以对外用 |
| 认证（certify） | 拿真实问题考系统，业务方判断对不对，对的签字 |
| 回归题库 | 以前考过的题，改了口径就重考，防止倒退 |
| 影子模式 | 新草稿先在后台跟着跑，不影响用户，对得上再转正 |
| 最小可用集（MVS） | 先做最常用的 20 个指标，覆盖 80% 的问题 |
| 可答性检查 | 先看手册里有没有这个词，没有就说答不了 |

## 考前 1 分钟

- **一句话**：我们只负责用手册，不负责编手册；客户没有，我们帮他编，但每一页要签字。
- **核心判断**：难的不是编，是签字。
- **三步**：摸底 → 机器写草稿 → 人签字。
- **四档**：L0 只能查 / L1 简单统计 / L2 部分承诺 / L3 完整问答。
- **四样凭证**：谁签的、什么时候、拿什么验的、结果多少。
- **一条铁律**：草稿不能进正式回答。
- **一个对比**：NVIDIA 把"编"做重，我们把"签字之后"做重。
