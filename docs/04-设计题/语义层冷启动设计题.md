# 客户没有指标口径，语义层怎么冷启动（未实现 · 大白话版）

> **先说结论**：客户没有指标口径，我们的系统不是"不能用"，是"只能按词典的完整程度，提供不同程度的功能"。真正难的不是让机器编词典，是让人点头签字。

> **证据边界（很重要）**：这篇文章里的做法，项目里**一个都没做**。
> - 现在只有一个脚本 `scripts/init_semantic.py`：把表名、字段名、字段注释导出来，再按字段名里有没有 `_amount`、`_price` 这种词，猜几个指标，生成一份 YAML。
> - 设计文档 `docs/business/10-semantic-layer.md` 里写过"给字段注释打分、用 AI 补描述"，**那也只是设计，代码里没有**。
> - 现在的指标配置基本只有"怎么算"和"中文名"两个字段，没有"谁签的字""什么时候签的""拿什么验的"。
> - 面试时只能说："我知道该怎么做，当时没做，原因是……"

**怎么用这份文档**：第 2 节背下来，第 3 节理解，第 7 节应付追问，第 8 节防止说错话。

---

## 0. 先打个比方：给新同事编一本《公司黑话手册》

想象客户招了一个新数据分析师。

- 他会写 SQL，但听不懂"流水""GMV""动销"。
- 公司也没有一本手册告诉他这些词到底怎么算。
- 你让他直接查数，他只能猜。猜出来的数看着挺像，但和财务对不上。

**语义层就是这本手册。** 左边写业务的话，右边写数据库怎么算。

客户"没有指标口径"，就是**这本手册是空的**。

这时候直接上系统，会发生什么？

> 系统会自己编一本手册，然后当作官方手册用。编错一条，后面所有引用它的报表全错，而且不报错、数字看着还挺合理。

所以不能硬上。但也不能说"你先把手册写好再来"——那是把活推给客户。

正确的做法是：**我们帮他把手册编出来，但每一页都要他签字。**

## 1. 面试官问这句话，其实在听三件事

| 他在听 | 他想确认 | 扣分的回答 |
|---|---|---|
| 你知不知道系统的前提 | 你会不会把半成品吹成万能 | "什么库都能接，AI 自己会理解" |
| 你会不会交付 | 遇到"没有"的情况，你有没有办法 | "那得客户先自己整理好指标" |
| 你懂不懂成本 | 你知不知道这活到底贵在哪 | "让 AI 生成一下，一天就搞定" |

---

## 2. 三句话回答（先背这个）

1. **我们只负责"用"手册，不负责"编"手册。** 客户没有手册，硬上等于让 AI 瞎编，编错了还没人发现。
2. **编手册不难，难的是让人签字。** 机器一小时能写 100 条，业务方认这 100 条要两个月。
3. **所以我的做法是：机器先写草稿，人逐条签字，签完的才能对外用。** 产品上再按手册的完整程度，分四档服务。

## 3. 两分钟口语版（可以直接背）

> 客户没有指标口径，说白了就是没有一本"销售额到底怎么算"的手册。我们不会让 AI 直接编一本然后当真手册用——编错一条，后面所有报表都错，而且不报错，这个最吓人。
>
> 我的做法分三步。
>
> **第一步，先看看客户手里有什么。** 连上数据库，看表名、字段名、注释全不全，有没有字典表，有没有历史查询记录和 BI 报表。一两天就能判断他是"完全空白"还是"有一点基础"。
>
> **第二步，让机器写草稿。** 顺序很重要：先用数据库里的现成信息，再用历史 SQL 反推，再看业务文档，最后才让大模型猜。历史 SQL 最值钱，因为那里面的算法都是人真用过的，不是模型编的。
>
> **第三步，让人签字。** 不是拿个表格让他填，而是拿二三十个真实问题让系统跑一遍，他只看三件事：算法对不对、字段对不对、结果对不对。对的签字，错的改。签过字的题存进"回归题库"，以后改口径要重考。
>
> 产品上再分四档：客户什么都没有，就只提供"探索取数"，能查但不承诺口径；有注释了，提供单表统计；有部分指标了，签过字的承诺一致，没签字的标"草稿"；全都有了，才提供完整的经营问答加权限审计。
>
> 一句话：不是不能用，是"按手册完整度，提供不同服务"。

**30 秒版**（电话里用）：

> 这块我们没做，是明确的边界。客户没有口径时，我的做法是三步：先看手里有什么，再让机器写草稿，最后拿真实问题让人签字。草稿和正式的分开放，草稿不进正式回答。产品上按手册完整度分四档，不承诺做不到的事。核心判断是：难的不是编，是签字。

## 4. 三步具体怎么做

### 4.1 第一步：摸底（1–2 天）

要看的东西，以及"看到什么意味着什么"：

| 看什么 | 说明白点 | 看到了说明什么 |
|---|---|---|
| 表名、字段名、注释 | 数据库自带的说明书 | 注释多，机器能猜得准一点 |
| 字典表、维表 | 比如"地区表""状态码表" | 能把"华东"自动翻译成 `HD` |
| 历史 SQL、BI 报表 | 以前人是怎么查数的 | 最值钱，能反推出真实算法 |
| 指标手册、Excel | 有没有写下来的口径 | 有就直接抄，省一半事 |
| 敏感字段 | 手机号、身份证这些 | 决定能不能开放明细 |

最后出一页纸，结论就一句话："这个客户现在是什么水平，我们能提供什么，不能承诺什么。"

### 4.2 第二步：让机器写草稿

四个来源，从靠谱到不靠谱：

1. **数据库自己的信息**（表名、字段名、注释、字典表）：最省事，但只能得到"有哪些字段"，得不到"销售额怎么算"。
2. **历史 SQL / BI 报表**：最值钱。把以前的查询语句拆开，看它是不是经常 `SUM(付款金额)`、按地区分组，出现得多了，就说明这就是大家嘴里的"销售额"。
3. **业务文档 / 指标手册**：如果有，直接抄；没有就跳过。
4. **大模型猜**：只能用来"起名字""补描述"，不能用来定算法。

历史 SQL 怎么反推（说人话）：

> 把以前的查询语句一条条拆开 → 看它用了哪个字段、怎么加总、按什么分组 → 一样的归成一类 → 出现次数多的排前面 → 变成"指标候选"，后面附一句"这条是从 137 次查询里总结出来的"。

这样业务方看到的是"你们平时都这么查，我把它整理成一条了"，而不是"AI 觉得销售额应该这么算"。前者他愿意看，后者他不敢信。

**草稿要单独放，不能和正式的混在一起。**

| 类型 | 放哪 | 系统回答问题时能不能用 | 能不能进正式报表 |
|---|---|---|---|
| 草稿（draft） | 单独一个文件 / 一张表 | 不能 | 不能 |
| 已认证（certified） | 现在的指标配置文件 | 能 | 能 |

为什么？因为一旦草稿混进去，系统就会拿"猜的"当"定的"用，错了还没人知道。

### 4.3 第三步：让人签字

#### 怎么签：拿真题考，不要拿表格填

1. 找 20–50 个业务方平时真的会问的问题。
2. 让系统跑一遍，把它"理解成了什么、生成了什么 SQL、算出来什么"摆给他看。
3. 他只判断三件事：算法对不对、字段对不对、结果对不对。
4. 对的签字，错的改，改完再跑。
5. 签过字的题，存进"回归题库"。

为什么不用表格？因为让业务方从零写"销售额怎么算"，他写不出来；但让他看一个结果说"不对，应该扣掉退款"，他立刻能说。

#### 签完要有凭证

每条指标至少记四样东西：

- 谁签的字（`owner`）
- 什么时候签的（`version`）
- 拿哪些问题验的（`evidence`）
- 签完的结果是多少（`sample_result`）

没有这四样，就不算"已认证"，不能出现在正式问答里。

#### 签完还要防倒退

把签过字的题存成"回归题库"。以后谁改了指标算法，先把题库跑一遍，分数掉了就拦住。

这就像改完手册，拿以前考过新人的题再考一遍，确认没把会的改不会。

#### 新指标先"偷偷跑"一段时间

新写的草稿先别给用户看。后台同时跑"草稿版"和"正式版"，记录两边算出来一样不一样。一样率达到 95% 以上，再转正。

这叫影子模式——新东西先在旁边跟着跑，不影响到人。

## 5. 不同客户，提供不同服务（四档）

| 档位 | 客户什么样 | 我们提供什么 | 我们敢承诺什么 |
|---|---|---|---|
| **L0** | 只有数据库，没注释没指标 | 帮他找表、看样本数据、预览 SQL | 只保证"查得到"，不保证"口径对" |
| **L1** | 有表结构、有注释 | 单表 / 多表统计问答 | 答案里写明"这个数是怎么算的" |
| **L2** | 有一部分指标定义 | 签过字的指标承诺一致，没签字的标"草稿" | 签字的保证一致，没签字的提前说明 |
| **L3** | 指标齐全、有权限有审计 | 完整经营问答 | 口径一致、权限受控、能审计 |

一句话：**手册越全，服务越多；不是"能不能用"，是"敢承诺到哪一步"。**

三条规矩：

1. 档位决定"能回答哪类问题"，不决定"系统能不能上线"。
2. 任何答案都要能说清"这个数是从哪条指标来的、签没签字"。
3. 降级要明说，不能偷偷用草稿回答。

## 6. 和 NVIDIA auto-ontology 什么关系

一句话：**他们把我们说的这套"机器写草稿、人签字"做成了产品，但也没有跳过"人签字"这一步。**

- 他们能从数据库信息、历史查询里，自动生成"业务词、算法、表之间怎么关联"。
- 生成完，人在界面里用真实问题试，试对了点"认证"。
- 有一个"这题能不能答"的检查：手册里没有这个词，就直接说答不了，不硬编。
- 做完再通过 MCP 这类接口，给别的 AI 助手用。

我们没做这套，但思路一样。差别是：他们把"自动生成"做得很重，我们把"签字之后的权限、审计、评测"做得很重。

## 7. 面试官可能接着问（10 个）

| # | 他会问 | 你就这么答 |
|---|---|---|
| 1 | 没有历史 SQL 怎么办？ | 先做最常用的 20 个指标，覆盖 80% 的问题，别想一次做全。 |
| 2 | AI 编错了谁负责？ | 所以要有签字和版本；草稿的回答必须标"未认证"，不能进正式报表。 |
| 3 | 为什么不直接让 AI 每次现算？ | 同一个问题两次答案不一样，业务方就不信了；而且没法审计、没法控权限。 |
| 4 | 客户不愿意出人签字怎么办？ | 那他现在更适合自助取数工具，我们要诚实说边界。愿意的话，两个人两周能完成第一轮。 |
| 5 | NVIDIA 不是能自动生成吗？ | 能生成，但也要人认证；至少 NVIDIA 这个项目没有跳过这一步。 |
| 6 | 签字要多久？ | 一条 15 分钟，加上返工，20 条大概 8–10 个工时，排期两周。 |
| 7 | 口径改了旧报表怎么办？ | 指标带版本，旧报表锁旧版本，新报表用新版本，两边都跑回归。 |
| 8 | 多个部门口径打架怎么办？ | 各域各自注册，同名不同算法；跨部门比较必须显式说明用谁的。 |
| 9 | 能不能先上线再补签字？ | 可以，但只能开 L0 / L1，而且答案必须标"未认证"。 |
| 10 | 怎么算冷启动成功？ | 签字的指标覆盖率、高频问题覆盖率、反问率、返工率、口径争议数。 |

## 9. 名词解释（大白话）

| 词 | 大白话 |
|---|---|
| 语义层 | 一本翻译手册：左边业务的话，右边数据库怎么算 |
| 指标口径 | "销售额到底怎么算"的约定（含不含退货、含不含税） |
| 冷启动 | 手册是空的，从零把它编出来 |
| 草稿（draft） | 机器写的初稿，没人签过字 |
| 已认证（certified） | 业务方点头签字的版本，可以对外用 |
| 认证（certify） | 拿真实问题考系统，业务方判断对不对，对的签字 |
| 回归题库（regression suite） | 以前考过的题，改了口径就重考，防止倒退 |
| 影子模式（shadow mode） | 新草稿先在后台跟着跑，不影响用户，对得上再转正 |
| 最小可用集（MVS） | 先做最常用的 20 个指标，覆盖 80% 的问题 |
| 可答性检查 | 先看手册里有没有这个词，没有就说"答不了" |
| MCP | 一种标准接口，让别的 AI 助手能调用这套能力 |
| RBAC | 按角色分权限，比如普通员工看不到工资 |
| PII | 能认出个人的信息，比如手机号、身份证 |

## 10. 考前 1 分钟

- **一句话**：我们只负责用手册，不负责编手册；客户没有，我们帮他编，但每一页要签字。
- **核心判断**：难的不是编，是签字。
- **三步**：摸底 → 机器写草稿 → 人签字。
- **四档**：L0 只能查 / L1 简单统计 / L2 部分承诺 / L3 完整问答。
- **四样凭证**：谁签的、什么时候、拿什么验的、结果多少。
- **一条铁律**：草稿不能进正式回答。
- **一个对比**：NVIDIA 把"编"做重，我们把"签字之后"做重。
