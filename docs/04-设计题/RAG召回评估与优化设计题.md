# RAG 召回评估：面试官会怎么一路追问（未实现 · 问答版）

> **证据边界**：这篇里的评估方法，项目里**没有做**。
> - 已实现的是检索链本身：四集合召回、jieba 关键词 + 向量双通道、CrossEncoder 精排、4000 字符预算。见 [RAG 检索链专项](../03-专项/RAG检索链专项.md)。
> - 没有的：标注集、Recall@K / MRR / nDCG、分通道归因、精排增益、阈值校准、RRF。
> - 现在只有端到端评测（DSL 对不对），检索层好不好，说不清。
> - 面试口径："检索链做了，检索评估没做；这是我要补的第一件事。"

**怎么用**：先背第 0 节的问题树，再逐问看。每一问都按「他真正想问什么 → 一句话怎么答 → 继续追怎么展开 → 别说错」写。

## Q1：你们 RAG 效果怎么评？

**他真正想问的**：你有没有检索层的评估，还是只看"最后答对了没有"。

**一句话怎么答**：

> 现在只有端到端——看最后 DSL 对不对。检索层没评：不知道是没召回，还是召回了没用对。

**他继续追时怎么展开**：

检索链是四段：

```
查询 → 关键词通道 ─┐
     → 向量通道   ─┼→ 合并去重 → 精排 → 阈值 → top_k
```

链条越长，越需要分段评。因为端到端错了，可能是任何一段坏的。

**别说错**："我们准确率 86.9%。"——那是端到端，不是检索。

---

## Q2：为什么不能只看端到端？

**他真正想问的**：你知不知道"端到端对"会掩盖两种完全不同的失败。

**一句话怎么答**：

> 因为端到端错了，分不清是"没召回"还是"召回了没用对"。这两种修法完全不同：一个改召回，一个改生成或排序。

**他继续追时怎么展开**：

```
失败 A（没召回）：RAG 根本没把 gmv 的定义放进上下文
                  → 模型不知道有 gmv，只能猜

失败 B（没用好）：上下文里有 gmv，但模型没选它
                  → 这是生成/排序的问题，不是检索的问题
```

A 要改召回（阈值、词典、embedding），B 要改 prompt 或生成链路。

**只有端到端分数，你永远不知道该修哪边。**

**别说错**："端到端对了就说明检索没问题。"——模型可以靠 prompt 里的硬规则兜住，掩盖召回缺失。

## Q3：那要建什么地基？

**他真正想问的**：你知不知道评检索的前提是标注集。

**一句话怎么答**：

> 一份标注集：每道题写清楚，四个集合里各自应该召回哪些 name。没有它，所有指标都是空中楼阁。

**他继续追时怎么展开**：

```yaml
cases:
  - id: r001
    query: "各品牌的流水"
    expected:
      metrics: [gmv]
      terms:   [GMV]
      schema:  [brand]
      history: []
```

四条设计规矩：

| 规矩 | 为什么 |
|---|---|
| 按集合分开标 | 四个集合语义不同，混在一起算 Recall 没意义 |
| 标到 name 粒度 | name 是最终能落到实体的最小单位 |
| 允许空 expected | 不是每道题都要命中所有集合 |
| 标"相关"不是"唯一正确" | 一道题可以有多条相关 |

**起步 50 条**，覆盖六类：术语别名（流水→gmv）、英文缩写（AOV）、多维度、时间表达、否定、歧义。

来源：现有测试脚本扩写、线上审计表的真实问题、LLM 生成 + 人工筛。

**质量红线**：标注必须人工过一遍。LLM 自己标自己评 = 循环论证。

**别说错**："用 LLM 生成标注集就行。"——那是在自己考自己。

## Q4：具体看哪些指标？

**他真正想问的**：你是不是只知道 Recall。

**一句话怎么答**：

> 五个：Hit Rate、Recall、Precision、MRR、nDCG。先看 Recall（该找的找到没），再看 MRR（第一个对不对），精排对比用 nDCG（排序质量），Precision 配着看，Hit Rate 做健康度看板。

**他继续追时怎么展开**：

### 先看总表：五个指标各管一件事

| 指标 | 一句话 | 分母是什么 | 排序敏感 | 什么时候看 |
|---|---|---|---|---|
| **Hit Rate@K** | 有没有命中 | query 总数 | 否 | 给老板看的健康度 |
| **Recall@K** | 该找的找到没 | **应召回的相关条数** | 否 | **最先算** |
| **Precision@K** | 捞进来的干不干净 | K | 否 | 配 Recall 一起看 |
| **MRR** | 第一个相关排第几 | query 总数 | 只看第一个 | 预算紧张时 |
| **nDCG@K** | 整体排序质量 | 理想排序 | **是** | **精排对比必用** |

**记忆口诀**：**Hit 看有没有、Recall 看漏没漏、Precision 看脏不脏、MRR 看头名、nDCG 看顺序。**

---

### ① Hit Rate@K —— 最粗的一个

**回答什么**：前 K 条里，只要命中**任意一条**相关结果，这道题就算过。

**公式**：

```
Hit Rate@K = 命中过至少一条相关的 query 数 / 总 query 数
```

**手算**：3 道题，看各自 top3 里有没有相关：

| query | top3 | 有相关吗 |
|---|---|---|
| q1 | gmv, avg_order_value, sales_amount | ✅（gmv） |
| q2 | customer_count, total_balance, sales_amount | ❌ |
| q3 | region, brand, channel | ✅（brand） |

```
Hit Rate@3 = 2/3 ≈ 0.67
```

**什么时候用**：给非技术的人看"整体有没有救"。比如产品经理问"检索能用吗"，你说 Hit Rate@5 是 85%，他能听懂。

**三个坑**：

| 坑 | 说明 |
|---|---|
| 不看排第几 | 相关的排第 1 还是第 5，Hit Rate 都是 1 |
| 不看命中几条 | 该召回 5 条，只命中 1 条，Hit Rate 还是 1 |
| 容易被"命中一条"安慰 | Hit Rate 90% 看着好，可能 Recall 只有 30% |

**别说错**："Hit Rate 高说明检索好。"——它只说明"至少捞到了一条"，不说明捞全了、也不说明排得对。

---

### ② Recall@K —— 最先算的那个

**回答什么**：**该召回的相关结果里，前 K 条覆盖了多少。**

**公式**：

```
Recall@K = （前 K 条里命中相关数） / 应召回的相关总数
```

**手算**：query"各品牌的流水"，metrics 集合应召回 `{gmv}`（1 条），实际 top3 是 `[gmv, avg_order_value, sales_amount]`：

```
Recall@3 = 1/1 = 1.0
```

换一个"让利最多的牌子"，相关 `{total_discount}`，实际 top3 是 `[sales_amount, gmv, customer_count]`：

```
Recall@3 = 0/1 = 0.0
```

**为什么第一个算它**：检索的第一性目标是"该找的东西找到了吗"。**Recall 不行，后面所有优化都是白费**——模型没看到 gmv 的定义，它就只能瞎猜。

**为什么它是分母最容易被搞错的指标**：

```
如果标注里写了 3 条相关（gmv、sales_amount 都可能对），
实际只召回 1 条 → Recall = 1/3 = 0.33，不是 1.0
```

**所以标注必须标全**——不能只标"最理想的那一条"，否则 Recall 会虚高。

**什么时候用**：所有检索评估的起点。

**别说错**："Recall 高就说明检索好。"——Recall 高但 Precision 低，说明把一堆垃圾也捞进来了，会挤占 prompt 预算（你只有 4000 字符）。详见 ③。

---

### ③ Precision@K —— 捞进来的干不干净

**回答什么**：前 K 条里，**有几条是真有用的**。

**公式**：

```
Precision@K = 命中相关数 / K
```

注意区别：**Recall 的分母是"该召回的条数"，Precision 的分母是 K（你实际取了几条）**。

**手算**：top3 = `[gmv, avg_order_value, sales_amount]`，相关只有 `{gmv}`：

```
Precision@3 = 1/3 ≈ 0.33
```

意思是：**我给了模型 3 条上下文，只有 1 条有用，另外 2 条是噪声。**

**为什么它对你这套系统特别重要**：

你的 `build_context` 有 **4000 字符的硬预算**。垃圾结果不是"多占一点地方"这么简单——**它会把有用的挤出去**。

极端例子：
```
预算只装得下 2 条
召回 = [sales_amount(相关), 一堆垃圾]
真正的 gmv 被挤到第 5 条 → 进不了 prompt → 模型还是不知道 gmv
```

**所以 Recall 高不代表模型能看到**——还要看 Precision，因为**能进 prompt 的只有前几条**。

**和 Recall 是跷跷板**：

```
K 调大 → Recall ↑（能捞的更全）、Precision ↓（垃圾也进来了）
K 调小 → Recall ↓、Precision ↑
```

**折中可以用 F1**：

```
F1 = 2 × Precision × Recall / (Precision + Recall)
```

举例：Recall = 1.0、Precision = 0.33：

```
F1 = 2 × 0.33 × 1.0 / (0.33 + 1.0) = 0.66 / 1.33 ≈ 0.50
```

**什么时候用**：
- 配 Recall 一起看，判断"是漏了"还是"脏了"
- 你的场景**尤其要看**，因为上下文预算有限

**三个坑**：

| 坑 | 说明 |
|---|---|
| K 很小时抖动大 | K=1 时 Precision 只能是 0 或 1，噪声极大 |
| 标注只标了"必须命中"的项 | 其他结果其实也有用，但被算成不相关 → Precision 被低估 |
| 和 Recall 分开看 | 单看 Precision 会鼓励"只取 1 条"，那是放弃覆盖 |

**别说错**："Precision 低说明检索差。"——也可能只是 K 设太大了，或者标注集只标了核心项。

---

### ④ MRR —— 第一个相关排第几

**回答什么**：**用户/模型最先看到的那条，对不对。**

**公式**：

```
RR = 1 / 第一个相关结果的排名
MRR = 所有 query 的 RR 的平均值
```

**手算**：

| query | 第一个相关排第几 | RR |
|---|---|---|
| q1 | 1 | 1/1 = 1.0 |
| q2 | 2 | 1/2 = 0.5 |
| q3 | 4 | 1/4 = 0.25 |

```
MRR = (1.0 + 0.5 + 0.25) / 3 ≈ 0.58
```

**为什么它对你有用**：你的场景里，**排最前面的结果权重最高**（prompt 里越靠前，模型越容易采纳）。所以"第一个对不对"比"整体排序"更贴近实际效果。

**什么时候用**：
- 上下文预算很紧，只塞得下一两条
- 想快速判断"精排是不是把对的顶到前面了"

**坑**：它只看"第一个相关"，**多个相关结果的贡献被忽略**。比如该召回 3 条、全部都在 top5 里，但第一个相关排第 4 —— MRR 只有 0.25，会显得很差，尽管你其实捞全了。这种情况要配 Recall 一起看。

**别说错**："MRR 高说明排序好。"——它只保证头名对，不管后续。

---

### ⑤ nDCG@K —— 整体排序质量

**回答什么**：**相关结果排得靠前还是靠后**——越靠前越值钱。

**公式**：

```
DCG@K  = Σ(i=1..K)  相关_i / log2(i+1)
IDCG@K = 理想情况（相关全排最前）的 DCG
nDCG@K = DCG / IDCG
```

`log2(i+1)` 的作用：**位置越靠后，折算权重越小**。第 1 位权重 1，第 2 位 0.63，第 3 位 0.5……

**手算**：相关 `{total_discount}`，top4 = `[sales_amount(0), total_discount(1), gmv(0), customer_count(0)]`：

```
DCG@4  = 0/log2(2) + 1/log2(3) + 0/log2(4) + 0/log2(5)
       = 0 + 1/1.585 + 0 + 0
       ≈ 0.631

IDCG@4 = 1/log2(2) + 0 + 0 + 0 = 1.0     ← 理想：相关排第 1

nDCG@4 = 0.631 / 1.0 ≈ 0.631
```

**换个更好的排序**：如果 top4 = `[total_discount(1), sales_amount, gmv, customer_count]`：

```
DCG@4  = 1/log2(2) + 0 + 0 + 0 = 1.0
nDCG@4 = 1.0 / 1.0 = 1.0
```

**从 0.631 提升到 1.0**——这就是"精排把对的顶上去"的量化表现。

**什么时候用**：**精排前后对比必须用它**。因为精排的唯一价值就是"改变顺序"，只有位置敏感的指标能测出这个变化。Recall 和 Precision 对顺序不敏感，精排前后它们完全不变。

**坑**：
- 二元相关（命中/不命中）用 0/1 就够了；多级相关（非常相关/相关/不相关）要用 `2^rel - 1` 这种增益函数
- Recall 低的时候 nDCG 高也没意义——该有的都没有，排序再好也是排垃圾

**别说错**："nDCG 最高，所以只看 nDCG。"——它是排序指标，不衡量覆盖。

---

### ⑥ 五个指标怎么组合读（这才是重点）

**单看任何一个都会误判**，要看组合：

| 现象 | 说明什么 | 该改哪里 |
|---|---|---|
| **Recall 高 + Precision 低** | 该找的都找到了，但捞了一堆垃圾 | 降 K、调高阈值、上精排 |
| **Recall 高 + MRR 低** | 找到了，但排得靠后 | 上精排、调权重 |
| **Recall 低 + Precision 高** | 很准，但漏得多 | 提高 K、加召回通道、补 jieba 词典 |
| **Recall 低 + Precision 低** | 整体崩了 | 先查索引/embedding/标注集，别调参数 |
| **Hit Rate 高 + Recall 低** | 只命中了一小部分相关项 | 标注集有多条相关，得标全 |
| **nDCG 高 + MRR 低** | 多个相关整体排得不错，但头名不是 | 看你更在意哪个：只塞 1 条就优化 MRR |

**举个例子说明为什么不能只看一个**：

```
只报 Recall@5 = 1.0，看起来满分
但实际：top5 里 4 条是垃圾（Precision = 0.2）
       有用的那条排第 5（MRR = 0.2）
你的预算只装得下前 2 条 → 模型根本看不到有用的那条
```

**Recall 满分，实际效果为零。**

---

### ⑦ K 怎么选

```
K 应该 ≈ 你能塞进上下文的条数
```

你的场景 `top_k=5`、预算 4000 字符，所以：

- ✅ 报 **Recall@5**、**nDCG@5**——和实际使用一致
- ❌ 报 Recall@50——你根本不会把 50 条塞进 prompt，那是自欺欺人

> 面试可以补一句："**K 要和实际消费的条数对齐**，报 Recall@50 只能说明系统里有，不能说明模型看得见。"

---

### ⑧ 建议报告格式

```
【metrics 集合】
Recall@5 = 0.85   ← 该找的漏了多少
Precision@5 = 0.34 ← 捞进来的有多脏
MRR = 0.72        ← 头名对不对
nDCG@5 = 0.79     ← 整体排序好不好
```

**全局再加一个** `Hit Rate@5 = 0.92`（给非技术的人看）。

**不要只报一个数。**

---

**别说错**："我们看准确率。"——检索层没有"准确率"这个标准定义，必须说清是 Recall 还是 Precision。这是面试官判断你是否真的做过评估的一个信号。

## Q5：Recall@K 怎么算？为什么先看它？

**他真正想问的**：你会不会算，以及懂不懂它的分母。

**一句话怎么答**：

> 前 K 条覆盖了多少"该召回的相关结果"。它是检索的第一性目标——该找的东西找到了吗。

**他继续追时怎么展开**：

```
Recall@K = |相关结果 ∩ 前K条| / |相关结果|
```

手算：query"各品牌的流水"，metrics 集合应该召回 `{gmv}`，实际 top3 = `[gmv, avg_order_value, sales_amount]`：

```
Recall@3 = 1/1 = 1.0
```

换个 query"让利最多的牌子"，相关 `{total_discount}`，实际 top3 = `[sales_amount, gmv, customer_count]`：

```
Recall@3 = 0/1 = 0.0
```

```python
def recall_at_k(ranked, relevant, k):
    if not relevant:
        return 1.0                 # 没要求召回 → 不扣分
    hits = sum(1 for n in ranked[:k] if n in relevant)
    return hits / len(relevant)
```

**坑**：分母是"相关条数"。标了 3 条但只召回 1 条，Recall 是 1/3，不是 1。所以标注要标全。

**别说错**："Recall 高就说明检索好。"——Recall 高但 Precision 低，说明捞了一堆垃圾，会挤占 prompt 预算。

---

## Q6：MRR 和 nDCG 有什么区别？

**他真正想问的**：你知不知道"只关心第一个"和"关心整体排序"是两件事。

**一句话怎么答**：

> MRR 只看第一个相关结果排第几；nDCG 看整体排序，越靠前越值钱。预算只装得下一两条时看 MRR，精排前后对比看 nDCG。

**他继续追时怎么展开**：

**MRR**：

```
RR = 1 / 第一个相关结果的排名
MRR = 所有 query 的 RR 平均
```

| query | 第一个相关排第几 | RR |
|---|---|---|
| q1 | 1 | 1.0 |
| q2 | 2 | 0.5 |
| q3 | 4 | 0.25 |

MRR = (1.0 + 0.5 + 0.25) / 3 ≈ 0.58。

**nDCG**：

```
DCG  = Σ 相关_i / log2(i+1)
IDCG = 理想情况下（相关都排最前）的 DCG
nDCG = DCG / IDCG
```

手算：相关 `{total_discount}`，top4 = `[sales_amount, total_discount, gmv, customer_count]`：

```
DCG@4  = 0 + 1/log2(3) + 0 + 0 = 0.631
IDCG@4 = 1/log2(2) = 1.0
nDCG@4 = 0.631
```

**什么时候用**：**精排前后对比必须用 nDCG**——精排的价值就是把对的东西排到前面，只有位置敏感的指标能测出来。

**别说错**："nDCG 越高越好，所以只看 nDCG。"——Recall 低的时候，nDCG 高也没用（该有的都没有）。

---

## Q7：召回不低，答案还是错，怎么定位？

**他真正想问的**：你会不会做归因，还是只会调参数。

**一句话怎么答**：

> 分通道归因：分别只开关键词、只开向量、全链路，各算一遍 Recall，看是哪条通道拖后腿。

**他继续追时怎么展开**：

```python
report = {
    "keyword_only":  recall(只开关键词),
    "vector_only":   recall(只开向量),
    "hybrid_rerank": recall(全链路),
}
```

读结果的四条规则：

| 现象 | 结论 | 改什么 |
|---|---|---|
| 关键词高、向量低 | 短实体精确匹配是主力 | 查 embedding，或降向量权重 |
| 向量高、关键词低 | 语义有用，词典没覆盖 | 补 jieba 词典 / 别名 |
| 两路都低、融合高 | 融合在起作用 | 保持，可试 RRF |
| 两路都高、融合没更高 | 融合没增益甚至有害 | 查合并去重有没有丢序 |

**加分句**："没有这个归因，调检索就是蒙着眼睛改参数。"

**别说错**："效果不好就调 top_k。"——top_k 是结果，不是原因。

---

## Q8：精排到底有没有用？怎么证明？

**他真正想问的**：你上 CrossEncoder 是靠感觉，还是有数据。

**一句话怎么答**：

> 同一批 query 跑两次：不精排取 top5，和精排后取 top5，比 nDCG 差值。正增益才说明值。

**他继续追时怎么展开**：

```
基线：粗召回（不精排）直接取 top5
精排：粗召回 top10 → CrossEncoder → 取 top5
增益 = nDCG(精排后) - nDCG(基线)
```

- `> 0` 且显著 → 精排有用；
- `≈ 0` → 白跑，粗召回已经够好，或者 reranker 没吃对输入；
- `< 0` → 精排添乱，可能对短中文实体不敏感。

为什么 CrossEncoder 更强：粗召回是双塔，query 和 doc 分开编码；CrossEncoder 把两者拼起来编码，能捕捉交互信息。

**别说错**："加了 rerank 效果肯定更好。"——短文本、专有名词场景，rerank 经常没增益。

---

## Q9：阈值 0.5 怎么来的？

**他真正想问的**：你的参数是拍的，还是数据定的。

**一句话怎么答**：

> 拍的。正确做法是看分数分布 + 验证集扫阈值 + 监控回退率。

**他继续追时怎么展开**：

**第一步：看分布。** 相关候选的分数集中在 0.7–0.95，不相关的在 0.1–0.4，阈值取中间。如果两者重叠严重，说明 reranker 分不开，调阈值没用，得换模型。

**第二步：扫。** 在验证集上从 0.2 到 0.9 扫一遍，找 Recall@5 最高的点。

**第三步：看回退率。** 链路里有个逻辑：某集合被阈值全过滤掉，就回退 top3。这个回退发生的比例就是回退率。

- 回退率 > 30% → 阈值太高，精排形同虚设；
- 回退率 ≈ 0 → 阈值太低，过滤没起作用；
- 健康区间大概 5%–15%。

**别说错**："0.5 是经验值。"——经验值也要有分布支撑。

---

## Q10：两路结果怎么融合？RRF 是什么？

**他真正想问的**：你知不知道"分数不可比"这件事。

**一句话怎么答**：

> 现在是硬拼接：关键词的排前面，向量的补后面。更好的做法是 RRF——不融合分数，融合排名，因为排名跨通道可比。

**他继续追时怎么展开**：

现在的合并问题：关键词通道的第 1 名和第 9 名没区别，都是"先放进去"；向量通道里一个高相关结果，反而排在关键词的垃圾后面。

为什么不能直接融合分数？关键词相似度、向量相似度、精排 logit，三个量纲，直接加权是比苹果和橘子。

为什么排名可以融合？第 1 就是第 1，不管分数多少。

```
RRF_score(d) = Σ 1 / (k + rank_L(d))     # k 通常取 60
```

手算：`gmv` 关键词第 1、向量第 3：

```
1/61 + 1/63 ≈ 0.0323
```

`sales_amount` 关键词第 5、向量第 2：

```
1/65 + 1/62 ≈ 0.0315
```

`gmv` 胜出。注意：**不需要调任何权重**。

```python
def rrf_fuse(ranked_lists, k=60):
    scores = {}
    for ranked in ranked_lists:
        for rank, name in enumerate(ranked, 1):
            scores[name] = scores.get(name, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=lambda n: scores[n], reverse=True)
```

**为什么分母 +60**：让高排名之间的差距变平滑，避免某条通道的第 1 名完全碾压其他通道。60 是经验值。

**别说错**："两路分数加权平均。"——量纲不同，加权没有意义。

---

## Q11：Query 改写有用吗？

**他真正想问的**：你会不会什么都上 LLM。

**一句话怎么答**：

> 有用，但先做零成本的：术语表改写。PRF 和 LLM 改写成本高、可能引幻觉，只在规则覆盖不到时用。

**他继续追时怎么展开**：

**第一档：术语表规则改写（最该先做）。**

```python
# "各品牌的流水" → "各品牌的流水 gmv"
hits = [std for alias, std in alias_map.items() if alias in query]
return query if not hits else f"{query} {' '.join(hits)}"
```

把别名命中显式带进查询向量，提高向量通道对标准名的相似度。

**第二档：伪相关反馈（PRF）。** 第一轮检索拿 top-N，把里面的高频词追加到 query 再检索。成本翻倍，做补救用。

**第三档：LLM 改写。** 多一次调用、延迟和成本都涨，还可能引入幻觉。规则覆盖不到、业务量又证明值得时再上。

**别说错**："让 LLM 把问题改写成标准问法。"——先问一句"这会多一次调用，值吗"。

## Q12：这些你们做了吗？

**他真正想问的**：你会不会把设计说成实现。

**一句话怎么答**：

> 没做。检索链是有的：四集合、双通道、CrossEncoder、阈值、回退。但标注集、Recall/MRR/nDCG、分通道归因、精排增益、阈值校准、RRF，都还没有。

## 附：不同 agent 项目用什么指标

> 这一节回答"指标是不是通用的"——**不是。用法跟项目形态强相关。**

### 先分清两层指标

| 层 | 指标 | 回答什么 |
|---|---|---|
| **检索层** | Hit / Recall / Precision / MRR / nDCG | 该给模型看的东西，看到了吗 |
| **Agent 层** | 任务成功率 / 工具调用准确率 / 步数 / 成本 / 延迟 | 活儿干成了吗、干得划算吗 |

不同项目"重哪一层"完全不同——这一点决定了你该拿什么指标当主指标。

---

### ① Hit Rate@K —— 客服 / FAQ 类的主指标

**在这些项目里是主指标**：

| 项目 | 为什么 |
|---|---|
| **客服机器人**（内部 wiki、售后 FAQ） | 业务逻辑是"有答案就答，没有就转人工"。工程上只需知道"能不能捞到一条可用知识" |
| **工单 / 知识库分流** | 命中一条就够做分类 |
| **RAG 的初版验收** | 先看"能不能用"，不看"用得多好" |

**为什么客服场景爱用它**：客服的 KPI 是"**问题解决率**"，不是"检索覆盖度"。命中一条能答上就解决了；没命中就转人工——转人工本身是可接受的兜底。

**什么时候完全没用**：

- 需要多条证据综合的场景（深度研究、合规审查）——命中一条远远不够
- **你的项目**——ChatBI 里命中一个指标但漏了另一个，查询就是错的

> **一句话**：Hit Rate 是"有没有救"的指标，不是"好不好"的指标。

---

### ② Recall@K —— 数据查询 / 深度研究 / 代码检索的命门

最通用的检索指标，但有三类项目把它当生死线：

**A. 数据查询 / ChatBI（你的项目）**

```
指标没召回 → 模型不知道有 gmv → 只能猜 → 整条查询废掉
```

为什么是命门：这类系统的"正确答案"是唯一的（选对指标 + 选对维度），**漏一个就等于全错**，没有兜底话术。
**主看哪些集合**：`metrics` 和 `terms`——这两个漏了后果最严重。

**B. 深度研究 Agent（多步检索 + 报告生成）**

```
漏掉关键证据 → 结论偏了 → 报告不可用
```

这类 Agent 要"多角度覆盖"（正面证据/反面证据/数据/案例），Recall 低 = 视角缺失。典型做法是看 **Recall@20 甚至 Recall@50**（候选池要宽）。

**C. 代码检索（coding agent 的上下文召回）**

```
漏掉已有的工具函数 → 模型重复造轮子 / 调不存在的 API
```

代码库里相关文件往往只有 2-3 个，Recall 差 = 模型看不到项目已有的封装。

**你的优先级**：**最高**。因为漏召回没有兜底。

---

### ③ Precision@K —— 上下文预算紧的项目才真正在意

**在这些项目里是主指标**：

| 项目 | 为什么 |
|---|---|
| **长文档 RAG**（法律、财报、论文） | 一段条款几千 token，垃圾挤进来直接把答案挤出去 |
| **代码 Agent** | 上下文被代码占满时，噪声显著降低完成率 |
| **few-shot 召回** | 示例错了会**主动误导**模型，比"没有示例"更糟 |
| **你的项目** | 4000 字符预算，垃圾会挤掉真正的指标定义 |

**为什么很多项目"算但不当目标"**：Precision 可以通过"少召回"轻易拉高（K 设 1、阈值调高），代价是 Recall 崩掉。**单独优化 Precision 是危险的。**

**正确用法**：当 Recall 已经不错、但效果还差时看它——怀疑方向是"垃圾挤占预算"。

> **一句话**：Precision 不是目标，是**排查工具**。

---

### ④ MRR —— "只看第一条"的场景

**在这些项目里是主指标**：

| 项目 | 为什么 MRR 最贴切 |
|---|---|
| **搜索式交互**（用户扫一眼列表） | 用户只看第一条，第 5 名等于没用 |
| **代码补全 / 行内建议** | 只显示一条，第一个不对就是错的 |
| **单跳问答**（问一个事实） | 只需要一个答案 |
| **自动补全 / 联想** | 同上 |

**为什么这些场景不用 nDCG**：nDCG 默认"多个相关结果都有价值"；**只消费第一条时，用 nDCG 是浪费信息**。

**什么时候完全不用**：

- 深度研究 / 多步分析——需要多条证据
- **你的项目**——`top_k=5` 都会进 prompt，MRR 只是参考

> **判断标准**：**你实际消费几条？只消费 1 条 → MRR；消费 5 条 → nDCG / Recall。**

---

### ⑤ nDCG@K —— 所有上了精排的项目

**在这些项目里是主指标**：

| 项目 | 为什么 |
|---|---|
| **任何上了 Rerank 的项目** | 精排的唯一价值是"改顺序"，只有 nDCG 能测出来 |
| **搜索引擎 / 推荐系统** | 排序质量就是产品价值 |
| **A/B 对比排序算法** | nDCG 差值是最直接的证据 |
| **你的项目（精排对比时）** | 证明 CrossEncoder 有用 |

**为什么它是精排项目的标配**：

```
Recall 和 Precision 对顺序不敏感
→ 精排前后它们的值完全不变
→ 只有 nDCG 能反映"对的被顶上来了"
```

**什么时候没用**：

- 没有精排的项目——排序由向量分数决定，你优化不了
- Recall 很低的项目——该有的都没有，排序再好也是排垃圾
- 多证据场景——只要都召回到了，谁先谁后影响不大

> **一句话**：nDCG 是"排序改动的验收指标"，不是"系统健康的日常指标"。

---

### ⑥ 按项目类型横向看（这张表最实用）

| 项目类型 | 北极星（业务） | **检索主指标** | 关键过程指标 | 基本不看 |
|---|---|---|---|---|
| **企业知识库问答** | 答案正确率 / 转人工率 | Recall@5 + Precision@5 | 无答案识别率 | nDCG |
| **ChatBI / Text2SQL**（你的） | SQL 正确率 | **Recall@K（指标/维度）** | 校验通过率、修正次数 | Hit Rate |
| **编码 Agent** | 任务完成率 | Recall@10（上下文召回） | 首次通过率、步数、成本 | Hit Rate |
| **深度研究 Agent** | 报告可采纳率 | Recall@K（多角度覆盖） | 证据条数、来源多样性 | MRR |
| **搜索 / 单跳问答** | 首条正确率 | **MRR** | 点击率、无结果率 | nDCG |
| **客服多轮** | 解决率 / 转人工率 | Precision（防跑偏） | 澄清率、平均轮次 | nDCG |
| **精排 / 排序产品** | 排序质量 | **nDCG** | 精排增益、延迟 | Hit Rate |
| **流程自动化（RPA+LLM）** | 任务成功率 | 通常无检索 | **工具调用准确率**、步数 | 检索类全部 |

### ⑦ Agent 层指标的分布

| 指标 | 谁在建 |
|---|---|
| **任务成功率** | 所有 agent 的北极星（编码、研究、流程） |
| **工具调用准确率**（该调没调 / 参数对不对） | 工具型 agent、流程自动化 |
| **平均步数 / 最大步数** | 自主循环型（编码、研究）——防失控 |
| **成本 / 单任务 token** | 所有商业化项目 |
| **P95 延迟** | 交互式场景（客服、补全） |
| **澄清率 / 转人工率** | 客服、问数 |
| **人工接管率** | 高风险流程（金融、医疗） |
| **幻觉率** | 所有生成型 |

**规律**：

```
越自主的 agent → 越关注"步数 + 成本 + 成功率"
越交互的 agent → 越关注"延迟 + 澄清率"
越治理敏感的 agent → 越关注"接管率 + 审计覆盖率"
```

| 词 | 大白话 |

## 考前 1 分钟

- **一句话**：端到端是"答对没"，检索评估是"该看到的看到没"，中间隔着模型自己。
- **两个失败**：没召回 / 没用好，修法不同。
- **三个指标**：Recall 先算、MRR 看首位、nDCG 看排序。
- **一个地基**：50 条标注集，标到 name 粒度。
- **一个诊断**：分通道归因。
- **一个增益**：精排前后 nDCG 差值。
- **一个融合**：RRF，1/(60+rank)。
