# 多轮对话与澄清：怎么听懂"那华南呢"（未实现 · 大白话版）

> **先说结论**：多轮不是"把聊天记录存下来"，是"把半句话补成整句话"。补完整了再交给后面的流程，后面的流程根本不用知道这是在聊天。

> **证据边界**：项目现在是**单轮**。
> - 一次查询就开一个线程（`thread_id = query_id`），查完就结束，没有"同一个人还在聊"的概念。
> - 流程的中间状态只存在内存里（`InMemorySaver`），服务一重启就没了；而且一个线程只对应一次查询，不会跨轮复用。
> - 澄清是"问完就结束"：系统问一句、用户答一句，这个回答接不回原来的问题。
> - 文中的会话编号、补话节点（改写节点）、摘要、记忆分层，**一个都没做**。
> - 现在唯一用到"检查点"的地方是人工审核暂停，不是多轮。已实现的部分见 [上下文工程专项](../03-专项/上下文工程专项.md)。

**怎么用这份文档**：第 1 节想明白，第 3 节看方案，第 7 节背口播，第 9 节防止说错话。

---

## 0. 三个日常场景，就是全部问题

**场景一（说半句）**

```
你：华东的销售额是多少？
你：那华南呢？          ← 系统只看到"那华南呢"四个字
```

**场景二（省略）**

```
你：查一下近 7 天的订单量
你：换成近 30 天        ← 系统不知道"换成"是换什么
```

**场景三（澄清之后）**

```
系统：请问时间范围是本月、上月还是最近 7 天？
你：最近 7 天           ← 系统只收到这四个字，不知道前面问的是什么
```

这三句话的共同点：**单独拿出来，都是半句话。**

---

## 1. 一句话想明白：请个"补话员"

想象在流程最前面站一个人，专门负责补话。

他手里有一本小本子，记着刚才聊了什么。每来一句新问题，他只做一件事：

> **上一句 + 这半句 → 拼成一句完整的话。**

比如：

- 上一句"华东的销售额是多少" + 这半句"那华南呢" = "华南的销售额是多少"
- 上一句"近 7 天的订单量" + 这半句"换成近 30 天" = "近 30 天的订单量"

补完之后，他把完整的话交给后面的人。后面的人（生成查询、检查、查库）**根本不知道刚才在聊天**，他们只看到一句完整的话。

这样做有三个好处：

- 多轮这件事只在一个地方处理，出问题好查。
- 后面那一整套流程，一行都不用改。
- 测试的时候，只需要测"补话员补得对不对"。

> 这个"补话员"，正式名字叫**改写节点**（rewrite）。下面就用这个名字。

---

## 2. 现在为什么做不到（两个硬伤）

### 2.1 每次查询都是"从零开始"

现在代码里，一次查询就用一个线程编号（`thread_id = query_id`）。查完，这个线程就结束了。下一次问"那华南呢"，系统眼里是一个全新的、没头没尾的问题。

而且这个线程的中间状态存在内存里（`InMemorySaver`），**服务一重启就没了**。不过就算不重启也没用——一个线程只服务一次查询，下一轮根本不会复用它。

打个比方：你去银行办业务，每说一句话就换一个柜员，新柜员还不看你之前的记录。你刚说"我要取钱"，下一句"取五百"，新柜员只会问"取什么？"

### 2.2 澄清是"死路"

现在系统发现你问得不清楚，会问你一句，然后这条流程就结束了。

你回答"最近 7 天"，前端只能把这四个字当成一个新问题再发一次。系统收到"最近 7 天"，还是不知道你要查什么。

> 就像医生问"哪里疼"，你说"左边"，然后换了个医生进来。新医生只听到"左边"。

## 3. 怎么改：四步

### 3.1 第一步：把"一次聊天"和"一次查询"分开

现在这俩是同一个东西。要拆成两个编号：

| 编号 | 是什么 | 活多久 | 用来干嘛 |
|---|---|---|---|
| 会话编号（`session_id`） | 一次聊天 | 可能几十轮 | 把同一段聊天串起来，记小本子 |
| 查询编号（`query_id`） | 一次提问 | 一次请求 | 查日志、追问题、对反馈 |

用吃饭打比方：**会话是一顿饭，查询是点的一道菜。** 一顿饭可以点很多道菜，但结账算一顿。

拆开之后，同一段聊天里的每一轮，都能找到"上一轮说了什么"。

### 3.2 第二步：请"补话员"（改写节点）

补话分两档，先便宜后贵。

**第一档：死规则。** 高频句式直接套：

- "那 X 呢" → 把上一轮里的地区/品牌换成 X
- "换成 X" → 把上一轮里的时间换成 X
- "再来一次 / 重新查" → 原样再跑一遍

这几条能盖住大部分日常说法，而且不花钱、不会瞎编、出了问题能解释。

**第二档：大模型兜底。** 规则没盖住的，再让模型补。给它的指令就一句：

> 把这句话补成一个能独立看懂的问题，不要加用户没说的条件，判断不了就原样返回。

**三条纪律**（这段面试很加分）：

1. **改写的模型要"笨"一点**：温度设 0，能用小模型就别用大的——这活不需要创造力。
2. **改写失败不能报错**：超时、模型挂了，就拿原话继续跑。宁可少补，不能查不了。
3. **改写前后要留痕**：记下"原话是什么、补成了什么、规则补的还是模型补的"。否则用户问"你为什么查成这个"，你答不上来。

### 3.3 第三步：把澄清做成"一问一答"

关键改动：**给每个问题编个号。**

现在是系统问一句、用户答一句，两句话对不上。改成：

1. 系统问的时候，带上编号：`c1：时间范围选哪个？本月 / 上月 / 最近 7 天`
2. 用户答的时候，把编号带回来：`c1 = 最近 7 天`
3. 系统拿到"原问题 + 编号对应的答案"，拼成一句完整的话再往下走

比如：

- 原问题："查一下销量"
- 系统问："销量是指支付订单量，还是发货数量？"（编号 c1）
- 用户答："支付订单量"
- 拼起来："查一下销量（支付口径）"

**一条铁律**：拼完之后，还是要走完整的检查流程（生成、校验、权限），不能因为"用户已经确认过了"就跳步。

### 3.4 第四步：小本子写满了怎么办

聊到第 20 轮，把前面 19 轮全塞给模型，会超长、会变慢、会变贵。

做法很简单：**最近 3 轮留原话，更早的压成一句话。**

```
【会话摘要】用户在查华南销售额，时间从近 7 天改成近 30 天，要求按品牌分组。
【最近对话】第 18、19、20 轮的原话
【这一轮的问题】...
```

三个坑：

- **否定条件别丢**：用户说过"不要含退款"，摘要不能变成"查销售额"。
- **数字别丢**："近 7 天"不能压成"近期"。
- **别反复压**：摘要是"旧摘要 + 新增的旧轮次"，不是"把摘要再摘要一遍"，不然越压越走样。

## 4. 记忆不是"存一份聊天记录"

小本子要分格子放，不是什么都堆一起：

| 格子 | 放什么 | 例子 |
|---|---|---|
| 工作记忆 | 这次查询正在用的东西 | 当前生成的查询、置信度 |
| 情景记忆 | 发生过什么事 | "上周你问过华东销售额" |
| 语义记忆 | 你这个人的习惯 | "他总爱按品牌看" |
| 程序记忆 | 做事的方法 | "'流水'要当成 GMV" |

用办公室打比方：

- 工作记忆 = 你桌上正在处理的文件
- 情景记忆 = 部门的会议记录
- 语义记忆 = 同事对你的印象（"他喜欢先看汇总"）
- 程序记忆 = 公司的操作手册

---

## 5. 最重要的不是"记"，是"不记"

这是多轮系统最容易翻车的地方：**什么都记，三个月后本子上全是废话，模型反而被带偏。**

| 值得记 | 不值得记 |
|---|---|
| 用户明确确认过的口径（"我要支付口径"） | 每次查出来的具体数字 |
| 说过三次以上的偏好（总按品牌分组） | 一次性的临时条件 |
| 用户纠正过的错（"不是这个指标"） | 闲聊、寒暄 |

三条"忘掉"的规矩：

- 太久没用的，降低权重（比如 30 天没碰，权重减半）
- 新说法和旧说法冲突，旧的标记成"已作废"，但**不删**，方便追溯
- 一个人记的条目太多，先淘汰最不常用的

## 6. 走一遍三轮对话

**第 1 轮**

```
你：华东近 7 天的销售额
系统：没有上文，原样处理 → 生成 → 查库 → 返回
```

**第 2 轮**

```
你：那华南呢？
补话员：命中"那 X 呢" → 补成"华南近 7 天的销售额"
后面的人：收到一句完整的话，正常处理
```

**第 3 轮**

```
你：换成近 30 天
补话员：命中"换成 X" → 补成"华南近 30 天的销售额"
顺带：小本子上超过 3 轮了，把前两轮压成一句摘要
```

三轮下来，后面的人始终只看到"一句完整的话"。这就是为什么要请补话员。

## 7. 面试怎么答（三段，背下来）

**问：多轮对话怎么支持？**

> 核心不是存聊天记录，是把半句话补成整句话。三步：第一，把"一次聊天"和"一次查询"的编号拆开，让同一段聊天能接上；第二，在流程最前面加一个补话节点，先用死规则匹配"那 X 呢""换成 X"这类句式，规则盖不住的再交给模型，模型失败就用原话继续；第三，聊得久了，最近 3 轮留原话，更早的压成摘要。关键约束是：后面的流程完全不知道有多轮，它们只收到一句完整的话。

**问：记忆怎么设计？**

> 分四层：这次查询用的放工作记忆，发生过的事放情景记忆，这个人的习惯放语义记忆，做事方法放程序记忆。但最重要的是**写入策略**——只记用户明确确认过的口径、和重复出现三次以上的偏好，不是什么话都记。没有写入策略的记忆系统，三个月后就是噪声源。

**问：长对话上下文爆了怎么办？**

> 最近 3 轮留原话，更早的压成摘要。摘要里必须显式保住两类东西：否定条件（"不要含退款"）和具体数字（"近 7 天"），这两类最容易在压缩时丢掉。

## 8. 常见追问

| 问 | 答 |
|---|---|
| 为什么先规则后模型？ | 高频句式就那几种，规则零成本、不会瞎编、好排查；剩下的再交给模型，能省掉大部分调用。 |
| 改写错了怎么办？ | 改写只做"补全"、不做"发挥"；失败或拿不准就原样返回，宁可少补。改写前后都留痕，能解释。 |
| 澄清为什么要编号？ | 因为用户可能同时被问两三个问题，回答可能只答一个。没有编号，就不知道哪个答案对应哪个问题。 |
| 用户中间换话题怎么办？ | 补话时先判断"这句和上文有没有关系"，没关系就不补，当新问题处理，避免串上下文。 |
| 摘要把"不要退款"弄丢了怎么办？ | 摘要指令里明确要求保留否定条件；关键约束不放进摘要，单独存一份"硬约束"。 |
| 多轮怎么评测？ | 四类题：指代（那华南呢）、省略（换成 30 天）、澄清（选完选项继续）、干扰（问个无关的再回来）。看整段对话有没有完成任务，不只看单轮对不对。 |

## 9. 千万别说这五句话

| 别说 | 为什么 | 改成 |
|---|---|---|
| "我们支持多轮" | 项目是单轮，一问就穿帮 | "现在是单轮，如果要做我会这样设计" |
| "多轮就是把聊天记录存下来" | 存了也不会用，反而变噪声 | "多轮是把半句话补成完整的话" |
| "把历史全塞进 prompt" | 二十轮就爆，还贵 | "最近几轮留原话，更早的压摘要" |
| "什么都记下来" | 三个月后全是噪声 | "只记确认过的和重复三次以上的" |
| "澄清就是再问一次" | 回答接不回去，等于白问 | "给问题编号，把答案拼回原问题" |

## 10. 名词解释（大白话）

| 词 | 大白话 |
|---|---|
| 单轮 / 多轮 | 一问一答就结束 / 能接着上一句继续聊 |
| 会话编号（`session_id`） | 一次聊天的编号，用来把几十轮串起来 |
| 查询编号（`query_id`） | 一次提问的编号，用来查日志、追问题 |
| 线程（thread） | 系统内部给一次对话流程起的名字 |
| 检查点（checkpointer） | 把流程中间状态存下来的机制，这里现在只用于人工审核暂停 |
| 改写（rewrite） | 把半句话补成完整的话 |
| 澄清（clarification） | 系统发现你问得不清楚，先反问一句 |
| 滚动摘要 | 旧对话压成一句话，新对话保留原话 |
| 工作记忆 | 这次查询正在用的东西 |
| 情景记忆 | 发生过什么事 |
| 语义记忆 | 你这个人的习惯 |
| 程序记忆 | 做事的方法 |
| 遗忘 | 太久没用的降权、旧的作废、太多的淘汰 |
| 降级 | 高级做法失败时，退回简单做法，保证还能用 |
| 留痕 | 把"原话、补成什么、为什么"记下来，方便解释 |

## 11. 考前 1 分钟

- **一句话**：多轮不是记聊天记录，是把半句话补成整句话。
- **两个硬伤**：一次查询一个线程（接不上）、澄清问完就结束（答不回去）。
- **四步**：拆编号 → 补话 → 澄清编号 → 压缩。
- **三条纪律**：温度 0、失败用原话、前后留痕。
- **四层记忆**：工作 / 情景 / 语义 / 程序。
- **一条铁律**：后面的流程永远只看到一句完整的话。
- **收尾**：多轮的不确定性，全挡在"补话"这一层。
