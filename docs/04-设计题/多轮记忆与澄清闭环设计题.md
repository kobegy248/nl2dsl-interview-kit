# 多轮记忆与澄清闭环设计题（未实现）

> **证据边界**：本文全部是**设计提案**。NL2DSL 项目是单轮系统，**没有会话记忆、没有多轮、澄清无回灌**。
> 面试口径：「我们现在是单轮，如果要做我会这样设计」——不要说成"已经支持多轮"。
> 已实现部分见 [上下文工程专项](../03-专项/上下文工程专项.md)。

---

## 0. 定位

一句话：**"我的上下文工程只覆盖单轮那一半；多轮和记忆是缺口，但我知道最小闭环怎么补。"**

---

## 一、缺口清单

| 缺口 | 现状 |
|---|---|
| 会话状态 | thread_id = query_id，每次新线程 |
| 指代消解 | 无 |
| 澄清闭环 | 返回选项即结束，无回灌 |
| 历史压缩 | 无摘要机制 |
| 记忆分层 | 只有工作记忆（QueryState） |

## 二、未采用的技术

### 2.1 记忆四层

| 层级 | 存什么 | 典型实现 | 现状 |
|---|---|---|---|
| **工作记忆** | 当前任务中间状态 | LangGraph state | ✅ 有 |
| **情景记忆** | 发生过什么（对话/事件） | 会话表 / 事件流 | ❌ 无 |
| **语义记忆** | 沉淀的事实（偏好、口径） | 向量库 + 摘要 | ❌ 无 |
| **程序记忆** | 怎么做事（SOP、示例） | Prompt 模板 / 示例库 | ⚠️ 有 history 集合，但只是问句样例 |

### 2.2 上下文四手段

| 手段 | 现状 |
|---|---|
| 选择 | ✅ RAG 四通道 + 精排 |
| 排序 | ✅ terms > schema > metrics > history |
| 压缩 | ⚠️ 只有按条裁剪，无摘要 |
| 隔离 | ✅ 子查询独立 state |

### 2.3 多轮四件事

| 能力 | 说明 |
|---|---|
| 会话状态管理 | session 维度隔离、断点续聊 |
| 指代消解 | "那华南呢" → 补全完整查询 |
| 澄清闭环 | 用户回答 → 回灌 → 继续 |
| 历史压缩 | 滑动窗口 + 滚动摘要 |

### 2.4 长上下文技术

| 技术 | 说明 |
|---|---|
| 滑动窗口 | 只保留最近 N 轮 |
| 滚动摘要 | 老对话压成一段摘要 |
| 分层摘要 | 会话级 + 话题级两级 |
| RAG over conversation | 历史对话做成可检索库 |
| 结构化记忆 | 抽成 (用户, 偏好, 值) 三元组 |
| Prompt caching | 复用不变的 system 前缀 |

### 2.5 多轮评测

| 技术 | 现状 |
|---|---|
| 单轮 DSL 正确性 | ✅ 有 |
| 指代消解是否正确 | ❌ 无 |
| 会话级任务达成率 | ❌ 无 |
| 澄清有效性 | ❌ 无 |

## 三、怎么补

### 3.1 三条原则

1. **会话 ID ≠ 查询 ID**：现在两者是同一个，改成 `session_id` 做会话、`query_id` 做单次请求，是一切的前提。
2. **记忆分层，不是"存一份历史"**：工作记忆进 state，情景记忆进会话表，语义记忆进向量库。
3. **上下文是预算，不是容器**：窗口再大也有成本。

### 3.2 方案 A：澄清闭环（1 天，收益最直接）

```python
# 1. ClarificationItem 带 id
class ClarificationItem(BaseModel):
    item_id: str
    type: str
    question: str
    options: list[str]

# 2. 请求加 answers
class QueryRequest(BaseModel):
    question: str
    user_id: str
    tenant_id: str
    clarification_answers: dict[str, str] | None = None   # item_id -> 选中项

# 3. clarification 节点：有 answers 就跳过检测，直接拼进问题
def clarification_node(state):
    answers = state.get("clarification_answers")
    if answers:
        # "查询华东销售额" + {"time": "最近7天"} → "查询华东销售额（最近7天）"
        return {"question": _apply_answers(state["question"], answers),
                "status": "pending"}
    ...
```

价值：用户不用重打一遍问题，这是多轮体验第一步。

### 3.3 方案 B：多轮会话（1 周，核心改造）

```
① 引入 session_id
   - 请求体加 session_id（前端生成或服务端首次返回）
   - thread_id 改成 session_id → checkpointer 天然支持会话续跑
   - InMemorySaver → SqliteSaver/PostgresSaver 持久化

② 加 query_rewrite 节点（在 clarification 之前）
   - 输入：当前问题 + 最近 N 轮
   - 输出：改写后的完整问题 + rewrite_reason
   - 改写失败降级用原问题，不能因改写失败而报错

③ state 加会话字段
   - session_id / turn_index / conversation_summary / recent_turns

④ 长对话压缩
   - 最近 3 轮保留原文
   - 更早的压成摘要（每 3 轮重压一次）
```

改写节点示意：

```python
REWRITE_PROMPT = """把用户的最新问题改写成一个独立的、完整的问题。
如果它引用了上一轮的实体（比如"那华南呢"），请补全。
只输出改写后的问题，不要解释。

【最近对话】
{recent_turns}

【最新问题】
{question}
"""
```

关键取舍：**改写用小模型/低温度**（只需补全指代，不需要创造力），失败降级为原问题。

### 3.4 方案 C：记忆体系（1 个月）

1. **情景记忆**：`nl2dsl_session` 表（session_id / turn_id / question / dsl / status / created_at）。
2. **语义记忆**：稳定事实抽三元组（偏好、常用指标、常查维度），检索时与新问题一起召回。
3. **程序记忆**：成功问答对沉淀成 few-shot（现在的 history 集合是雏形，可从审计表自动积累）。
4. **写入策略**：只记"用户显式确认的口径"和"重复出现的偏好"，否则记忆越存越脏。
5. **遗忘策略**：按时间 + 访问频率衰减，避免旧记忆压制新事实。

> 第 4 点最容易翻车：**没有写入策略的记忆系统，三个月后必然变成噪声源。**

## 四、设计类追问

**Q1：多轮对话怎么支持？**
> "三步：请求带 session_id 并复用检查点；上下文注入最近几轮；加改写节点把'那华南呢'补全。关键是**改写要在进 DSL 生成之前完成**。"

**Q2：长对话上下文爆了怎么办？**
> "分层压缩：最近 3 轮保留原文，更早的压成摘要，摘要滚动重压。也可以把历史做成可检索库，按需召回——但要小心过时信息。"

**Q3：记忆和 RAG 的区别？**
> "RAG 从外部知识库取事实，记忆从交互历史取偏好和上下文。技术上可共用向量库，但写入策略完全不同：RAG 是离线同步、可信的；记忆是线上产生、需要筛选和遗忘的。"

**Q4：指代消解用规则还是 LLM？**
> "优先规则：'那X呢''换成Y'这类固定模式直接规则改写，零成本可控；规则覆盖不到的再交给 LLM，并要求输出改写前后对比便于审计。"

**Q5：为什么不用向量库直接存对话历史？**
> "对话历史强时序、强最近性。按相似度召回很容易把三个月前的旧口径翻出来干扰当前查询。所以历史优先按时间窗口 + 摘要，只有稳定事实才进向量库。"

**Q6：怎么评测多轮能力？**
> "三类用例：指代类（上一轮问华东，这轮'那华南呢'）、澄清类（给选项后能否正确继续）、省略类（'再来一次'）。指标是会话级任务达成率，不是单轮 DSL 正确率。"

**Q7：多轮会不会破坏 DSL 校验的确定性？**
> "会，所以要在改写层收敛——进图的必须是完整独立的问题。多轮的不确定性被挡在图外。"

## 五、速查

| 问题 | 答案 |
|---|---|
| 现在支持多轮吗 | 不支持（单轮，thread = query） |
| 记忆分层 | 只有工作记忆，情景/语义/程序都没有 |
| 澄清能连续吗 | 不能，无回灌接口 |
| 最小闭环 | 澄清回灌（1 天）→ session + 检查点持久化（1 周）→ 指代改写 |
| 压缩策略 | 最近 3 轮原文 + 滚动摘要（未实现） |
| 记忆写入 | 只记显式确认的口径和重复偏好（未实现） |
| 一句话 | **"上下文工程做了单轮那一半，多轮和记忆是缺口，但最小闭环清楚。"** |
