> **证据边界**：本文全部是**设计方案与教学**。NL2DSL 项目是单轮系统：没有会话记忆、没有多轮、澄清无回灌。
> 面试口径：「我们现在是单轮，如果要做我会这样设计」——不要说成"已经支持多轮"。
> 已实现部分见 [上下文工程专项](../03-专项/上下文工程专项.md)。
>
> **怎么读**：每节按「问题 → 原理 → 方案 → 代码 → 坑」讲，看完能自己实现一个最小多轮。

## 0. 为什么单轮不够：三个真实场景

```
场景 1（指代）
用户：华东的销售额是多少？
用户：那华南呢？          ← 系统只看到"那华南呢"，不知道要算销售额

场景 2（省略）
用户：查一下近7天的订单量
用户：换成近30天          ← 系统不知道"换成"是换什么指标

场景 3（澄清后继续）
系统：请确认时间范围（本月/上月/最近7天）
用户：最近7天             ← 系统只收到"最近7天"四个字，没有原问题
```

这三个场景的共同点：**当前这句话单独拿出来是不完整的**。所谓"多轮能力"，本质就是**把不完整的话补成完整的话**，再交给下游。

> 一句话：**多轮不是"记住聊天记录"，而是"把当前这句话还原成一条完整查询"。**

## 1. 会话状态：session ≠ query（一切的前提）

### 1.1 现在的问题

```python
# api_factory.py
config = {"configurable": {"thread_id": query_id}}   # thread = 一次查询
```

`thread_id` 用的是 `query_id`，所以每次查询都是**新线程**，LangGraph 的检查点不会复用。要支持多轮，第一个改动就是把这两个 ID 拆开：

| ID | 生命周期 | 用途 |
|---|---|---|
| `session_id` | 一次会话（可能几十轮） | 检查点的 thread_id、记忆的主键 |
| `query_id` | 一次请求 | 审计、trace、反馈关联 |

### 1.2 检查点选型（这一步很多人踩坑）

| Saver | 存储 | 能否多实例 | 适用 |
|---|---|---|---|
| `InMemorySaver` | 进程内存 | ❌ | 单机演示、HITL |
| `SqliteSaver` | 本地文件 | ❌（多实例要共享文件系统） | 单机生产 |
| `PostgresSaver` | 数据库 | ✅ | 生产集群 |

现在用的是 `InMemorySaver`（`engine.py`），**进程一重启，所有会话就没了**。做多轮必须换持久化。

### 1.3 状态里要加什么

```python
class QueryState(TypedDict):
    # 已有
    question: str
    query_id: str
    ...
    # 多轮新增
    session_id: str
    turn_index: int                    # 第几轮
    recent_turns: list[dict]           # 最近 N 轮原文
    conversation_summary: str | None   # 更早对话的摘要
    rewritten_question: str | None     # 改写后的问题（下游只看这个）
    clarification_answers: dict | None # 用户对澄清的回答
```

关键原则：**下游节点（validation / build_sql / execute）完全不感知多轮**，它们只读 `rewritten_question`。多轮的不确定性被挡在改写层。

## 2. 指代消解：把"那华南呢"补全

### 2.1 规则 vs LLM：先规则后模型

| 方式 | 优点 | 缺点 | 用在哪 |
|---|---|---|---|
| 规则匹配 | 零成本、可控、可审计 | 覆盖窄 | 固定句式（那X呢 / 换成X / 再来一次） |
| LLM 改写 | 覆盖广、能理解语义 | 多一次调用、可能幻觉 | 规则兜不住的 |

**正确顺序**：先把高频句式写成规则，剩下交给 LLM。这样 80% 的指代不花一次模型调用。

### 2.2 规则版

```python
import re

_PATTERNS = [
    # "那华南呢" / "华南呢" → 替换上一轮里的同类实体
    (re.compile(r"^那?(?P<entity>[\u4e00-\u9fa5A-Za-z]{1,10})呢[？?]?$"), "replace_entity"),
    # "换成近30天" → 替换时间
    (re.compile(r"^换成(?P<time>近\d+天|本月|上月|今年)$"), "replace_time"),
    # "再来一次" → 原样重跑
    (re.compile(r"^(再来一次|重新查|再查一遍)$"), "repeat"),
]

def rule_rewrite(question: str, last_turn: dict | None) -> str | None:
    if not last_turn:
        return None
    for pattern, kind in _PATTERNS:
        m = pattern.match(question.strip())
        if not m:
            continue
        if kind == "repeat":
            return last_turn["question"]
        if kind == "replace_entity":
            # 把上一轮问题里的实体替换成新实体
            return _replace_entity(last_turn["question"], m.group("entity"))
        if kind == "replace_time":
            return _replace_time(last_turn["question"], m.group("time"))
    return None
```

### 2.3 LLM 版（规则兜不住时）

```python
REWRITE_PROMPT = """把用户的最新问题改写成一个独立的、完整的问题。

规则：
1. 如果它引用了上一轮的实体（如"那华南呢"），请补全成完整问题。
2. 如果它省略了指标/维度（如"换成近30天"），从上文继承。
3. 不要改变用户的意图，不要自己加条件。
4. 如果无法判断，原样输出。

【最近对话】
{recent_turns}

【最新问题】
{question}

只输出改写后的问题，不要解释。"""
```

### 2.4 三条工程约束（必须写进代码）

1. **低温度 + 小模型**：改写只是"补全指代"，不需要创造力。用 `temperature=0`，能用小模型就别用大的。
2. **失败降级**：改写失败/超时 → 用原问题继续，**绝不能因为改写失败而报错**。
3. **可审计**：改写前后的对比要进 trace（`rewrite_reason`），否则用户问"你为什么查成这个"没法解释。

```python
def rewrite_node(state):
    question = state["question"]
    last_turn = (state.get("recent_turns") or [{}])[-1]

    rewritten = rule_rewrite(question, last_turn)          # 先规则
    reason = "rule"
    if rewritten is None and state.get("llm_available"):
        try:
            rewritten = llm_rewrite(question, state["recent_turns"])
            reason = "llm"
        except Exception:
            rewritten, reason = question, "fallback"
    if not rewritten:
        rewritten, reason = question, "original"

    return {"rewritten_question": rewritten,
            "trace": {"step": "rewrite", "original": question,
                      "rewritten": rewritten, "reason": reason}}
```

## 3. 澄清闭环：从"死路"变成"一问一答"

### 3.1 现在为什么是死路

```
graph: clarification → END
返回：{"clarifications": [{type: "time_missing", options: [...]}]}
```

用户选了"最近7天"，前端只能重新发一个 `question="最近7天"`——但这句话单独看毫无意义。

### 3.2 改法：把澄清做成"带 id 的问题"

```python
class ClarificationItem(BaseModel):
    item_id: str          # ★ 新增：前端回传时要带上
    type: str             # time_missing / metric_ambiguous / ...
    question: str
    options: list[str]

class QueryRequest(BaseModel):
    question: str
    session_id: str
    user_id: str
    tenant_id: str
    clarification_answers: dict[str, str] | None = None   # item_id -> 选中项
```

### 3.3 状态机

```
第 1 轮：question="查一下销量"
        → 检测到 metric_ambiguous
        → 返回 items=[{item_id: "c1", options: ["支付订单量","发货数量"]}]
        → status = "clarification"，图结束

第 2 轮：question="查一下销量", clarification_answers={"c1": "支付订单量"}
        → clarification 节点跳过检测，把答案合进问题
        → 合成："查一下销量（支付订单量）"
        → 继续正常链路
```

### 3.4 合并逻辑

```python
def _apply_answers(question: str, items: list[ClarificationItem],
                   answers: dict[str, str]) -> str:
    parts = []
    for item in items:
        ans = answers.get(item.item_id)
        if not ans:
            continue
        # 不同歧义类型合进问题的说法不同
        if item.type == "time_missing":
            parts.append(ans)                     # "最近7天"
        elif item.type == "metric_ambiguous":
            parts.append(f"（指标口径：{ans}）")
        elif item.type == "dimension_ambiguous":
            parts.append(f"（按{ans}）")
        elif item.type == "comparison_ambiguous":
            parts.append(f"（对比基准：{ans}）")
    return question + ("".join(parts) if parts else "")
```

> 关键：**澄清答案要能落在 DSL 的确定性字段上**。合并后的问题仍然走完整链路（生成 → 校验 → 权限），不跳过任何护栏。

## 4. 上下文压缩：长对话怎么不爆窗口

多轮跑起来之后，第三个问题立刻出现：**第 20 轮时，把前 19 轮都塞进 prompt 会爆**。

### 4.1 四种策略对比

| 策略 | 做法 | 信息损失 | 成本 | 适用 |
|---|---|---|---|---|
| **滑动窗口** | 只保留最近 N 轮 | 早期信息全丢 | 零 | 短任务、指代只看最近一轮 |
| **滚动摘要** | 早期对话压成一段摘要 | 中（细节丢，结论留） | 定期一次 LLM | 大多数场景 |
| **分层摘要** | 会话级 + 话题级两级 | 低 | 较高 | 超长会话（100+ 轮） |
| **RAG over conversation** | 历史做向量库，按需召回 | 按需 | 需建索引 | 需要"很久以前提过的事" |

### 4.2 滚动摘要怎么实现

**触发条件**（两个满足一个就触发）：

```python
def should_summarize(state) -> bool:
    return (len(state["recent_turns"]) > MAX_TURNS      # 比如 > 6
            or state["total_chars"] > MAX_CHARS)         # 比如 > 3000
```

**摘要 prompt**：

```
请把下面的对话压缩成一段简短摘要，保留：
1. 用户查询过的指标和维度
2. 用户指定的过滤条件（地区、时间、客户类型）
3. 用户明确表达过的偏好或纠正
删除：寒暄、系统提示、重复内容。

【待压缩对话】
{turns}

输出：不超过 200 字的摘要。
```

**压缩后 state 变成**：

```python
{
    "conversation_summary": "用户先查了华东近7天销售额，又对比了华南，"
                            "并明确要求按品牌分组、只看前5。",
    "recent_turns": [最近 3 轮原文],
}
```

**组装 prompt 时**：

```
【会话摘要】{conversation_summary}
【最近对话】{recent_turns}
【最新问题】{question}
```

### 4.3 坑（很关键）

| 坑 | 后果 | 对策 |
|---|---|---|
| 摘要把"否定"弄丢 | 用户说"不要含退款"，摘要后变成"查询销售额" | 摘要 prompt 里**显式要求保留否定和纠正** |
| 摘要反复重压 | 摘要的摘要，语义漂移 | 保留原始摘要，每次只压缩"新增的旧轮次"，不重压已有摘要 |
| 摘要吃掉数字 | "近7天"变成"近期" | 要求"保留具体数值和时间" |
| 摘要延迟高 | 每轮都触发 | 只在超阈值时触发，且用异步/后台 |

## 5. 记忆分层：不是"存一份历史"

### 5.1 四层记忆

| 层 | 存什么 | 存哪 | 例子 |
|---|---|---|---|
| **工作记忆** | 当前任务的中间状态 | LangGraph state | 当前 DSL、置信度、trace |
| **情景记忆** | 发生过什么 | 会话表 | "上周你问过华东销售额" |
| **语义记忆** | 沉淀的事实/偏好 | 向量库 + 摘要 | "这个用户习惯按品牌看" |
| **程序记忆** | 怎么做事 | Prompt 模板 / few-shot | "遇到'流水'要映射成 gmv" |

### 5.2 什么才值得写进记忆（最重要的一条）

**不是所有对话都值得记。** 写入策略：

| 值得记 | 不值得记 |
|---|---|
| 用户明确确认过的口径（"我要的是支付口径"） | 每次查询的具体数值 |
| 重复出现 3 次以上的偏好（总按品牌分组） | 一次性的临时条件 |
| 用户纠正过的错误（"不是这个指标"） | 闲聊和寒暄 |

```python
def should_remember(turn: dict, history: list[dict]) -> bool:
    # 1. 用户显式确认过的口径
    if turn.get("explicit_confirmation"):
        return True
    # 2. 同类偏好出现 >= 3 次
    same_pref = sum(1 for t in history if t.get("dimensions") == turn.get("dimensions"))
    return same_pref >= 3
```

> **没有写入策略的记忆系统，三个月后一定变成噪声源。** 这是记忆系统失败最常见的原因——什么都记，等于什么都没记。

### 5.3 遗忘策略

- **按时间衰减**：30 天未访问的记忆权重 ×0.5
- **按冲突覆盖**：新事实与旧事实冲突时，旧的标记为 superseded（不是删除，保留可追溯）
- **按容量淘汰**：单用户记忆超过 N 条时，淘汰最低频的

## 6. 完整走查：一次三轮对话

```
【第 1 轮】
用户：华东近7天的销售额
  → rewrite: 无上文，原样
  → 生成 DSL → 执行 → 返回结果
  → 写 state: recent_turns=[{q:"华东近7天销售额", dsl:{...}}]

【第 2 轮】
用户：那华南呢？
  → rewrite（规则命中 "那X呢"）:
      "那华南呢" + 上一轮问题 → "华南近7天的销售额"
  → 下游完全不知道这是多轮，正常生成 DSL
  → recent_turns 追加

【第 3 轮】
用户：换成近30天
  → rewrite（规则命中 "换成X"）:
      "换成近30天" + 上一轮 → "华南近30天的销售额"
  → 正常执行
  → 触发摘要（recent_turns 超过 3 轮）:
      压缩成 "用户在查华南销售额，时间从近7天改为近30天"
```

**注意三轮里下游节点的输入都是一条完整问题**——这就是"多轮被挡在改写层"的含义。

## 7. 落地代码骨架

```
nl2dsl/session/
├── models.py     # SessionState / Turn
├── rewriter.py   # 规则 + LLM 改写
├── summarizer.py # 滚动摘要
└── store.py      # 情景记忆（会话表）
```

```python
# rewriter.py 主编排
def rewrite(question, session) -> tuple[str, str]:
    last = session.recent_turns[-1] if session.recent_turns else None

    # 1. 规则优先
    r = rule_rewrite(question, last.to_dict() if last else None)
    if r:
        return r, "rule"

    # 2. 无上文 → 不需要改写
    if not last:
        return question, "no_context"

    # 3. LLM 兜底
    try:
        return llm_rewrite(question, session.recent_turns[-3:]), "llm"
    except Exception:
        return question, "fallback"
```

## 8. 多轮怎么评测

| 用例类型 | 例子 | 判分标准 |
|---|---|---|
| **指代类** | 第 1 轮"华东销售额"，第 2 轮"那华南呢" | 第 2 轮 DSL 的 region filter = 华南，且 metric 仍为 sales_amount |
| **省略类** | 第 1 轮"近7天"，第 2 轮"换成30天" | time_range 被替换，其他不变 |
| **澄清类** | 触发澄清 → 选选项 → 继续 | 最终 DSL 包含所选口径 |
| **干扰类** | 问一个无关问题后再回来 | 不串上下文 |

**指标**：会话级任务达成率（整段对话是否达成目标）> 单轮 DSL 正确率。

## 9. 面试怎么答

**"多轮对话怎么支持？"**
> "核心不是存聊天记录，而是把当前这句话还原成完整查询。三步：① 拆 session_id 和 query_id，让检查点按会话复用；② 在进图前加改写节点，先规则匹配'那X呢''换成X'这类句式，剩下交给 LLM，失败就降级用原问题；③ 长对话按'最近3轮原文 + 更早滚动摘要'压缩。关键约束是下游节点不感知多轮，多轮的不确定性全挡在改写层。"

**"记忆怎么设计？"**
> "分四层：工作记忆进 state，情景记忆进会话表，语义记忆进向量库，程序记忆进 prompt 模板。但最重要的是**写入策略**——只记用户显式确认的口径和重复出现的偏好，不是什么对话都记。没有写入策略的记忆系统，三个月后就是噪声源。"

**"长对话上下文爆了怎么办？"**
> "滑动窗口 + 滚动摘要。最近3轮保留原文，更早的压成摘要，摘要要显式保留否定条件和具体数值——这两类最容易在压缩时丢。"

## 10. 速查

| 问题 | 答案 |
|---|---|
| 多轮本质 | 把不完整的话补成完整查询，不是存聊天记录 |
| 前提改造 | session_id ≠ query_id；检查点换持久化（Postgres/Sqlite） |
| 指代消解 | 规则优先（那X呢/换成X/再来一次），LLM 兜底，失败降级 |
| 关键约束 | 下游节点只看 rewritten_question，不感知多轮 |
| 澄清闭环 | item_id + clarification_answers 回灌，合并进问题后走完整链路 |
| 压缩 | 最近3轮原文 + 滚动摘要；摘要必须保住否定和数值 |
| 记忆四层 | 工作 / 情景 / 语义 / 程序 |
| 写入策略 | 只记显式确认 + 重复3次以上的偏好 |
| 遗忘 | 时间衰减 / 冲突覆盖 / 容量淘汰 |
| 评测 | 指代 / 省略 / 澄清 / 干扰四类，看会话级达成率 |
| 一句话 | **多轮的不确定性挡在改写层，下游永远是"单轮 + 一条完整问题"。** |
