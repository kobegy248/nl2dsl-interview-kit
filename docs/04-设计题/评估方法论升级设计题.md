## 0. 先分清两类评测

| 类型 | 判什么 | 该用什么 | 你的项目 |
|---|---|---|---|
| **客观维度** | DSL 对不对、SQL 能不能跑 | 确定性比对（canonical + 二元） | ✅ 已实现 |
| **主观维度** | 解释说得清不清楚、澄清问得对不对 | LLM-as-judge + 人工校准 | ❌ 没有 |

所以判断标准很简单：

```
能用代码判的 → 绝不交给模型（可复现、可门禁）
不能形式化的 → 交给模型，但必须先证明这个模型靠谱
```

**"证明靠谱"就是本文的重点**：一致性度量（kappa）+ 多次采样 + 统计显著性。

## 1. LLM-as-judge 的四种模式

| 模式 | 做法 | 输出 | 成本 | 一致性 |
|---|---|---|---|---|
| **Pointwise（绝对打分）** | 给单个答案打 1-5 或 0-1 | 分数 | 低 | 最低 |
| **Pairwise（成对比较）** | 给两个答案，判哪个更好 | A / B / 平局 | 中 | **最高** |
| **Rubric（评分卡）** | 拆成 3-5 条检查项，逐项判 0/1 再汇总 | 分数 + 明细 | 中 | 较高 |
| **Reference-based（对照参考）** | 给标准答案，判是否等价 | 通过/不通过 | 低 | 高（有标准答案时） |

### 1.1 为什么 pairwise 一致性最高

人有绝对尺度问题，模型也有。问"这个答案值 7 分还是 8 分"很难稳定；问"A 和 B 哪个更好"就容易得多——**比较比打分简单**，这是心理学和评测研究都验证过的。

### 1.2 你的场景该用哪个

| 评测对象 | 推荐 |
|---|---|
| 自然语言解释是否准确 | **Rubric**（拆成"指标对不对/条件全不全/有没有编造"） |
| 澄清问题是否问到位 | **Rubric** |
| 两个版本的答案谁更好 | **Pairwise**（版本对比时） |
| 有没有出现某个错误 | Reference-based |

> 对你的项目，**Rubric 最合适**——因为"DSL 解释是否准确"可以拆成可勾选项，而不是让模型打个 0.87 分。

## 2. judge 的四种偏见，以及怎么消

| 偏见 | 现象 | 缓解 |
|---|---|---|
| **位置偏见** | pairwise 时总是偏向 A（或 B） | **交换顺序各判一次**，两次一致才算数 |
| **长度偏见** | 更长/更详细的答案得分更高 | 控制长度，或在 rubric 里明确"简洁也是优点" |
| **自我偏好** | 用同一个模型当裁判，会偏向自己的输出 | **跨模型判**（你项目支持 deepseek + ark，天然有条件） |
| **谄媚偏见** | 答案语气自信就给高分 | rubric 里只判事实，不判语气 |

### 位置偏见的消除（代码）

```python
def pairwise_unbiased(judge, question, ans_a, ans_b):
    r1 = judge.compare(question, ans_a, ans_b)   # A 在前
    r2 = judge.compare(question, ans_b, ans_a)   # B 在前
    # 交换后结论必须一致，否则视为"判不准"
    if r1 == "A" and r2 == "B":
        return "A"
    if r1 == "B" and r2 == "A":
        return "B"
    return "tie_or_unstable"
```

**能识别出"判不准"本身就是价值**——它告诉你要提高 rubric 质量，而不是盲信 judge。

## 3. 一致性度量：Cohen's kappa（重点，会手算）

### 3.1 为什么不能只看"一致率"

假设 judge 和人工的一致率是 **85%**，听起来很好。但如果 90% 的样本都该判"通过"，那 judge **无脑全判通过**也能有 90% 一致率。

**原始一致率会被"类别不平衡"骗**。所以要扣掉"碰巧一致"的部分——这就是 kappa。

### 3.2 公式

```
kappa = (po - pe) / (1 - pe)

po = 观察到的实际一致率
pe = 随机情况下的期望一致率（按各自的判定分布算）
```

解读：`kappa = 1` 完全一致；`kappa = 0` 等于随机；负数是比随机还差。

### 3.3 手算（100 条样本，二分类）

| | 人工=通过 | 人工=不通过 | 合计 |
|---|---|---|---|
| **judge=通过** | 60 | 10 | 70 |
| **judge=不通过** | 5 | 25 | 30 |
| **合计** | 65 | 35 | 100 |

**第一步：算实际一致率 po**

```
po = (60 + 25) / 100 = 0.85      ← 对角线 / 总数
```

**第二步：算期望一致率 pe**（假设两者独立，按各自比例相乘）

```
人工通过率 = 65/100 = 0.65    人工不通过率 = 0.35
judge通过率 = 70/100 = 0.70    judge不通过率 = 0.30

pe = 0.65×0.70 + 0.35×0.30 = 0.455 + 0.105 = 0.56
```

**第三步：算 kappa**

```
kappa = (0.85 - 0.56) / (1 - 0.56) = 0.29 / 0.44 = 0.659
```

**结论**：原始一致率 85% 看起来很棒，但 **kappa 只有 0.66** —— 按通用标准属于"勉强可用"，还不能直接进总分。

### 3.4 通用解读标准

| kappa | 含义 | 该不该用 |
|---|---|---|
| < 0.40 | 差 | 弃用 |
| 0.40 ~ 0.60 | 一般 | 只做参考 |
| 0.60 ~ 0.80 | **较好** | 可以进总分，但要标注 |
| > 0.80 | 很好 | 可以当主指标 |

### 3.5 代码

```python
def cohen_kappa(rater_a: list[int], rater_b: list[int]) -> float:
    """二分类 kappa，输入 0/1 列表。"""
    n = len(rater_a)
    po = sum(1 for a, b in zip(rater_a, rater_b) if a == b) / n

    a1 = sum(rater_a) / n
    b1 = sum(rater_b) / n
    pe = a1 * b1 + (1 - a1) * (1 - b1)

    if pe == 1:
        return 1.0
    return (po - pe) / (1 - pe)
```

> 多分类要把 `pe` 改成"每个类别的边缘概率乘积求和"，原理一样。

## 4. 多次采样：把 judge 的抖动压下去

单次调用 → 模型温度、上下文微差都会让结果跳。做法是**同一题判 3 次，看一致性**：

```python
def judge_with_votes(judge, case, n=3) -> JudgeResult:
    votes = [judge.judge_one(case) for _ in range(n)]     # ["pass","pass","fail"]
    pass_rate = votes.count("pass") / n
    return JudgeResult(
        passed=pass_rate >= 2/3,        # 多数票
        agreement=pass_rate if pass_rate >= 0.5 else 1 - pass_rate,
        raw=votes,
    )
```

**关键产出是 `agreement`**：

- 3 次全同 → agreement = 1.0，很可信；
- 2:1 → agreement = 0.67，边缘；
- 报告里把 agreement < 0.6 的用例单独列出来——**这些是 judge 自己也没把握的题，应该转人工**。

## 5. 统计显著性：你那个 86.9% 到底可不可信

### 5.1 先看问题有多严重

你现在的评测是 10 例数据集：

```
每道题 = 10 个百分点
72.8% → 7.3 题对
86.9% → 8.7 题对

差 1.4 题 → 分数差 14 个百分点
```

**一道题的正误就能让分数跳 10 个点**。这种情况下"从 72.8 提升到 86.9"极可能只是换了 1-2 道题的运气。

### 5.2 Bootstrap 置信区间（原理 + 代码）

**思路**：手里只有一份样本，就"假装"总体是它——有放回地重复抽样 1000 次，每次算一个均值，看这些均值的分布。

```python
import numpy as np

def bootstrap_ci(scores: list[float], n_boot=1000, alpha=0.05):
    scores = np.array(scores)
    means = [np.mean(np.random.choice(scores, size=len(scores), replace=True))
             for _ in range(n_boot)]
    lo = np.percentile(means, alpha / 2 * 100)
    hi = np.percentile(means, 100 - alpha / 2)
    return lo, hi
```

**手算直觉**：假设 10 例里有 7 例通过（0.7）。重采样时，某一次可能抽到 8 例通过 → 0.8；另一次抽到 5 例 → 0.5。1000 次之后，均值的分布可能就是 `[0.5, 0.9]` 这个区间。

**结论写法**：

```
❌ 准确率 69.7%
✅ 准确率 69.7%（95% CI: 57.2% ~ 80.9%，n=50）
```

置信区间宽，说明样本不够——**这本身就是结论**。

### 5.3 配对比较（判断 A 版是否真的比 B 版好）

**不能**拿两次独立运行的均值直接比精度，因为两次用的可能是不同题目的运气。正确做法是**同一批题、只换版本**，然后用配对 bootstrap：

```python
def paired_bootstrap_diff(scores_a, scores_b, n_boot=1000):
    """A 版和 B 版在同一批用例上的分数，算差值分布。"""
    diffs = []
    n = len(scores_a)
    for _ in range(n_boot):
        idx = np.random.randint(0, n, n)        # 同一组索引同时取两边
        diffs.append(np.mean(np.array(scores_a)[idx])
                     - np.mean(np.array(scores_b)[idx]))
    lo, hi = np.percentile(diffs, [2.5, 97.5])
    return np.mean(diffs), lo, hi
```

**判读规则**：

```
如果 CI 不包含 0  → 差异显著（95% 置信）
如果 CI 包含 0    → 无法判断，可能只是噪声
```

例：差值均值 +0.14，CI `[-0.02, 0.31]` → **包含 0，不能宣称提升**。

### 5.4 效应量

显著性只回答"是不是噪声"，不回答"有多大用"。10 例的样本里，1 道题的差别就能"显著"。

```
相对提升 = (新 - 旧) / 旧
绝对提升 = 新 - 旧
```

报告里两个都写。业务上更关心绝对提升（准确率从 70% 到 72%，还是 70% 到 85%）。

## 6. 小样本怎么办

| 做法 | 说明 |
|---|---|
| **标注"样本不足"** | n < 30 时，明确写在报告里 |
| **报区间不报点** | 都带 CI |
| **固定用例集** | 版本对比必须用同一批题（配对） |
| **分层看** | 按难度/类别分组看，比总分更稳 |
| **扩样本** | 最终解法还是扩到 200+ 条 |

> 面试时要敢说："这个 10 例数据集的波动区间是 ±15 个百分点，任何小于 15 点的提升我都不会当成结论。"——这句话本身就是资深信号。

## 7. 在线评测：离线好不代表线上好

| 手段 | 做法 | 回答什么问题 |
|---|---|---|
| **Shadow** | 新版本影子跑，不影响用户，只记录 | 新版本在真实流量上会不会崩 |
| **灰度 / AB** | 按比例分流 | 新版本是否真的更好（有真实用户） |
| **反馈回流** | 差评 → 人工确认 → 进回归集 | 线上错过的题永不再犯 |
| **漂移监控** | 监控成功率、澄清率、P95 随时间变化 | 模型升级/数据变化的影响 |

**最小闭环**：

```
用户点"踩" → 该 query 的 trace + DSL 落库
          → 人工确认
          → 写入 regression.yaml
          → 下次 CI 拦住同样的错
```

## 8. 数据质量：两个隐形杀手

### 8.1 数据泄漏

用例和"训练/提示"数据重叠——比如把线上问过的问题又加进评测集，模型靠记忆答对。

**检查方法**：评测集的 query 与 prompt few-shot 示例、history 集合做相似度比对，超过阈值就人工看。

### 8.2 标注质量

- **单人标注** = 没有一致性可言；
- **双人标注 + 仲裁** = 至少能算出标注者之间的 kappa，低于 0.6 说明**评测任务本身定义不清**，先改定义再加数据。

## 10. 面试怎么答

**"你们用 LLM-as-judge 吗？"**
> "评测框架里不用，刻意的——核心维度都能 canonical 化，交给模型反而不可复现。运行时有两个 LLM 裁判：confidence 判 DSL 质量、verify_dsl 执行后自检，它们只告警不阻断。"

**"LLM 判分不可靠怎么办？"**
> "四件事：只出 PASS/FAIL 不出小数分；用 rubric 拆成可勾选项；同一题判 3 次投票并记录一致率；上线前用人工金标集算 Cohen's kappa，到 0.8 才允许进总分。"

**"怎么证明这次提升不是噪声？"**
> "用配对 bootstrap：同一批用例上新旧两个版本各跑一遍，算差值分布，CI 不包含 0 才算显著。我现在的问题是只报点估计——10 例数据集一道题就是 10 个百分点，所以任何小于 15 点的提升我都不敢当结论。"

**"kappa 是什么、为什么要它？"**
> "扣掉随机一致后的真实一致率。因为原始一致率会被类别不平衡骗——如果 90% 样本都该判通过，judge 无脑全判通过也有 90% 一致率。kappa = (po-pe)/(1-pe)，我算过一个例子：原始一致率 85% 但 kappa 只有 0.66。"

## 11. 速查

| 问题 | 答案 |
|---|---|
| 什么该交给 judge | 只有不可形式化的：解释质量、澄清质量、多轮 |
| 四种模式 | pointwise / pairwise / rubric / reference |
| 哪种最稳 | pairwise（比较比打分简单）；你的场景用 rubric |
| 四种偏见 | 位置 / 长度 / 自我偏好 / 谄媚 |
| 位置偏见消法 | A/B 交换各判一次，不一致=判不准 |
| 一致性 | Cohen's kappa = (po-pe)/(1-pe)，>0.8 才能当主指标 |
| 原始一致率的坑 | 类别不平衡时会虚高（85% 可能只是 0.66 的 kappa） |
| 多次采样 | 3 次投票，记录 agreement，<0.6 转人工 |
| 置信区间 | bootstrap 重采样 1000 次取分位数 |
| 显著判断 | 配对 bootstrap，差值 CI 不含 0 才算显著 |
| 小样本 | n<30 标注"样本不足"；10 例 = 每题 10 个百分点 |
| 一句话 | **确定性维度是考试，judge 是面试；面试官必须先考及格（kappa）才能上岗。** |
