# 评估方法论升级：面试官会怎么一路追问（未实现 · 问答版）

> **证据边界**：这篇里的"升级"部分，评测框架里**没有做**。
> - 已经有的：能代码判的题——canonical 规范化 + 二元判定、真实链路跑、baseline 回归门禁。见 [Agent 评估体系专项](../03-专项/Agent评估体系专项.md)。
> - 没有的：AI 当裁判打分、置信区间、显著性检验、线上评测。
> - 评测集一共 **77 条**；按域跑时银行、供应链各只有 10 条。
> - 运行时有两个 AI 裁判：`confidence`（低于 0.6 转澄清，算拦截）、`verify_dsl`（只告警）。
> - 面试口径："没做。要做的话，第一步不是上 AI 打分，是先证明裁判靠得住。"

**这份文档怎么用**：下面是一条真实的追问链。每一问都按「他真正想问什么 → 一句话怎么答 → 他继续追时怎么展开 → 别说错」写。**先背第 0 节的问题树，再逐问看。**

## Q1：你们怎么评测的？

**他真正想问的**：你有没有一套能复现、能拦回归的评测，而不是"我们试了试，感觉还行"。

**一句话怎么答**：

> 分四类十二个维度加权：语义（意图、指标、维度、过滤）、计划（join、limit、排序）、执行（SQL 跑不跑通、结果对不对）、治理（权限、脱敏、审计）。能代码判的一律代码判——canonical 规范化之后做二元判定，跑真实链路，最后用 baseline 做回归门禁。

**他继续追时怎么展开**：

核心判断只有一句：**能用代码判的，绝不交给模型。**

原因很实在：代码判分可复现、能进 CI、能卡住回归；模型判分今天 80、明天 78，你没法拿它当门禁。

所以现在的框架里**没有** AI 裁判，这是刻意的，不是不会。

**别说错**："我们用 GPT 给答案打分。"——你没做，一问细节就穿帮。

## Q2：这个 86.9% 可信吗？

**他真正想问的**：你懂不懂样本量。很多人报个小数就以为很精确。

**一句话怎么答**：

> 不太可信。我们的题太少：按域跑的时候，银行和供应链各只有 10 条，**一道题就是 10 个百分点**；全量 77 条，一道题也有 1.3 个点。所以我现在只敢报区间，不敢报单点。

**他继续追时怎么展开**：

先算给他看：

```
10 条题的域：72.8% → 对了 7.3 道；86.9% → 对了 8.7 道
差了 1.4 道题 = 14 个百分点
```

**换一两道题，分数就能跳 14 个点。** 这时候说"提升了 14 个点"，很可能只是运气。

所以正确写法是带区间：

```
❌ 准确率 69.7%
✅ 准确率 69.7%（95% 区间：59.4% ~ 80.0%，样本 77 条）
```

区间怎么来的？大白话：**手里只有一份成绩单，就把它当成全校的样子，反复抽 1000 次（每次抽完放回），看平均分在什么范围里晃。**

```python
import numpy as np

def bootstrap_ci(scores, n_boot=1000):
    scores = np.array(scores)
    means = [
        np.mean(np.random.choice(scores, size=len(scores), replace=True))
        for _ in range(n_boot)
    ]
    return np.percentile(means, 2.5), np.percentile(means, 97.5)
```

**加分句**："区间很宽，本身就是结论——它告诉你该扩样本了，而不是告诉你系统变差了。"

**别说错**："86.9%，比上一版高 14 个点。"——没区间，等于没结论。

## Q3：那你怎么证明新版真的比旧版好？

**他真正想问的**：你知不知道"两次独立跑分"不能直接比。

**一句话怎么答**：

> 同一批题、只换版本，做配对比较。差值区间不包含 0 才算显著；包含 0 就只能说"还看不出来"。

**他继续追时怎么展开**：

为什么不能拿两次独立运行比？因为两次可能抽到不同难度的题。A 版碰巧考了简单题，B 版碰巧考了难题，比出来的差值没有意义。

正确做法：**同一批题，两边一起抽题号，算差值。**

```python
def paired_bootstrap_diff(scores_a, scores_b, n_boot=1000):
    diffs = []
    n = len(scores_a)
    for _ in range(n_boot):
        idx = np.random.randint(0, n, n)      # 同一组题号，两边一起抽
        diffs.append(
            np.mean(np.array(scores_a)[idx]) - np.mean(np.array(scores_b)[idx])
        )
    return np.mean(diffs), np.percentile(diffs, 2.5), np.percentile(diffs, 97.5)
```

判读规则：

```
区间不包含 0  → 真的更好（95% 把握）
区间包含 0    → 说不准，可能只是运气
```

例子：平均高了 14 个点，但区间是 `[-2, 31]`——**跨过 0 了，不能宣称提升。**

再补一句更值钱的：

> 显著只回答"是不是运气"，不回答"有多大用"。10 条题的小域里，多对 1 道就能"显著"，但业务上可能毫无意义。所以报告里绝对提升和相对提升都要写。

**别说错**："新版提升 2.1%。"——如果区间是 `[-6.4%, +10.2%]`，这句话就是错的。

## Q4：解释质量、澄清质量这种主观的，你们怎么评？

**他真正想问的**：客观题你能用代码判，那"话说得清不清楚"呢？

**一句话怎么答**：

> 这类只能请 AI 当裁判。但请之前先做一件事：**证明这个裁判靠得住**，不然它的分数就是噪声。

**他继续追时怎么展开**：

AI 裁判有四种判法，稳定性差很多：

| 判法 | 大白话 | 稳不稳 |
|---|---|---|
| 打分 | 给一个答案打 1–5 分 | **最不稳** |
| 两两比 | 两个答案选一个 | **最稳** |
| 检查表 | 拆成 3–5 条，逐条判"是/否" | 较稳 |
| 对答案 | 拿标准答案比对 | 有答案时很稳 |

为什么打分最不稳？因为**人和模型都没有稳定的绝对刻度**。问"这个答案值 7 分还是 8 分"，同一个人上午下午能给出不同答案；问"A 和 B 哪个好"，就稳定得多。**比较比打分简单。**

**你们该用检查表。** 比如"解释准不准"拆成三条：

- 指标用对了吗？
- 过滤条件说全了吗？
- 有没有编造不存在的东西？

每条勾"是/否"，比让模型打个 0.87 分可靠得多。

**别说错**："让模型打 1–5 分，取平均。"——这是最不稳的做法，而且没法校准。

## Q5：AI 判得准吗？

**他真正想问的**：你敢不敢用一个没校准的模型当裁判。

**一句话怎么答**：

> 先和人工对一批题，算 kappa。0.6 以下不用，0.6 到 0.8 只能参考，0.8 以上才让它当主指标。

**他继续追时怎么展开**：

校准流程一共四步：

1. 挑 30–50 条有代表性的题，人工判一遍（金标）；
2. 让 AI 裁判判同一批题；
3. 算"一致率"，但**更要算 kappa**；
4. kappa 不达标，先改检查表，别急着用。

这是整条链里最关键的一问：**答不出 kappa，说明你没真正做过评测，只是调过 prompt。**

**别说错**："我们人工看了下，感觉挺准的。"——"感觉"不是指标。

## Q6：kappa 是什么？为什么不能只看一致率？

**他真正想问的**：你知不知道"类别不平衡"会把一致率骗高。

**一句话怎么答**：

> kappa 是扣掉"蒙对"之后的真实一致率。因为一致率会被类别不平衡骗——90% 的题都该判通过，裁判全判通过也能有 90% 一致率。

**他继续追时怎么展开**：

手算一遍，100 道题，只分"通过/不通过"：

| | 真人判通过 | 真人判不通过 | 合计 |
|---|---|---|---|
| **AI 判通过** | 60 | 10 | 70 |
| **AI 判不通过** | 5 | 25 | 30 |
| **合计** | 65 | 35 | 100 |

**第一步：实际对上多少**

```
po =（60 + 25）/ 100 = 0.85
```

**第二步：蒙也能对上多少**

真人通过率 65%，AI 通过率 70%。如果两边各判各的、纯靠运气：

```
pe = 0.65 × 0.70 + 0.35 × 0.30 = 0.455 + 0.105 = 0.56
```

**第三步：扣掉蒙对的部分**

```
kappa =（0.85 − 0.56）/（1 − 0.56）= 0.29 / 0.44 = 0.66
```

**结论：一致率 85% 看着漂亮，kappa 只有 0.66——勉强能用，不能直接进总分。**

```python
def cohen_kappa(rater_a, rater_b):
    n = len(rater_a)
    po = sum(1 for a, b in zip(rater_a, rater_b) if a == b) / n
    a1 = sum(rater_a) / n
    b1 = sum(rater_b) / n
    pe = a1 * b1 + (1 - a1) * (1 - b1)
    return 1.0 if pe == 1 else (po - pe) / (1 - pe)
```

**别说错**："一致率 85%，挺高的。"——这正是要被追问的地方。

## Q7：AI 裁判有什么偏心？

**他真正想问的**：你用过，而且踩过坑。

**一句话怎么答**：

> 四种：位置偏心、长度偏心、自我偏好、马屁精。都有办法防。

**他继续追时怎么展开**：

| 偏心 | 大白话 | 怎么防 |
|---|---|---|
| 位置偏心 | 两两比时总偏向先看到的那个 | A/B 交换顺序各判一次，两次一致才算数 |
| 长度偏心 | 写得长就给高分 | 控制长度，检查表里写明"简洁也算好" |
| 自我偏好 | 同一个模型当裁判，偏向自己的输出 | 换个模型判（你们有 deepseek 和 ark） |
| 马屁精 | 语气自信、话说得漂亮就给高分 | 检查表只判事实，不判语气 |

位置偏心的防法（代码短，但思路值钱）：

```python
def pairwise_unbiased(judge, question, ans_a, ans_b):
    r1 = judge.compare(question, ans_a, ans_b)   # A 在前
    r2 = judge.compare(question, ans_b, ans_a)   # B 在前
    if r1 == "A" and r2 == "B":
        return "A"
    if r1 == "B" and r2 == "A":
        return "B"
    return "判不准"
```

**加分句**："'判不准'本身也是信息——它说明检查表写得不好，而不是让你盲信裁判。"

**别说错**："我们只判一次，结果挺稳定的。"——模型有随机性，单次结果不可信。

## Q8：判一次不稳怎么办？

**他真正想问的**：你知不知道模型输出会抖。

**一句话怎么答**：

> 同一题判三次，少数服从多数，同时记下三次的一致程度。一致程度低于 0.6 的题，转人工。

**他继续追时怎么展开**：

```python
def judge_with_votes(judge, case, n=3):
    votes = [judge.judge_one(case) for _ in range(n)]   # 比如 ["过","过","不过"]
    pass_rate = votes.count("过") / n
    return {
        "passed": pass_rate >= 2/3,                    # 多数票
        "agreement": max(pass_rate, 1 - pass_rate),    # 三次有多一致
        "raw": votes,
    }
```

- 三次全一样 → 1.0，可信；
- 2:1 → 0.67，边缘；
- 报告里把一致程度 < 0.6 的单独列出来 → **裁判自己都没把握，转人工。**

**别说错**："判一次就定了。"——连模型自己都会变，你怎么敢定。

## Q9：样本太少怎么办？

**他真正想问的**：你知不知道小样本的结论不可外推。

**一句话怎么答**：

> 五件事：标注"样本不足"、报区间不报单点、版本对比用同一批题、按难度分层看、最终扩到 200 条以上。

**他继续追时怎么展开**：

| 做法 | 大白话 |
|---|---|
| 标注样本不足 | 少于 30 条，报告里写明 |
| 报区间 | 别只说 69.7%，要说 57% 到 81% |
| 固定题库 | 版本对比必须考同一批题 |
| 分层看 | 按难度、类别分开看，比总分稳 |
| 扩样本 | 最终解法还是扩到 200 条以上 |

**加分句**："按小域跑只有 10 条题，一道题 10 个点；全量 77 条，一道题 1.3 个点。所以我不看单点提升，先看区间——区间跨 0，就当我没提升。"

## Q10：离线评测好，线上就一定好吗？

**他真正想问的**：你知不知道离线集和真实流量是两回事。

**一句话怎么答**：

> 不一定。离线是小考，线上是期末考。要做四件事：影子、灰度、差评回流、漂移监控。

**他继续追时怎么展开**：

| 手段 | 大白话 | 回答什么问题 |
|---|---|---|
| 影子 | 新版本在后台偷偷跟着跑，不影响用户 | 真实流量下会不会崩 |
| 灰度 / AB | 分一部分用户去用新版本 | 是不是真的更好 |
| 差评回流 | 用户点"踩"→ 人工确认 → 记进错题本 | 错过的题不再犯 |
| 漂移监控 | 盯着成功率、澄清率、响应时间的变化 | 模型升级、数据变了有没有影响 |

最小闭环：

```
用户点"踩" → 这道题的记录落库
          → 人工确认
          → 写进回归题库
          → 下次上线自动拦住同样的错
```

**别说错**："离线 90%，线上应该也差不多。"——线上有真实用户、真实数据分布、真实脏问题。

## Q11：评测集本身可靠吗？

**他真正想问的**：你有没有想过"评测集本身会骗人"。

**一句话怎么答**：

> 两个坑：漏题和标准不清。漏题是评测题和提示词示例重复，模型背过答案；标准不清是一个人判卷，没有一致性可言。

**他继续追时怎么展开**：

**漏题（数据泄漏）**：评测题如果和 few-shot 示例、history 集合重复，模型是"背过答案"才答对的。

查法：把评测题和示例做相似度比对，超过阈值就人工看。

**标准不清（标注质量）**：

- 一个人判：没有"一致不一致"这回事；
- 两个人判 + 一个仲裁：至少能算 kappa；如果两个人都吵不出结果，说明**题目本身没定义清楚**，先改定义，再加题。

**别说错**："评测集是我自己写的，肯定没问题。"——自己写的最容易漏题。

---

## Q12：这些你们做了吗？

**他真正想问的**：你会不会把设计说成实现。

**一句话怎么答**：

> 没做。现在有的是：代码判分、真实链路、baseline 门禁，加上运行时两个 AI 裁判——`confidence` 低于 0.6 会转澄清（算拦截），`verify_dsl` 只告警不阻断。评测框架里的 AI 裁判、置信区间、显著性检验，都还没做。

**他继续追时怎么展开**：

如果问"那你会先做哪个"：

> 先做 kappa 校准，不是先上 AI 打分。因为裁判不可信，打出来的分全是噪声，做了也白做。第二步才是置信区间——先把"一道题 10 个点"这个问题暴露出来，团队才会愿意扩样本。

**别说错**："我们已经在用 AI 打分了。"——这是最容易翻车的一句。

## 名词解释（大白话）

| 词 | 大白话 |
|---|---|
| 客观维度 / 主观维度 | 代码能对答案的题 / 得靠人判断的题 |
| AI 裁判（LLM-as-judge） | 让模型来判分 |
| 打分 / 两两比 / 检查表 / 对答案 | 打绝对分 / 两个选一个 / 逐条勾是或否 / 和标准答案比 |
| kappa | 扣掉蒙对之后的真实一致率 |
| 置信区间 | 分数大概在哪个范围里飘 |
| bootstrap | 反复有放回抽样，看分数怎么晃 |
| 配对比较 | 同一批题、只换版本，再比 |
| 显著 | 差异不太可能是运气 |
| 效应量 | 差异到底有多大，值不值得高兴 |
| 数据泄漏 | 评测题和提示词示例重复，等于考前漏题 |
| 影子（shadow） | 新版本在后台跟着跑，不影响用户 |
| AB / 灰度 | 分一部分用户去用新版本 |
| 漂移 | 指标随时间悄悄变差 |
