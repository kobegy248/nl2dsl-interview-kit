# 评估方法论升级设计题（未实现）

> **证据边界**：本文全部是**设计提案**。NL2DSL 的评测框架里**没有 LLM-as-Judge 打分、没有置信区间、没有显著性检验、没有检索层指标**。
> 面试口径：「我们没做，但在做之前我会先解决 judge 可信度问题」。
> 已实现部分见 [Agent 评估体系专项](../03-专项/Agent评估体系专项.md)。

---

## 0. 定位

一句话：**"我的评测能判对错，但不能回答'这次提升是不是噪声'和'judge 本身靠不靠谱'。"**

已有：canonical 二元判定、真实链路执行、baseline 门禁、运行时 LLM 裁判。
缺口：统计显著性、judge 校准、检索层指标、在线闭环、安全用例。

## 一、缺口清单

| 缺口 | 后果 |

| 无安全用例集 | 越权、注入没有回归覆盖 |

## 二、未采用的技术

### 2.1 LLM-as-Judge 的标准化做法

| 技术 | 说明 | 现状 |
|---|---|---|
| Pointwise 打分 | 给单个答案打绝对分 | 运行时用了，但无 rubric、无锚点 |
| **Pairwise 比较** | 两个答案比谁更好，一致性远高于绝对分 | ❌ |
| **Rubric 评分卡** | 拆成可勾选检查项，逐项 0/1 再汇总 | 部分（verify_dsl 有 4 条检查项） |
| Few-shot 锚点 | 给满分/零分样例校准尺度 | 部分（verify_dsl 给了 4 个示例） |
| **多次采样投票** | 同一 judge 跑 3~5 次取多数 | ❌ |
| **位置交换双判** | pairwise 时交换 A/B 顺序 | ❌ |
| **跨模型交叉判** | 不同厂模型判同一批 | ❌（项目支持 deepseek/ark 双 provider，有条件） |
| **Judge 元评估** | 拿人工标注集测 judge 本身（kappa） | ❌ |
| 自我偏好规避 | judge 不能和生成用同一模型 | ❌ |

> 现状定性：**有一个"LLM 裁判"的雏形，但它是单次、单模型、无校准、无一致性验证的裸调用。**

## 三、怎么补

### 3.1 原则：确定性维度是"考试"，LLM-judge 是"面试"

| 评测对象 | 能否形式化 | 应该用什么 |
|---|---|---|
| DSL 语义正确性 | 能 | **确定性比对**（现状） |
| SQL 可执行性、结果一致性 | 能 | **确定性执行**（现状） |
| 自然语言解释是否准确 | 不能 | **LLM-judge** |
| 澄清问题是否问到位 | 不能 | **LLM-judge** |
| 多轮指代是否正确 | 部分 | 规则 + judge 兜底 |
| 检索相关性 | 半结构化 | 人工标注 + judge 辅助 |

> **一句话：考试不请考生自己当阅卷人；面试可以请第三方，但要先证明第三方靠谱。**

### 3.2 方案 A：让 judge 可信（1~2 周）

1. **金标集**：30~50 条人工标注"解释是否准确"，作为 judge 的考卷。
2. **一致性度量**：算 judge 与人工的 Cohen's kappa（>0.8 可用，0.6~0.8 勉强，<0.6 弃用）。
3. **多次采样**：同一用例判 3 次，2:1 以上才算 PASS，同时记录一致率。
4. **跨模型交叉判**：deepseek + ark 都判 PASS 才算 PASS。
5. **二元输出**：judge 只出 PASS/FAIL，不产生 0.87 这种分数（延续项目二元原则）。

```python
@dataclass
class JudgeResult:
    passed: bool
    reason: str
    agreement: float        # 3 次采样一致率
    raw: list[str]

class Judge(ABC):
    @abstractmethod
    def judge(self, case, observation) -> JudgeResult: ...
```

**规则**：judge 一致性 < 0.8 就不进总分，只做参考。

### 3.3 方案 B：统计化（1 周）

```python
def bootstrap_ci(scores: list[float], n: int = 1000, alpha=0.05):
    means = [np.mean(np.random.choice(scores, len(scores))) for _ in range(n)]
    return np.percentile(means, [alpha/2*100, (1-alpha/2)*100])
```

- 报告写 `69.7% (95% CI: 57~81)` 而不是裸的 69.7%；
- 版本对比用配对检验（同一批用例），而不是比两个均值；
- 小样本（<30）时明确标注"样本不足，结论仅供参考"。

### 3.4 方案 C：体系化（1~2 月）

1. **三层评测**
   - L1 确定性核心维度：CI 全量，零容忍
   - L2 LLM-judge 体验维度：CI 抽样，容忍 -3%
   - L3 人工抽检（每周 20 条）：校准 L2，发现 judge 漂移
2. **检索专项**：Recall@K / MRR + 分通道归因（详见 [RAG 召回评估与优化设计题](RAG召回评估与优化设计题.md)）。
3. **反馈进评测**：差评 → 人工确认 → 写入 `regression.yaml` → 下次 CI 拦住同样的错。
4. **安全用例集**：越权、注入、敏感字段，每类 5~10 条，进 governance 维度并绑门禁。
5. **在线**：shadow 流量 + 关键指标看板 + 模型升级漂移告警。

## 四、设计类追问

**Q1：LLM 判分不可靠怎么办？**
> "四件事：judge 只出 PASS/FAIL 不出小数分；rubric 拆成可勾选项；同一用例跑 3 次投票并记录一致率；上线前用 40 条人工金标集校准 kappa——到 0.8 才允许进总分，不到就只做参考。"

**Q2：怎么证明这次提升不是噪声？**
> 诚实版："目前证明不了。10 例数据集三次跑出 72.8/86.9/89.8，点估计不可靠。正确做法是 bootstrap 置信区间 + 配对显著性检验，这是我评测体系最大的方法论缺口。"

**Q3：怎么证明 judge 本身可信？**
> "做 judge 的元评估：拿人工标注集当考卷，算 judge 与人的一致率（kappa）、跨模型一致率、以及 judge 的假阴性率（判 PASS 但实际错）。这三个数不达标，judge 就不能进总分。"

**Q4：RAG 的检索效果怎么评？**
> "标注 query→相关条目，算 Recall@5 / MRR / nDCG；再分通道测（关键词、向量、精排后），定位哪层拖后腿。我目前只评了端到端，这是缺口。"

**Q5：怎么评测多轮 agent？**
> "三类用例：指代类、澄清类、省略类；指标是会话级任务达成率，不是单轮 DSL 正确率。"

**Q6：离线评测好就够了，为什么还要在线？**
> "离线集是采样出来的，线上分布会漂。要有 shadow/灰度看真实流量下的成功率、澄清率、P95；还要监控模型升级后的指标漂移。"
